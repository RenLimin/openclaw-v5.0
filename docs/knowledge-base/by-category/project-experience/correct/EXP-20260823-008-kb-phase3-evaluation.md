# 知识库阶段 3 启动评估

## 1. 背景

Rex 2026-08-23 08:07 授权「开始知识库自建」。ADR-003 定义了 3 阶段演进 + 7 个
阶段 3 触发条件，且 §5.3 明确缓解措施是「**7 个触发条件中至少 2 个才评估**」。

直接开工会与自己写的 ADR 冲突。所以先建阶段 2 工具链（`scripts/kb_index.py`），
用它把 3 个**定性**条件转成可测数据，再决定阶段 3。

工具链本身不是绕路 —— ADR-003 §4.4 列的自建系统六项子能力里，
解析/索引/检索/关联四项就是这个工具，阶段 3 直接复用。

## 2. 七条件实测结果

| # | 条件 | 阈值 | 实测 | 达成 |
|---|---|---|---|---|
| 1 | 文档数量爆炸 | >200 篇 | 知识库 19 篇（全 docs 35） | ❌ |
| 2 | AI 检索效率瓶颈 | 完成任务 >3 步 | **1 步**（见 §3.1） | ❌ |
| 3 | 跨维度查询需求强 | 频繁交叉查询 | 三维覆盖 8/12 格，**L3/L4 仅 design 有内容** | ❌ |
| 4 | 关系/链接需求 | 需显式关系 | 15/16 已连通，**孤岛仅 1** | ❌ |
| 5 | 团队扩张 | ≥3 人 | 2（Limin Ren / OpenClaw） | ❌ |
| 6 | 跨系统移植 | 有需求 | 无 | ❌ |
| 7 | 时间兜底 | 2027-Q1 | 2026-08 | ❌ |

**0/7 达成。ADR-003 要求 ≥2 才评估 → 阶段 3 暂缓。**

## 3. 三个定性条件的实测方法

### 3.1 条件 2：检索效率（原本最容易凭感觉误判）

「找出 L2 层运维阶段与 cron 相关的经验」——

```bash
python3 scripts/kb_index.py --query layer=L1 stage=manage tag=cron
# → 1 步命中 2/19，含完整路径与 tags
```

阈值是 >3 步，实测 1 步。**19 篇规模下 grep + 结构化查询完全够用**，
瓶颈不存在。这条如果不实测，很容易主观认为"检索很麻烦"。

### 3.2 条件 3：跨维度查询（数据揭示真问题不在工具）

`--stats` 三维交叉覆盖：

| layer | design | develop | manage |
|---|---|---|---|
| L1 | 5 | 1 | 7 |
| L2 | 7 | 2 | 5 |
| L3 | 4 | 0 | 0 |
| L4 | 3 | 0 | 0 |

非空 8/12。**L3/L4 的 develop/manage 全空** —— 因为业务层还没开始建，
不是查询能力不足。真瓶颈是**内容缺口**，自建系统解决不了。

### 3.3 条件 4：关系链接（差点误判为"需要图数据库"）

`--xref` 结果：16 个带 ID 文档，**孤岛只有 1 个**（ADR-009，昨天刚写还没被引用），
断链 0。frontmatter `related` + 正文 ID 提及已经足够表达关系。

## 4. 工具首跑抓到 34 个真问题

这是本次最实际的收益 —— 问题一直存在，只是没有工具就看不见：

| 类别 | 数量 | 例子 |
|---|---|---|
| schema 漂移 | 15 | `layer` vs `layers`、`kind` vs `category`、`type: experience-card` vs `experience` |
| 缺 `stage` 字段 | 11 | 全部 9 篇 ADR + 2 篇 EXP —— **三维查询直接漏掉它们** |
| 相对链接失效 | 3 | ADR-004/005/006 写 `./components/...`，实际在 `docs/architecture/components/...` |
| 误报（工具自身 bug） | 2 | `EXP-20261121-001 之类` 是占位举例，被正则当成真引用 |
| 导航页误归类 | 3 | INDEX/README 不承载知识，不该要求三维 frontmatter |

修完：**阻断性 0 / 警告 0 / 漂移 0**。

### 关键教训

**「缺 stage」是静默失败**，与 ADR-008 三态模型同类：文档看起来正常、
能读能引用，但三维查询会静默漏掉它 —— 不报错，只是不出现在结果里。
11/19 篇缺失意味着**三维查询在建工具前基本是残的**，而这一点在有工具前无法察觉。

## 5. 决策

| 项 | 结论 |
|---|---|
| 阶段 3 自建系统 | **暂缓** — 0/7 条件，ADR-003 §5.3 要求 ≥2 |
| 阶段 2 工具链 | **已交付** `scripts/kb_index.py` |
| 下一步 | 补 L3/L4 内容（真瓶颈），而非建系统 |
| ADR-003 | **不改** — 它的触发条件机制被验证有效，正好挡住了一次过早自建 |

## 6. 防回归

`scripts/git-hooks/pre-commit` 第 3 段集成：

- `--validate` 有阻断性错误（非法 layer/stage/category、重复 ID、缺 title）→ **拒绝提交**
- `--emit-index` 自动重生 INDEX.md 派生小节并加入提交
- 实测验证：造 `layers: [L9]` + `stage: nonsense` 的文件，commit 被成功拦下

## 7. 可复用结论

1. **触发条件写进 ADR 是有用的**。它挡住了一次本可以发生的过早自建 —— 若没有量化阈值，
   「知识库该升级了」这种感觉几乎必然通向重写。
2. **定性条件也能实测**，前提是先有工具。工具比系统便宜两个数量级，且是系统的子集。
3. **建工具的副产品可能比工具本身值钱**：34 个隐藏问题、11 篇文档的静默检索缺失。
4. **YAGNI 的正确用法不是拒绝建设，是先量化再决定**。
