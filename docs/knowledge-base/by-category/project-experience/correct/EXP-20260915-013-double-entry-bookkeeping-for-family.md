# [EXP-20260915-013] 借贷记账法在家庭理财中的落地实践

## 1. 背景

家庭理财系统如果用「单式记账」（一条记录 = 金额 + 分类），初期简单但很快会遇到问题：
- 转账怎么记（从 A 卡转到 B 卡，既不是收入也不是支出）？
- 信用卡还款怎么记（花的时候是支出，还款时又扣一次？）？
- 如何保证数据一致性（漏记、重记没法发现）？

业界成熟方案（GnuCash / Firefly III）全部采用**复式记账（借贷记账法）。

## 2. 问题

如何在家庭理财场景中落地借贷记账法，同时：
1. 保持会计恒等式（资产 = 负债 + 权益）的严格一致
2. 对用户友好（不需要懂会计也能用）
3. 支持 5 大类账户（资产 / 负债 / 收入 / 费用 / 权益）

## 3. 方案

### 3.1 账户分类（5 大类）

| 类型 | 余额方向 | 增加方向 | 举例 |
|---|---|---|---|
| 资产 (ASSET) | 借方 | 借 | 现金、银行卡、投资、房产 |
| 负债 (LIABILITY) | 贷方 | 贷 | 信用卡、房贷、车贷 |
| 收入 (INCOME) | 贷方 | 贷 | 工资、投资收益、兼职 |
| 费用 (EXPENSE) | 借方 | 借 | 餐饮、交通、房租、娱乐 |
| 权益 (EQUITY) | 贷方 | 贷 | 期初余额、本年利润 |

### 3.2 每笔交易 = 借 + 贷

**核心规则**：每笔交易必有一个借方账户和一个贷方账户，金额相等。

**常见场景举例**：

| 场景 | 借方 | 贷方 | 说明 |
|---|---|---|---|
| 工资到账 | 银行卡 (资产) | 工资 (收入) | 资产↑ 收入↑ |
| 吃饭花钱 | 餐饮 (费用) | 银行卡 (资产) | 费用↑ 资产↓ |
| 信用卡消费 | 餐饮 (费用) | 信用卡 (负债) | 费用↑ 负债↑ |
| 信用卡还款 | 信用卡 (负债) | 银行卡 (资产) | 负债↓ 资产↓ |
| 转账 (A→B) | B 卡 (资产) | A 卡 (资产) | 资产内部转移 |
| 期初余额 | 银行卡 (资产) | 期初余额 (权益) | 初始化资产 |

### 3.3 数据模型

```sql
CREATE TABLE fin4_transactions (
    id TEXT PRIMARY KEY,
    family_id TEXT NOT NULL,
    date TEXT NOT NULL,
    debit_account_id TEXT NOT NULL,   -- 借方账户
    credit_account_id TEXT NOT NULL,  -- 贷方账户
    amount TEXT NOT NULL,             -- Decimal 字符串
    note TEXT,
    created_at TEXT
);
```

### 3.4 一致性保证

**写入时校验**：
```python
# 每笔交易保存前必须验证借贷相等
assert debit_account and credit_account
assert amount > 0
# 借贷恒等式：所有借方余额 = 所有贷方余额
# 资产+费用 余额在借方（正），负债+收入+权益 在贷方（正）
```

**定期校验**（资产负债表恒等）：
```python
total_debit = sum(asset_balances) + sum(expense_balances)
total_credit = sum(liability_balances) + sum(income_balances) + sum(equity_balances)
assert total_debit == total_credit, "借贷不平衡，数据可能损坏"
```

### 3.5 UI 层的用户友好化

用户不需要知道「借」和「贷」，只需要选择：
- **收入**：选「收入分类」+「到账账户」
- **支出**：选「支出分类」+「付款账户」
- **转账**：选「转出账户」+「转入账户」

系统自动生成对应的借贷分录。

## 4. 验证

- ✅ 178 个测试用例中，涉及交易的测试全部通过
- ✅ 资产负债表恒等式验证始终成立
- ✅ 快捷记账表单用户无需懂会计即可使用
- ✅ 转账场景不会重复计入收支（不会虚增收支）

## 5. 教训

**为什么有效**：
1. **一致性兜底**：借贷恒等式是强校验，任何数据错误都会导致不平衡，立即暴露
2. **场景全覆盖**：收入/支出/转账/还款/初始化 全都一套模型搞定
3. **可扩展**：未来加投资、外汇、多币种都基于同一套底层模型

**可推广条件**：
- 任何需要资金追踪的系统（不限于家庭理财）
- 需要数据一致性保证的财务系统
- 用户端可以「傻瓜化」屏蔽会计概念

**踩过的坑**：
- 期初余额处理：必须通过权益账户录入，不能直接改资产余额
- 负数金额陷阱：统一用正数 + 借贷方向表达，不要用正负号
- 账户分类不能错：账户类型决定余额方向，类型错了所有报表都错
