# [ADR-202608-001] 综合开放平台 4 层架构决策

## 1. 状态
**accepted** — 2026-08-21 起生效

## 2. 背景

Rex 启动"综合开放平台"系统建设，目标是构建一个**企业级、多系统、跨业务域**的开放平台（涵盖业务、技术、运营、治理的全景）。

**核心约束**（已知）：
- 系统基座**不可改**：必须基于 OpenClaw（2026.7.2-beta.7）作为 L1
- 团队当前全职 Rex 一人，但平台需**为多人协作和团队扩张留出空间**
- 全栈视角：前端 / 后端 / 部署 / 运维 / 治理都要考虑
- 长期目标：自建知识库系统（人机协作阅读、跨系统移植）

**待决策问题**：
系统建设应该采用哪种分层架构？分层粒度如何？各层的边界如何划定？

## 3. 考虑的选项

### 选项 A: 经典 3 层架构 (表现层 / 业务层 / 数据层)
- **思路**：传统 Web 应用的分层
- **优点**：广泛认知、团队熟悉
- **缺点**：
  - 缺少"基础设施层"独立切分 → 自定义能力与 L1 边界模糊
  - 缺少"专有业务"概念 → 多项目时无法隔离
  - 不符合"企业级全景"目标（缺治理层）
- **评估**：❌ 粒度不够

### 选项 B: 业务 4 层 (接入 / 应用 / 能力 / 基础设施)
- **思路**：经典 SaaS/业务系统分层
- **优点**：
  - "接入层"明确分离 web/IM/多端
  - "能力层"对应通用业务
  - "基础设施层"清晰
- **缺点**：
  - "接入"与"应用"界限模糊（webchat 是接入还是应用？）
  - 缺少"基座"概念 → L1 OpenClaw 契约不显式
  - 专有业务只能塞在"应用"层
- **评估**：❌ 缺基座边界

### 选项 C: 中台 5 层 (前端 / BFF / 服务 / 数据 / 基础设施)
- **思路**：大型分布式系统分层
- **优点**：
  - BFF 层显式分离前后端
  - 适合多团队多技术栈
- **缺点**：
  - **粒度过细**：当前 Rex 一人全职，5 层会带来管理负担
  - BFF 在我们的系统里可能不需要（OpenClaw 已统一 channel）
  - "数据层"作为独立层会增加存储决策负担
- **评估**：⏸️ 当前规模不匹配，未来如需要可细化

### 选项 D: 自定义 4 层 (L1 系统 / L2 基础设施 / L3 通用业务 / L4 专有业务) — **采用**
- **思路**：4 层架构，按"基座 → 基础设施 → 通用业务 → 专有业务"递进
- **优点**：
  - ✅ **L1 显式承认基座边界** — OpenClaw 契约成为第一公民
  - ✅ **L2 适配层隔离基座与业务** — L1 升级不会冲击业务
  - ✅ **L3 / L4 分离通用与专有** — 多项目/多客户时复用 vs 差异化清晰
  - ✅ 横切关注点（治理）天然兼容（可挂到 L2 或独立成横切层）
  - ✅ 匹配 Rex 提出的"OpenClaw 适配 + 通用业务沉淀 + 专有业务隔离"愿景
  - ✅ 知识库系统可作为 L2 或 L3 能力，自指友好
- **缺点**：
  - 业界无现成命名（需自定义 L1~L4 词汇）
  - L3 / L4 边界需要经验沉淀
- **缓解**：术语在 `docs/architecture/00-system-architecture.md#9-术语表` 显式定义；L3 维度划分原则 + L4 继承机制文档化

### 选项 E: 不分层（扁平）
- **思路**：不分层，所有代码/配置平铺
- **优点**：启动最快
- **缺点**：
  - 多项目/多业务时混乱
  - 知识库与业务耦合
  - 不符合"企业级全景"目标
- **评估**：❌ 长期不可持续

## 4. 决策

**采用选项 D：4 层架构**：
- **L1 系统层 (System Layer)** — OpenClaw 基座（不可改）
- **L2 基础设施层 (Infrastructure Layer)** — 自定义基础设施，**必须适配 L1 契约**
- **L3 通用业务层 (Generic Business Layer)** — 跨场景通用业务能力，**按业务维度切分**
- **L4 专有业务层 (Proprietary Business Layer)** — **继承 L3** + 专有业务规则/数据/流程

**理由**：
1. **基座契约显式化** — L1 是系统最强的约束，必须在架构里"一阶公民"化
2. **适配与业务解耦** — L2 是 L1 与业务的缓冲带，OpenClaw 升级不会冲击 L3/L4
3. **复用与差异化分离** — L3/L4 的分离让"通用能力沉淀"和"专有项目差异化"独立演进
4. **治理横切兼容** — 安全/合规/可观测/成本作为横切关注点贯穿 4 层，不破坏分层
5. **匹配 Rex 目标** — 满足"OpenClaw 适配 + 通用业务 + 专有业务 + 自建知识库"的全景需求

## 5. 后果

### 5.1 正面
- **L1 升级隔离**：OpenClaw 升级时只需调整 L2，业务层（L3/L4）不感知
- **能力复用**：L3 沉淀后，L4 多个项目可共享（避免重写通用逻辑）
- **横切一致**：安全/可观测等横切关注点有明确归属（L2 + 跨层）
- **决策可回溯**：每层独立演进，契约变更走 ADR，决策链清晰
- **知识库演进友好**：自建知识库系统可作为 L2 能力，文件形式作为导出格式保留
- **多项目支持**：L4 隔离让多个专有项目互不污染

### 5.2 负面
- **初期学习成本**：自定义 L1~L4 词汇，团队需熟悉
- **L3 边界模糊**：业务维度划分原则需要时间沉淀
- **架构前期投入**：阶段一（L2 最小可用 + 架构文档）需要时间但不立即产生业务价值
- **跨层违规诱惑**：L4 直连 L2 / L3 直连 L1 都是"看起来更快"的违规，需规则约束

### 5.3 风险
| 风险 | 缓解 |
|---|---|
| L3 维度划分不当导致后续重构 | 维度划分原则文档化（第 1 个维度先试，半年后回顾）|
| L2 与 L1 契约变化不同步 | L2 适配层有版本号，L1 升级前评估 L2 适配清单 |
| 团队扩张后分层被绕过 | 架构文档 + ADR + 经验卡片 三层防线 |
| 横切关注点（治理）被忽视 | 阶段四专项处理；阶段一~三先记录预留位 |

## 7. 验证标准

**3 个月后（2026-11）回看**：

1. **架构稳定性**
   - L1 OpenClaw 升级 ≥ 1 次，L2 适配清单覆盖无遗漏？
   - L3 / L4 是否启动？边界是否清晰？

2. **能力复用**
   - L3 是否有 ≥ 1 个被 L4 复用的能力？
   - L2 组件清单是否增长到 ≥ 3 个？

3. **决策可回溯性**
   - 架构相关决策是否全部走 ADR？
   - 经验卡片是否触发过 ADR 升级？

4. **横切关注点**
   - 安全/可观测/合规至少 2 项有明确归属？
   - 知识库是否成为 L2 或 L3 能力？

5. **未触发重新评估的迹象**
   - 没有出现"绕过 L2 直连 L1"的违规？
   - 没有出现"L4 重写 L3 通用能力"的反模式？

**回看动作**：写一份评估报告（EXP-20261121-001 之类的经验卡片），如评估不通过 → 触发 ADR-005（架构调整或部分推翻）。
