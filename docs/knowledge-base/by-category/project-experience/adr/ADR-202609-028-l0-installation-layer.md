# [ADR-202609-028] L0 系统安装层

## 1. 状态
**accepted** (2026-09-08)

## 2. 背景

ADR-012 确立了「Agent 运行时作为可变因素」的范式：系统安装部署后，由使用人指定 Agent 运行时。但当前存在三个问题：

1. **0→1 无标准化流程**：新环境部署依赖人工操作（安装 OpenClaw → 配置 → 导入 skills → 初始化适配层），步骤散落在各文档中，无统一入口
2. **运行时可选 = 选型复杂度**：使用人面对 OpenClaw / Claude Code / CrewAI 等多个选项，不知道各自能力边界、生态资产、安装门槛
3. **生态资产适配无标准**：系统的 L2/L3/L4 资产（skills、配置、凭据、知识库）如何部署到不同运行时，没有统一映射

**核心问题**：如何建设一个标准化的 L0 安装层，既支持运行时选型，又能一键把系统资产部署到选定运行时，并验证契约满足度？

## 3. 考虑的选项

### 选项 A：单运行时硬绑定（不做 L0）
- **方案**：继续维持「默认 OpenClaw，直接用」，不做独立的安装层
- **优点**：零工作量，现状即可用
- **缺点**：
  - 与 ADR-012「运行时可选」矛盾
  - 新环境部署靠文档+人工，容易出错
  - 新增运行时 = 人工重新适配，无标准化流程
  - 没有契约验证，「装好了 = 能用吗」不确定

### 选项 B：安装脚本集合
- **方案**：为每个运行时写一个 install.sh，做安装+基础配置
- **优点**：实现简单，每个脚本独立
- **缺点**：
  - 脚本之间逻辑重复（环境检测、快照、回滚）
  - 无统一的选型界面，使用人需要自己看脚本
  - 无契约验证，安装完成后不知道是否满足 L1 最小契约
  - 资产部署无统一映射，每个运行时各搞一套
  - 新增运行时 = 重写一套脚本，复用率低

### 选项 C：注册表 + 流水线 + 契约验证的完整安装层
- **方案**：
  - **registry/**：每个运行时一个 YAML 描述文件（元信息 + 能力自评 + 安装方式 + 生态资产 + 适配层路径）
  - **installer/**：六步流水线（env_probe → select → install → init_adapter → verify → snapshot），统一编排
  - **contract/**：L1 十项能力契约测试套件，安装后自动验证
  - **manifest/**：系统资产清单 + 各运行时部署映射
- **优点**：
  - 与 ADR-012 范式完全对齐，运行时选型标准化
  - 新增运行时 = 加一个 registry YAML + 一个适配层 + 一条部署映射，增量极小
  - 契约验证确保「安装成功 = 契约满足」，不是装完就完事
  - 资产部署有统一映射，L2-L4 资产可跨运行时复用
  - 快照+回滚机制，安装失败可回退
- **缺点**：
  - 设计和实现工作量大（P0 需要 7 个交付物）
  - 注册表的能力自评需要人工维护，可能滞后于运行时版本
  - 契约测试的覆盖度有限，不能保证 100% 发现问题

## 4. 决策

我们选择 **选项 C — 注册表 + 流水线 + 契约验证的完整安装层**。

理由：
1. **与 ADR-012 范式对齐**：运行时是变量，L0 是变量的装配器，二者是一对概念
2. **0→1 标准化刚需**：新环境部署、跨机器迁移、运行时切换，都需要一个可靠的入口
3. **契约验证是质量底线**：安装完成 ≠ 可用，必须验证 L1 十项契约
4. **增量成本可控**：P0 只做 OpenClaw 全流程 + 其他运行时预留，后续新增运行时成本很低
5. **可演进**：L0 是编排层，不侵入运行时本身，风险可控

## 5. 后果

### 5.1 正面
- **0→1 一键部署**：新环境一条命令完成安装+配置+验证+快照
- **运行时选型有依据**：registry 提供能力自评+生态资产，使用人可对比选择
- **契约有保障**：安装完成自动跑契约测试，不满足就回滚
- **资产复用**：manifest 定义跨运行时部署映射，L2-L4 资产一次编写处处部署
- **可回滚**：每步打快照，失败回滚到上一 checkpoint
- **新增运行时成本低**：加 registry YAML + 适配层 + 部署映射，< 1 人周

### 5.2 负面
- **P0 建设投入**：7 个交付物，设计+代码+测试
- **注册表维护成本**：运行时版本升级时，能力自评需要同步更新
- **契约测试覆盖度有限**：P0 只做最小代价测试，不代表全量功能验证
- **Bash 实现的可维护性**：installer 用 Bash 写（保证 0 依赖），复杂逻辑不如 Python 好维护

### 5.3 风险
| 风险 | 概率 | 影响 | 应对 |
|---|---|---|---|
| 运行时安装命令执行失败（网络/权限/依赖） | 中 | 高 | 失败即回滚 + 输出详细错误报告 + 指引手动安装 |
| 契约测试假阴性/假阳性 | 低 | 中 | P0 用最小代价测试，P1 完善用例；测试结果仅作参考，不强行阻断 |
| 注册表能力自评与实际不符 | 中 | 中 | 契约测试兜底；能力自评字段标注版本号；运行时升级时同步更新 |
| 快照回滚不完整（漏了某些状态） | 低 | 高 | 明确快照范围（配置+凭据索引+适配层版本），不承诺全量回滚；核心配置有 .bak 兜底 |

## 6. 实现计划

### 6.1 六步流水线

| 步骤 | 脚本 | 输入 | 输出 | 失败处理 |
|---|---|---|---|---|
| 0. env_probe | `00_env_probe.sh` | 无 | `env-report.json` | 终止，输出环境报告 |
| 1. select | `01_select.sh` | env-report + registry | 选定的 runtime name | 用户取消则终止 |
| 2. install | `02_install.sh` | runtime name + registry | 已安装的运行时 | 回滚到步骤 1 |
| 3. init_adapter | `03_init_adapter.sh` | runtime + 适配层路径 | 适配层就绪 | 回滚到步骤 2 |
| 4. verify | `04_verify.sh` | runtime + contract tests | `verify-report.json` | 回滚到步骤 3（可选，用户确认） |
| 5. snapshot | `05_snapshot.sh` | 当前状态 | 快照文件 | 警告但不阻断（快照是锦上添花） |

### 6.2 三文件交付物结构

```
L0-install/
├── DESIGN.md              ← 设计文档
├── registry/              ← 运行时注册表
│   ├── openclaw.yaml      ← 完整（P0）
│   ├── claude-code.yaml   ← 预留（P0）
│   └── crewai.yaml        ← 预留（P0）
├── installer/             ← 安装引擎
│   ├── install.sh         ← 主入口
│   ├── 00_env_probe.sh    ← 环境检测
│   ├── 01_select.sh       ← 运行时选型
│   ├── 02_install.sh      ← 运行时安装
│   ├── 03_init_adapter.sh ← 适配层初始化
│   ├── 04_verify.sh       ← 契约验证
│   └── 05_snapshot.sh     ← 快照
├── contract/
│   └── test_contract.py   ← L1 十项契约测试
└── manifest/
    ├── system-assets.yaml ← 系统资产清单（运行时无关）
    └── deployment-map.yaml← 各运行时部署映射
```

## 7. 验证标准

| 维度 | 验证方式 | P0 目标 |
|---|---|---|
| **OpenClaw 全流程** | 从零开始执行 `install.sh --runtime openclaw`，六步全部通过 | ✅ 全流程跑通 |
| **契约测试** | `test_contract.py` 输出十项结果，至少 8/10 pass（考虑沙箱/通道等依赖环境的项） | ≥ 8/10 pass |
| **新增运行时成本** | 模拟新增一个运行时需要改动的文件数和代码量 | ≤ 3 个文件（registry + adapter + deployment-map） |
| **失败回滚** | 故意在第 3 步制造失败，验证回滚到第 2 步状态 | 回滚后配置与第 2 步完成时一致 |
| **凭据安全** | 全流程 grep 敏感字段，确认无明文输出 | 0 处明文泄露 |
