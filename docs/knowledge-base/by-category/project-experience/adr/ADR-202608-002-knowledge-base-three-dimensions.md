# [ADR-202608-002] 知识库 3 维矩阵组织决策

## 1. 状态
**accepted** — 2026-08-21 起生效

## 2. 背景

Rex 启动"综合开放平台"系统建设，明确：
- **核心目标**：人机协作阅读 + 跨系统移植
- **承载形式**：当前 Markdown + 元数据；自建系统作为演进目标
- **沉淀对象**：业界最佳实践 + 理论知识 + 项目经验（正确/错误）

**待决策问题**：
知识库内容**如何组织和检索**？单一维度（如按主题）vs 多维度（按多种属性切分）？

## 3. 考虑的选项

### 选项 A: 单维按主题分类
- **思路**：所有文档按主题/标签分类（"架构"、"安全"、"性能"...）
- **优点**：
  - 简单，符合传统 wiki/blog 习惯
  - 检索直接
- **缺点**：
  - **缺少层级上下文**：跨层架构知识无法定位（如"基础设施层的演进"算哪类？）
  - **缺少阶段上下文**："设计阶段该看什么" 不清晰
  - **缺少类型区分**：业界实践和项目经验混在一起，难以分别查找
  - **知识膨胀后混乱**：标签体系难以维护
- **评估**：❌ 维度单一，不够

### 选项 B: 双维（层级 × 阶段）
- **思路**：把"层级 × 阶段"作为二维矩阵，类别不显式
- **优点**：
  - 层级和阶段两维度强相关（每层都有设计/开发/管理）
  - 矩阵直观
- **缺点**：
  - **类别混在每格内**：业界实践、理论知识、项目经验无法独立检索
  - "项目经验（踩坑）"这种高价值知识被淹没在通用知识里
  - 经验沉淀（EXP）和 ADR 没有专门分类
- **评估**：⏸️ 比 A 好但不够

### 选项 C: 三维（层级 × 阶段 × 类别）— **采用**
- **思路**：3 维矩阵，每条知识定位到 3 个轴
  - **层级 (Layer)**: L1 / L2 / L3 / L4
  - **阶段 (Stage)**: Design / Develop / Manage
  - **类别 (Category)**: Industry Practice / Theoretical Knowledge / Project Experience
- **优点**：
  - ✅ **3 维独立可检索**：每维可独立成为"入口"
  - ✅ **经验沉淀有专门位置**：project-experience 子目录有 correct/incorrect/adr
  - ✅ **避免"挂错地方"**：一条知识有清晰的归属
  - ✅ **人机共读友好**：人类可按任意一维找，AI agent 可按 frontmatter 精确查询
  - ✅ **目录结构支持 3 种入口**：by-layer / by-stage / by-category 三套并列
- **缺点**：
  - 初次使用需要决定"放在哪个目录" — 但每条知识可被引用 3 个目录
  - 3 维比 1 维复杂
- **缓解**：
  - **每条知识只放一次**（在 by-category），其他维用 frontmatter 元数据 + INDEX 引用
  - frontmatter 强制 3 维元数据，避免模糊

### 选项 D: 标签系统（无固定维度）
- **思路**：完全用标签（tag）组织，无固定结构
- **优点**：
  - 灵活
- **缺点**：
  - **标签难以标准化**：团队扩张后标签爆炸
  - 检索靠标签搜索，不如目录直观
  - 知识容易"孤儿化"（没有合适标签就放不下）
- **评估**：❌ 灵活但不可控

### 选项 E: 知识图谱
- **思路**：实体 + 关系（如 Datomic 风格）
- **优点**：
  - 表达力最强
  - 跨维度关系显式
- **缺点**：
  - **前期成本极高**：自建图谱系统是 L2/L3 大工程
  - 当前阶段（基座搭建）投入回报不匹配
  - 工具链不成熟（自建成本 > 价值）
- **评估**：⏸️ 长期目标可能用，短期不启动

## 4. 决策

**采用选项 C：3 维矩阵（层级 × 阶段 × 类别）**：

```
知识 = (layer, stage, category, content)
```

**具体规则**：
1. **每条知识必须 3 维元数据完整**（frontmatter 强制）
2. **每条知识物理上只放一次**（在 by-category 或按主类目）
3. **其他维度通过 INDEX 引用**或元数据过滤访问
4. **类别细目**：
   - `industry-practices` — 业界最佳实践（含外部参考）
   - `theoretical-knowledge` — 理论知识
   - `project-experience` — 项目经验（细分为 correct / incorrect / adr）

**理由**：
1. **3 维独立可检索** — 任意维度可作为入口
2. **类别细分** — 经验沉淀（正确/错误）和 ADR 有专门位置
3. **人机共读** — frontmatter 结构化（AI 友好）+ 文档正文叙述化（人类友好）
4. **跨系统可移植** — 3 维矩阵是**普遍适用**的分类法，不依赖具体工具
5. **演进到自建系统** — 3 维自然映射到关系数据库/对象存储 schema

## 5. 后果

### 5.1 正面
- **检索多样**：按层级（"L2 基础设施相关的所有知识"）/ 按阶段（"设计阶段该看什么"）/ 按类别（"所有项目踩坑记录"）
- **AI 友好**：frontmatter 元数据使 agent 可精确查询（如 "L3 设计阶段的 industry-practices"）
- **人类友好**：目录结构直观，新人可按任一维度浏览
- **知识不会孤儿化**：3 维强制要求位置
- **可移植**：3 维矩阵是通用分类法，迁到自建系统时 schema 直接映射

### 5.2 负面
- **元数据负担**：每条知识需要填 3 维（可模板化缓解）
- **目录选择困惑**：首次添加时需决定"放哪个物理目录"
- **3 维交叉检索需依赖 INDEX**：单一目录不支持

### 5.3 风险
| 风险 | 缓解 |
|---|---|
| 元数据不一致（某条知识 layer 标错） | 定期审查；CI 检查 frontmatter 完整性 |
| 维度太抽象，新人难理解 | README 三维矩阵 ASCII 图 + 术语表 |
| 类别膨胀（类别越来越多） | 类别控制在 3 个核心（业界/理论/经验），子目录细分 |
| 物理目录重复（一条知识在多个目录） | **硬性规则：物理只放一次**，其他靠引用 |

## 7. 验证标准

**1 个月后（2026-09-21）回看**：

1. **结构使用**
   - 是否每条新知识都有完整 3 维元数据？
   - by-category 物理目录是否成为主入口？by-layer / by-stage 引用是否有效？

2. **检索效率**
   - 找特定知识平均需要几步？目标 ≤ 3 步
   - AI agent 是否能通过 frontmatter 精确检索？

3. **沉淀覆盖**
   - 3 个类别（业界/理论/经验）是否都有 ≥ 1 条？
   - 经验类是否正确分为 correct / incorrect / adr？

4. **演进兼容性**
   - 3 维模型是否可平滑映射到自建系统的 schema？

**回看动作**：写一份评估卡片（EXP-20260921-001 之类）。如不通过 → 触发 ADR-005（模型调整或部分推翻）。
