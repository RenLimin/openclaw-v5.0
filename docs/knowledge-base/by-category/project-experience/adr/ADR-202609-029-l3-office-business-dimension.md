# [ADR-202609-029] L3 Office 业务维度设计

## 1. 状态
**proposed** — 2026-09-08 提出，待评审

## 2. 背景

### 上下文
- L2 Office Engine v2 (M1) 已完成统一 SDK 封装，提供 create/read/update/parse/convert 纯技术能力
- 现有 L4 业务组件（合同审批/交付月报/Bangcle PPT）已经开始使用文档生成能力，但缺乏**业务层面的通用资产复用**
- 当前每个业务场景各自定义文档规范、模板和角色，重复工作多，复用率低

### 问题
- ❌ 文档规范无统一标准：每个场景自行定义变量、结构、样式规范，一致性差
- ❌ 模板资产零散：没有通用模板索引，复用需要复制粘贴
- ❌ 角色定义缺失：业务场景中没有明确的文档工程师/分析师角色
- ❌ 业务知识沉淀缺失：没有对 Office 文档生产流程做标准化沉淀

### 目标
为所有 Office 文档生产场景提供**通用业务层能力底座**，让 L4 专有业务直接复用，避免重复建设。

---

## 3. 考虑的选项

### 选项 A: 不建 L3 维度，保持现状
- **优点**：零额外建设量
- **缺点**：业务知识、模板、角色无法复用，每个场景重复建设，一致性差
- **评估**：❌ 不符合架构复用原则

### 选项 B: L3 建通用业务维度，提供知识/模板/角色 — **采用**
- **优点**：
  - 统一规范，降低学习成本
  - 模板资产可复用，L4 只需要添加专有扩展
  - 角色标准化，调用方便
  - 严格符合架构分层：L2 技术底座 → L3 通用业务 → L4 专有业务
- **缺点**：
  - 需要初始建设量
  - 后续需要维护规范一致性
- **评估**：✅ 采用，符合整体架构设计

### 选项 C: L2 直接包含业务知识，L3 跳过
- **优点**：少建一层
- **缺点**：违反分层定位，L2 应该是纯技术，不包含业务知识
- **评估**：❌ 分层错误

---

## 4. 决策

**采用选项 B**：在 L3 新增 **Office 业务维度**，存放通用业务知识、通用模板资产、标准角色定义。

### 4.1 组件定位
| 维度 | 值 |
|---|---|
| 层级 | L3 通用业务层 |
| 组件名称 | Office 业务维度 |
| 依赖 | L2 Office Engine (011 v2) |
| 定位 | 为所有 Office 文档生产场景提供通用业务能力：文档规范、通用模板、标准角色 |
| 不包含 | 专有业务逻辑、专有模板、实现代码（这些放 L4） |

### 4.2 目录结构（对齐 L3 通用约定）
```

│   ├── variable-system.md  # 变量命名/类型体系
│   └── structure-guide.md # 常见文档结构指南
├── templates/             # 通用模板资产（Markdown 格式，供渲染）
│   ├── index.json         # 模板索引
│   ├── contract/           # 合同通用模板
│   │   ├── sales-contract.md
│   │   └── service-contract.md
│   ├── report/            # 通用报告模板
│   │   ├── weekly-report.md
│   │   ├── monthly-report.md
│   │   ├── quarterly-report.md
│   │   └── annual-report.md
│   ├── proposal/          # 方案通用模板
│   │   ├── project-proposal.md
│   │   └── technical-proposal.md
│   └── presentation/      # 汇报演示通用模板

```

### 4.3 核心设计决策

#### 决策 1：模板分通用/专有，通用放 L3，专有放 L4

**通用模板定义**：不包含业务专有逻辑，可被多个 L4 业务场景直接复用的模板。

| 模板类型 | 位置 | 示例 |
|---|---|---|
| 通用 | L3 | 销售合同框架、周报框架、项目方案框架 |
| 专有 | L4 | 某公司销售合同、某业务专属月报 |

**L4 复用方式**：继承 L3 通用模板，通过变量覆盖和局部修改实现专有化。**不复制粘贴**，保持对 L3 模板更新的继承。

#### 决策 2：模板存储格式为 Markdown + frontmatter

**理由**：
- 和现有知识库格式一致，工具链兼容
- 人机可读，版本控制友好
- frontmatter 存储元数据（title/description/author/created/updated/tags/variables）
- L2 Office Engine 可读取渲染为最终 Office 文件

#### 决策 3：角色定义遵循 L3 通用角色规范（4 文件模型）

每个角色包含三个文件：IDENTITY.md（简介）、SOUL.md（人设/边界）、AGENTS.md（能力/流程）。

**本期建设两个核心角色**：
1. **文档工程师**：负责文档生成、格式规范、模板渲染、格式转换
2. **业务分析师**：负责数据整理、内容分析、报告生成、变量填充

#### 决策 4：变量体系遵循统一命名规范

- 变量名：蛇形命名法 `project_name`，语义清晰
- 变量类型：string / number / date / list / table / markdown
- 变量作用域：全局 / 段落 / 表格 / 模板
- 模板中通过 `{{ variable_name }}` 占位，渲染时替换

### 4.4 层级归属验证（对照 L3 标准）

| 标准 | L3 Office 维度符合情况 | 判定 |
|---|---|---|
| L3 = "跨场景通用业务能力" | 文档规范、通用模板、标准角色，都是跨多个业务场景的通用能力 | ✅ 符合 |
| 不包含专有业务逻辑 | 只放通用框架，专有内容放 L4 | ✅ 符合 |
| L4 可继承复用 | L4 通过继承扩展，不破坏 L3 结构 | ✅ 符合 |
| 严格依赖方向：L3 → L2 | L3 Office 只依赖 L2 Office Engine，不反向依赖 | ✅ 符合 |

## 5. 后果

### 5.1 正面
- 所有 Office 文档场景可复用通用能力，减少重复建设
- 统一规范，提升一致性和可维护性
- L4 只需要做专有扩展，开发速度大幅提升
- 模板资产可沉淀，持续优化
- 严格符合分层架构契约

### 5.2 负面
- 初始建设需要一定工作量
- 模板需要持续维护更新，保持和 L2 能力同步

### 5.3 风险
| 风险 | 影响 | 缓解 |
|---|---|---|
| 通用模板定义过宽 | 模板太多影响检索 | 严格筛选通用模板，只放真正跨场景的 |
| L4 不遵循继承规范，直接复制 | 破坏分层，重复维护 | 文档明确规范，验收时检查 |
| 变量体系与 L4 冲突 | 复用成本高 | 文档明确变量命名规范，L4 只新增专有变量，不修改通用命名 |
