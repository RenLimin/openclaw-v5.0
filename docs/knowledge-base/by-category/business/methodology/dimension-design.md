# 业务维度设计方法

> 从业务需求到可落地的 L3 维度定义 —— 六步标准化流程。

## 1. 目标与定位

维度是 L3 业务知识库的**一级组织单元**。维度设计决定：

- **知识如何归类**：每个维度有独立的 `knowledge/` 子库
- **角色如何归属**：每个维度有 `roles/` 目录（SOUL + AGENTS + IDENTITY）
- **L4 如何继承**：L4 专有业务只叠加差异，不重建通用能力

维度设计的目标是回答架构文档的核心问题："这个业务场景需要哪些角色、哪些知识、哪些交付物"。

## 2. 六步设计流程

| 步骤 | 输入 | 产出 | 关键问题 |
|------|------|------|----------|
| 1. 需求识别 | 业务场景描述 | 维度清单 | "这个业务场景需要哪些角色？" |
| 2. 知识调研 | 业界标准/最佳实践 | 知识来源清单 | "这个领域有哪些权威知识体系？" |
| 3. 维度定义 | 调研结果 | 维度边界定义 | "这个维度包含什么、不包含什么？" |
| 4. 角色规划 | 维度边界 | 角色清单 | "这个维度需要哪些角色？" |
| 5. 依赖分析 | 角色清单 | 维度间依赖图 | "这个维度与其他维度如何协作？" |
| 6. 优先级排序 | 所有上述 | 建设顺序 | "先建哪个维度？" |

## 3. 维度定义原则

| 原则 | 说明 | 违背的后果 |
|------|------|-----------|
| **边界清晰** | 维度之间不重叠、不含糊 | 知识归属混乱，检索失效 |
| **角色充足** | 每个维度 ≥ 3 个角色 | 无法覆盖核心场景 |
| **松耦合** | 维度间通过共享上下文协作，不直接依赖 | 一改全改，无法独立演进 |
| **知识驱动** | 先有知识体系，再定角色 | 角色没有知识底座，空壳 |
| **可继承** | 能力可被 L4 直接复用 | L4 重复建设，违背分层契约 |

## 4. 知识调研方法

### 4.1 权威来源类型

| 类型 | 示例 | 验证方式 |
|------|------|----------|
| 国际标准 | PMBOK 8th / ITIL 4 / Scrum Guide | 官方机构发布（PMI/Axelos/scrumguides.org） |
| 监管框架 | 等保 2.0 / GDPR / 民法典 | 官方发布渠道 |
| 专业认证 | CFP / CFA | 认证机构官网 |
| 业界实践 | 跨境运营（Jungle Scout / 连连支付） | 头部平台 + 学术论文（交大安泰等） |

### 4.2 调研注意

- 每个知识体系**标注版本**（如 "PMBOK 第 8 版, 2026"），便于后续更新
- 优先一手来源（标准原文/官方文档），二手来源交叉验证
- 记录调研来源清单，沉淀进维度 `README.md`，可追溯

## 5. 维度结构模板

每个维度目录遵循统一结构（以 `project-management` 为例）：

```
<dimension>/
├── README.md            # 维度索引（frontmatter + 知识/角色/模板索引）
├── knowledge/           # 业务知识（按子领域分子目录）
│   └── <sub-area>/      # 如 pmbok-8th/ agile/ risk-management/
├── roles/               # 角色定义
│   └── <role>/
│       ├── SOUL.md      # 身份人设
│       ├── AGENTS.md    # 业务能力
│       └── IDENTITY.md  # 一句话简介
└── templates/           # 交付物模板（可选）
```

## 7. 常见错误

| 错误 | 表现 | 规避 |
|------|------|------|
| 维度过粗 | 一个维度装下所有业务 | 拆到"一个维度 = 一个业务领域 + 一组角色"粒度 |
| 维度过细 | 每个小功能一个维度 | 合并为知识子目录，不升维度 |
| 知识编造 | 无权威来源硬写 | 遵守 [knowledge-authoring.md](./knowledge-authoring.md) 的权威来源原则 |
| 角色空转 | 定义了角色但无知识/无模板支撑 | 按六步流程先调研后规划 |
