# 需求分析

## 需求层次

### 金字塔模型

```
        △ 业务需求（Business Requirements）
       ╱ ╲   "为什么做"
      ╱   ╲
     ╱ 用户需求 ╲  (User Requirements)
    ╱  "谁需要"  ╲
   ╱───────────────╲
  ╱  功能需求        ╲  (Functional Requirements)
 ╱  "系统做什么"      ╲
╱─────────────────────╲
     非功能需求           (Non-Functional Requirements)
     "系统做到什么程度"
```

### 各层说明

| 层次 | 来源 | 描述方式 | 示例 |
|------|------|----------|------|
| 业务需求 | 利益相关者 | 业务目标 | "提升订单转化率 20%" |
| 用户需求 | 用户研究 | 用户故事/场景 | "作为买家，我想筛选商品" |
| 功能需求 | 分析 | 功能规格 | "支持按价格/品牌/评分筛选" |
| 非功能需求 | 架构/运维 | 质量属性 | "筛选响应 < 200ms" |

## 需求获取技术

| 技术 | 适用 | 优点 | 缺点 |
|------|------|------|------|
| 访谈 | 深度理解 | 发现隐性需求 | 耗时、样本小 |
| 问卷 | 广泛收集 | 可量化 | 缺乏深度 |
| 观察 | 工作流程 | 发现未表述需求 | 霍桑效应 |
| 文档分析 | 现有系统 | 快速了解 | 可能过时 |
| 原型 | 交互需求 | 快速验证 | 可能限制思维 |
| 头脑风暴 | 创新需求 | 激发创意 | 需要引导 |

## 用户故事（User Story）

### 标准格式

```
作为 [角色]，
我想要 [功能]，
以便 [价值/原因]。
```

### 3C 模型

| C | 含义 | 说明 |
|---|------|------|
| Card | 卡片 | 简短描述，不承载全部细节 |
| Conversation | 对话 | 团队讨论，澄清细节 |
| Confirmation | 确认 | 验收标准（AC） |

### INVEST 原则

| 字母 | 含义 | 说明 |
|------|------|------|
| I | Independent | 故事间尽量独立 |
| N | Negotiable | 细节可协商 |
| V | Valuable | 对用户/业务有价值 |
| E | Estimable | 团队可估算 |
| S | Small | 一个迭代内可完成 |
| T | Testable | 可定义验收标准 |

### 验收标准（Acceptance Criteria）

**Given-When-Then 格式**：

```
Given [前置条件]
When [操作/事件]
Then [预期结果]
```

**示例**：
```
Given 用户已登录且购物车有商品
When 用户点击"结算"
Then 跳转到结算页，显示商品列表和总价
And 显示可用支付方式
```

## 非功能需求（NFR）

### 分类

| 类别 | 关注点 | 度量 |
|------|--------|------|
| 性能 | 响应时间、吞吐量 | ms, TPS |
| 可用性 | 系统正常运行时间 | 99.9% (8.76h/年停机) |
| 可扩展性 | 负载增长应对 | 水平/垂直扩展 |
| 安全性 | 数据保护 | 加密、认证、审计 |
| 可靠性 | 容错能力 | MTBF, MTTR |
| 可维护性 | 代码质量 | 圈复杂度、测试覆盖率 |
| 易用性 | 用户体验 | SUS 评分 |
| 合规性 | 法规满足 | GDPR, 等保 |

### SLA/SLO/SLI

| 术语 | 含义 | 示例 |
|------|------|------|
| SLI (指标) | 衡量指标 | 请求延迟 P99 |
| SLO (目标) | 目标值 | P99 < 200ms |
| SLA (协议) | 对外承诺 | 月度可用性 ≥ 99.9% |

## 需求管理

### 需求跟踪矩阵（RTM）

| ID | 需求描述 | 来源 | 优先级 | 状态 | 验收标准 | 测试用例 |
|----|----------|------|--------|------|----------|----------|
| REQ-001 | 用户登录 | 用户访谈 | Must | 已批准 | AC1-AC3 | TC-001 |

### 变更控制

1. **提交变更请求**：描述变更内容和理由
2. **影响分析**：评估对范围、进度、成本的影响
3. **审批**：CCB（变更控制委员会）决策
4. **实施**：更新需求文档和跟踪矩阵
5. **验证**：确认变更正确实施

## 需求规格说明书（SRS）

### 标准结构（IEEE 830）

1. 引言（目的、范围、定义）
2. 总体描述（产品视角、功能、用户特征）
3. 具体需求（功能需求、非功能需求）
4. 接口需求（用户接口、硬件接口、软件接口）
5. 数据需求
6. 附录（术语表、参考资料）

## 常见误区

1. **混淆需求和方案**："需要一个弹窗"是方案，"需要提醒用户"是需求
2. **忽视非功能需求**：只关注功能，性能和安全性后期补课
3. **需求镀金**：过度设计，超出实际需要
4. **一次性需求**：需求是活的，需要持续管理
5. **忽视利益相关者冲突**：不同角色的需求可能矛盾
