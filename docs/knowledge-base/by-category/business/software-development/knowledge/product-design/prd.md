# 产品需求文档（PRD）

## 定义

PRD（Product Requirements Document）是描述产品"做什么"和"为什么做"的正式文档，是产品、设计、研发、测试的共同参考源。

## 文档结构

### 标准模板

```markdown
# [产品/功能名称] PRD

## 1. 概述
- **产品/功能名称**：
- **作者**：
- **日期**：
- **状态**：草稿 / 评审中 / 已批准 / 已归档
- **优先级**：P0 / P1 / P2
- **迭代/版本**：

## 2. 背景与目标
- **业务背景**：为什么要做？
- **用户问题**：解决什么问题？
- **业务目标**：期望什么结果？（可度量）
- **成功指标**：如何衡量成功？

## 3. 目标用户
- **用户画像**：参考 persona
- **使用场景**：何时/何地/如何使用
- **核心需求**：用户最需要什么

## 4. 功能需求
### 4.1 [功能模块 A]
- 用户故事
- 验收标准（Given-When-Then）
- 交互说明（或链接到设计稿）
- 边界条件

### 4.2 [功能模块 B]
...

## 5. 非功能需求
- 性能：响应时间、并发量
- 安全：认证、授权、数据保护
- 兼容性：浏览器/设备/系统版本
- 可用性：可访问性标准

## 6. 信息架构
- 页面流程图
- 导航结构
- 数据流

## 7. 接口需求
- 内部接口：前后端 API
- 外部接口：第三方服务
- 数据格式：JSON schema

## 8. 发布计划
- MVP 范围：哪些功能先上
- 灰度策略：如何分批发布
- 回滚方案：出问题怎么办

## 9. 风险与依赖
- 技术风险
- 依赖项（其他团队/系统）
- 合规风险

## 10. 附录
- 术语表
- 参考资料
- 变更历史
```

## 写作原则

### 清晰性原则

| 原则 | 正确示例 | 错误示例 |
|------|----------|----------|
| 具体 | "列表按创建时间倒序" | "合理排序" |
| 可验证 | "响应时间 < 200ms" | "快速响应" |
| 无歧义 | "支持 JPG/PNG，单张 ≤ 10MB" | "支持常见图片格式" |
| 用户视角 | "作为用户，我想导出 CSV" | "系统需要导出功能" |

### 应该做的

- 基于用户故事，从用户视角描述
- 包含明确的验收标准
- 标注优先级和迭代归属
- 链接到设计稿、原型、技术方案
- 明确 MVP 范围和后续迭代计划

### 不应该做的

- 不描述"怎么做"（那是技术方案的范畴）
- 不复制粘贴用户原话（需要分析提炼）
- 不包含精确的 UI 尺寸（交给设计）
- 不写 SQL 或代码逻辑（交给研发）
- 不遗漏异常流程（错误提示、空状态、边界条件）

## 评审流程

### 评审检查清单

- [ ] 业务目标是否清晰可度量？
- [ ] 用户故事是否覆盖主要场景？
- [ ] 验收标准是否完整且可测试？
- [ ] 非功能需求是否明确？
- [ ] 边界条件和异常流程是否覆盖？
- [ ] 是否与现有功能冲突？
- [ ] 数据安全和合规是否考虑？
- [ ] 依赖项是否识别？
- [ ] MVP 范围是否合理？

### 评审参与者

| 角色 | 关注点 |
|------|--------|
| 产品经理 | 业务逻辑、优先级 |
| UX/UI 设计 | 交互可行性、一致性 |
| 研发负责人 | 技术可行性、工作量估算 |
| 测试负责人 | 可测试性、验收标准 |
| 项目经理 | 排期、依赖、风险 |

## PRD vs 技术方案

| 维度 | PRD | 技术方案（Tech Spec） |
|------|-----|----------------------|
| 回答 | "做什么" + "为什么" | "怎么做" |
| 读者 | 全团队 | 研发团队 |
| 内容 | 用户故事、验收标准、优先级 | 架构设计、数据库 schema、API 设计 |
| 作者 | 产品经理 | 研发负责人/架构师 |
| 时机 | 设计前 | 开发前 |

## 轻量化替代

对于小团队/敏捷项目，PRD 可以轻量化：

| 替代形式 | 适用 |
|----------|------|
| RFC (Request for Comments) | 技术驱动的产品决策 |
| Design Doc | 设计+需求合并 |
| Linear/Jira tickets | 小功能，ticket 即需求 |
| Loom 视频 + 截图 | 快速沟通，非正式 |

## 常见误区

1. **PRD 越长越好**：信息密度 > 篇幅，10 页讲清楚比 50 页好
2. **PRD 写完即丢**：PRD 应持续更新，反映最新决策
3. **PRD = 设计稿**：PRD 关注"做什么"，设计稿关注"长什么样"
4. **忽视异常流程**：80% 的 bug 来自未考虑的边界条件
5. **没有成功指标**：无法衡量成功 = 不知道做得好不好
