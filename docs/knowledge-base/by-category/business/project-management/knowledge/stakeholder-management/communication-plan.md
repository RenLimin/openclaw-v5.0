# 项目沟通管理计划

> 沟通计划明确"谁在什么时候通过什么方式接收什么信息"，是干系人管理落地的执行机制。

## 概述

沟通失败是项目失败的首要原因之一。沟通计划确保**正确的信息在正确的时间以正确的方式到达正确的人**，并减少信息过载和遗漏。

## 沟通需求分析

### 信息需求来源

| 来源 | 信息类型 |
|------|----------|
| 干系人登记册 | 各干系人的信息需求和偏好 |
| 组织架构 | 汇报线、决策链 |
| 项目文档 | 计划、风险、变更信息 |
| 法律法规 | 合规披露要求 |

### 5W1H 沟通模型

| 要素 | 问题 | 规划内容 |
|------|------|----------|
| Who（谁） | 谁需要信息？谁提供？ | 干系人 + 责任人 |
| What（什么） | 需要什么信息？ | 内容、格式、详细度 |
| When（何时） | 何时需要？ | 频率、时点 |
| Where（何地） | 在哪里获取？ | 存储位置、系统 |
| Why（为什么） | 为什么需要？ | 决策/知情/执行 |
| How（如何） | 如何传递？ | 渠道、方式、格式 |

## 沟通矩阵

| 沟通项 | 目标干系人 | 频率 | 方式 | 内容 | 责任人 |
|--------|------------|------|------|------|--------|
| 项目周报 | 发起人/管理层 | 每周一 | 邮件 | 进度/风险/决策点 | PM |
| 每日站会 | 开发团队 | 每日 | 面对面 | 进度/障碍 | SM |
| Sprint 评审 | 客户/干系人 | 每 Sprint | 演示会 | 增量展示/反馈 | PO |
| 风险月报 | 发起人 | 每月 | 会议 | 风险状态/应对 | PM |
| 变更公告 | 受影响干系人 | 即时 | 邮件/会议 | 变更内容/影响 | PM |

## 信息分发

### 渠道选择

| 渠道 | 优点 | 适用 |
|------|------|------|
| 面对面会议 | 高互动、即时反馈 | 决策、冲突解决 |
| 邮件 | 可追溯、异步 | 正式通知、周报 |
| 即时消息 | 快速、低成本 | 日常协作 |
| 文档/知识库 | 沉淀、可检索 | 计划、规范 |
| 演示 | 直观 | 评审、验收 |

### 信息分发原则
- **按需分发**：给决策者完整信息，给执行者必要信息
- **及时透明**：坏消息第一时间同步
- **单向 vs 双向**：通知用单向，决策用双向

## 沟通效果评估

| 指标 | 评估方式 |
|------|----------|
| 信息到达率 | 是否确认接收（阅读回执/签到） |
| 理解度 | 抽查反馈、提问答疑 |
| 满意度 | 干系人沟通满意度调查 |
| 决策时效 | 决策等待时间是否缩短 |

## 常见误区

| 误区 | 纠正 |
|------|------|
| 越多沟通越好 | 信息过载同样有害，按需分发 |
| 只报喜不报忧 | 掩盖问题会放大风险 |
| 沟通 = 发邮件 | 关键沟通需确认理解和反馈 |
| 计划一次到位 | 沟通计划需随干系人变化调整 |

## 注意事项

- 沟通计划与[参与计划](./engagement-plan.md)配套：参与是"为何互动"，沟通是"如何互动"
- 远程/分布式团队需额外规划跨时区沟通
- 沟通记录归档到项目文档库，支持审计
- 与 [status-report.md](../../templates/status-report.md) 模板配套

## 适用场景

- ✅ 项目启动时制定沟通机制
- ✅ 干系人变化后调整沟通方式
- ✅ 分布式/多团队项目的沟通协调
- ❌ 极小项目（沟通简单时直接列清单即可）
