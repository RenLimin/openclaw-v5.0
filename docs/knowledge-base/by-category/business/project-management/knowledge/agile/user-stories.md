# 用户故事编写指南

> 用户故事是从用户视角描述功能需求的简短描述，是敏捷需求管理的基本单元。

## 概述

用户故事不是"需求文档"，而是**关于对话的承诺**——它足够简短以支持讨论，而不是替代讨论。故事在迭代中持续细化（Refinement），直到可交付。

## 故事格式

### 标准模板

```markdown
作为 <角色>，我想要 <功能>，以便 <价值>
```

**示例**：
- 作为项目经理，我想要自动生成状态报告，以便节省每周汇报时间
- 作为客户，我想要在线查看交付进度，以便减少沟通成本

### 关键要素

| 要素 | 说明 | 示例 |
|------|------|------|
| 角色 | 谁需要这个功能 | 项目经理 |
| 功能 | 做什么 | 自动生成状态报告 |
| 价值 | 为什么需要 | 节省每周汇报时间 |

## INVEST 标准

好的用户故事满足 6 条标准：

| 字母 | 标准 | 检查问题 |
|------|------|----------|
| I | Independent（独立） | 能否独立交付？ |
| N | Negotiable（可协商） | 细节能否讨论？ |
| V | Valuable（有价值） | 对用户有明确价值？ |
| E | Estimable（可估算） | 团队能估算工作量？ |
| S | Small（足够小） | 能在一次 Sprint 完成？ |
| T | Testable（可测试） | 有明确验收标准？ |

## 验收标准（Gherkin 格式）

```gherkin
场景：<场景名称>
  给定 <前置条件>
  当 <触发动作>
  那么 <预期结果>
```

**示例**：
```gherkin
场景：项目经理生成周报
  给定 项目有已完成的 10 个任务
  当 项目经理点击"生成周报"
  那么 系统生成包含进度统计的周报
  且 周报可导出为 PDF
```

## 故事拆分

### 拆分时机
- 故事过大（> 1 个 Sprint 工作量）时
- 需求逐渐明确时（渐进明细）

### 拆分方式

| 方式 | 说明 | 示例 |
|------|------|------|
| 按操作步骤 | 按用户操作流程拆分 | 登录 → 查看 → 导出 |
| 按业务规则 | 按规则复杂度拆分 | 基础校验 → 复杂规则 |
| 按数据范围 | 按数据规模拆分 | 单条 → 批量 |
| 按用户角色 | 按不同用户场景拆分 | 管理员 → 普通用户 |

## 优先级排序

### 常用方法
- **MoSCoW**：Must / Should / Could / Won't
- **价值-成本矩阵**：高价值低成本优先
- **Kano 模型**：基本型/期望型/兴奋型

### Product Backlog 排序原则
- 高价值靠前（由 PO 决定）
- 高不确定性的前置（先验证风险）
- 依赖项排在依赖者之前

## 常见误区

| 误区 | 纠正 |
|------|------|
| 故事 = 任务清单 | 故事是"为什么"，任务是"怎么做" |
| 故事写太细 | 保留协商空间，细节在 Sprint 中细化 |
| 没有验收标准 | 无法测试的故事不是好故事 |
| 故事与用户脱节 | 必须从真实用户视角出发 |

## 注意事项

- 团队共同编写和估算（Planning Poker）
- 故事点（Story Points）用于估算相对工作量
- 与技术任务（Spike/重构）分开管理
- 故事完成后更新 [scrum-guide.md](./scrum-guide.md) 中的 Sprint Backlog 管理实践

## 适用场景

- ✅ 敏捷项目 Backlog 需求管理
- ✅ 需求需渐进明细的迭代开发
- ✅ 需要团队与干系人频繁对话确认需求
- ❌ 需求极其稳定且需正式文档存档的合规项目
