# Status Page 运维与客户沟通 SOP

## 适用场景

- SaaS 产品公共状态页（Status Page）的运营与维护
- 故障期间的客户沟通策略
- 计划内维护的通知流程
- 事后报告的发布规范

---

## 核心原则

1. **透明诚实** — 有问题就说有问题，不遮不掩，客户比你想的宽容
2. **及时更新** — 哪怕还不知道原因，也要说"我们在查"，别静默
3. **一个声音对外** — Status Page 是唯一真相来源，其他渠道引用它
4. **客户视角** — 说客户听得懂的话，别说技术黑话
5. **事后有交代** — 每次故障都要有完整的事后报告，不能不了了之

---

## 什么是 Status Page

Status Page 是公开的服务状态页面，客户可以实时看到：
- 当前服务是否正常
- 各模块的运行状态
- 历史故障记录
- 计划内维护安排
- 故障事后报告

**为什么需要 Status Page？**
- 减少客服工单（客户自己去看，不用来问）
- 建立信任（透明 = 可靠）
- 故障沟通的标准渠道
- SLA 透明度的体现

## Status Page 设计

### 状态展示

**状态等级：**

| 状态 | 颜色 | 说明 |
|---|---|---|
| 🟢 运行正常 | 绿色 | 所有系统正常 |
| 🟡 性能下降 | 黄色 | 性能下降，但功能可用 |
| 🔴 部分中断 | 橙色 | 部分功能不可用 |
| ⚫ 重大中断 | 红色 | 核心服务完全不可用 |
| 🔵 维护中 | 蓝色 | 计划内维护 |

### 模块划分

按功能模块展示状态，而不是只有一个"总状态"：

| 模块 | 说明 |
|---|---|
| 核心 API | 主要接口服务 |
| Web 应用 | 前端页面 |
| 管理后台 | 管理员后台 |
| 数据导出 | 导出功能 |
| 邮件服务 | 邮件通知 |
| 第三方集成 | API / Webhook |
| 搜索 | 搜索功能 |

**每个模块有独立的状态，总状态取最差的那个。**

### 历史记录

- 展示最近 90 天的事件时间线
- 每个事件有：时间、影响、状态更新记录
- 可筛选按模块 / 按严重程度
- 月度 / 年度可用性统计

## 故障期间的状态更新

### 更新频率

| 故障级别 | 首次更新 | 持续更新频率 | 恢复后 |
|---|---|---|---|
| P0 重大故障 | 5 分钟内 | 每 15-30 分钟 | 1 小时内总结 |
| P1 严重故障 | 15 分钟内 | 每 30-60 分钟 | 2 小时内总结 |
| P2 一般故障 | 1 小时内 | 每 2 小时 | 当天内总结 |
| P3 轻微故障 | 可事后记录 | - | 事后记录 |

### 更新内容模板

#### 首次更新（调查中）

```
🔴 【问题】服务异常
⏰ 时间：2026-09-06 22:30 UTC+8
📋 影响：部分用户无法登录，API 响应缓慢
🔍 状态：我们已经监测到问题，正在调查原因
🔄 下次更新：30 分钟内，或有进展时立即更新
```

#### 进展更新

```
🟡 【更新中】服务异常 - 更新 2
⏰ 更新时间：2026-09-06 22:55 UTC+8
📋 当前状态：已定位到数据库连接池问题，正在处理
⏱️ 预计恢复：约 30 分钟
🔄 下次更新：有进展时更新
```

#### 恢复通知

```
🟢 【已解决】服务已恢复
⏰ 恢复时间：2026-09-06 23:10 UTC+8
📋 状态：所有服务已恢复正常运行
📝 总结：本次故障持续约 40 分钟，原因为数据库连接池配置问题。我们将在 3 个工作日内发布完整的故障复盘报告。
🙏 对本次故障给您带来的影响深表歉意。
```

## 事后报告（Post-mortem）

### 发布时间

P0/P1 故障：恢复后 3 个工作日内发布
P2 故障：当周内发布

### 报告结构

```
1. 摘要
   - 故障级别
   - 起止时间
   - 影响范围
   - 根本原因（一句话）

2. 时间线
   - 精确到分钟的事件时间线
   - 发现 → 响应 → 定位 → 恢复

3. 根本原因分析
   - 直接原因
   - 深层原因（5 Whys）
   - 为什么监控没提前发现

4. 影响评估
   - 受影响的用户数 / 租户数
   - 业务影响
   - SLA 影响

5. 改进措施
   - 技术改进
   - 流程改进
   - 每项有负责人和预计完成时间

6. 总结与致歉
```

### 写作原则

- **诚实** — 不回避问题，不美化，不甩锅
- **具体** — 有具体时间、具体数字、具体原因
- **负责** — 我们的问题就是我们的问题，不找借口
- **行动导向** — 重点放在我们要怎么改，不只是解释

**反模式：**
❌ "受第三方服务商影响" — 第三方也是你选的，也是你的责任
❌ "极少数用户受影响" — 有多"极少"？给数字
❌ "不可抗力" — 真正的不可抗力很少，大多是可以预防的

## 计划内维护通知

### 通知流程

```
T-7 天：发布维护预告（Status Page + 邮件通知受影响客户）
T-3 天：再次提醒
T-1 天：最终提醒
T-0：维护开始，Status Page 更新为维护中
T+维护完成：Status Page 更新为已完成
```

### 维护通知模板

```
🔵 【计划维护通知】系统例行维护
📅 时间：2026-09-10 02:00 - 04:00 UTC+8
⏱️ 时长：约 2 小时
📋 影响：
  - 维护期间服务可能有 1-2 次短暂不可用（每次 < 5 分钟）
  - 部分后台操作可能延迟
🔧 内容：数据库版本升级，提升性能和稳定性
📧 如有紧急问题，请联系客户成功团队
```

### 维护窗口选择

- 选业务低峰期（一般凌晨 2-6 点）
- 避开工作日（一般选周末）
- 避开月底月初（财务月结等）
- 不同时区的客户照顾到当地时间

## 多渠道沟通

### 沟通渠道矩阵

| 渠道 | 适用场景 | 受众 |
|---|---|---|
| **Status Page** | 所有事件的主渠道 | 所有客户 |
| **邮件通知** | P0/P1 故障 + 计划维护 | 受影响客户 / 大客户 |
| **Status Page 订阅** | 实时推送通知 | 订阅用户 |
| **客服公告** | 客服话术同步 | 客服团队 |
| **客户成功一对一** | 大客户、重点客户 | CSM 对接的客户 |
| **社交媒体** | 重大故障 | 公众 |
| **内部公告** | 全公司同步 | 内部员工 |

### 客服话术同步

故障发生后第一时间给客服团队同步：
- 发生了什么
- 影响什么
- 现在是什么状态
- 预计什么时候恢复
- 客户问起来怎么说

**客服是第一线，不能让客户问的时候客服还不知道。**

## 常见陷阱

| 陷阱 | 表现 | 规避方法 |
|---|---|---|
| 能瞒就瞒 | 小故障不更新，假装没发生 | 诚信第一，越小的事越要透明 |
| 技术黑话 | 满篇技术术语，客户看不懂 | 用客户能听懂的话，说清楚影响 |
| 更新不及时 | 故障两小时了页面还是"调查中" | 定好更新频率，哪怕没进展也要说"还在查" |
| 事后不了了之 | 故障恢复了就完了，没下文了 | 每次 P0/P1 都要有事后报告 |
| 甩锅第三方 | 都是第三方的错，我们没问题 | 第三方也是你选的，你的责任 |
| 只有 Status Page | 只更新 Status Page，不主动通知客户 | 多渠道，大客户主动触达 |
| 客服信息不同步 | 客户问客服，客服说"我不知道" | 故障发生第一时间同步客服话术 |
