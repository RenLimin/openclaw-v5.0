# 监控告警体系建设 SOP

## 适用场景

- SaaS 产品的监控告警体系设计与落地
- 从基础设施到业务指标的全链路监控
- 告警分级、降噪、on-call 机制
- 监控系统的选型与运维

---

## 核心原则

1. **全栈可观测** — 基础设施、应用、业务、用户体验，层层都要有监控
2. **告警要能行动** — 每个告警都应该有明确的处理步骤，不能让人看了发呆
3. **降噪是第一要务** — 告警多了等于没有告警，狼来了的故事
4. **趋势比单点重要** — 看趋势，看变化，不纠结瞬时值
5. **监控自己也要监控** — 监控系统挂了谁都不知道，双重保险

---

## 监控分层体系

### 五层监控模型

```
L5 业务指标层：MRR、活跃用户、转化率、功能使用率
L4 应用性能层：APM、错误率、延迟、吞吐量
L3 系统服务层：中间件（MQ/Redis/ES）、数据库
L2 基础设施层：CPU、内存、磁盘、网络、容器
L1 物理环境层：机房、电力、网络设备、运营商
```

### 各层监控内容

#### L1 基础设施（IaaS）

| 监控项 | 指标 | 告警阈值（示例） |
|---|---|---|
| 计算 | CPU 使用率、内存使用率、磁盘使用率、磁盘 IOPS | CPU > 80% 持续 5 分钟 |
| 网络 | 带宽、丢包率、延迟、连接数 | 丢包 > 1% |
| 存储 | 磁盘剩余空间、IO 延迟 | 磁盘剩余 < 20% |
| 容器 | Pod 状态、重启次数、资源限制 | Pod 重启 > 3 次/小时 |

#### L2 中间件 / 数据层

| 组件 | 关键指标 |
|---|---|
| 数据库 | QPS、连接数、慢查询、主从延迟、事务数 |
| 缓存（Redis） | 命中率、内存使用率、连接数、key 数量 |
| 消息队列 | 积压深度、消费速度、死信队列数 |
| 搜索引擎 | 查询延迟、索引速率、集群健康状态 |
| API 网关 | QPS、错误率、延迟、限流次数 |

#### L3 应用层（APM）

**指标类型：**
- **Golden Signals（四大黄金指标）：** 延迟、流量、错误率、饱和度
- **RED 方法：** Rate（速率）、Errors（错误）、Duration（耗时）
- **USE 方法：** Utilization（使用率）、Saturation（饱和度）、Errors（错误）

**关键指标：**

| 指标 | 说明 | 告警 |
|---|---|---|
| 请求量（QPS/RPM） | 每秒/每分钟请求数 | 突增 / 突降 > 30% |
| 错误率 | 5xx / 总请求 | > 1% 警告，> 5% 严重 |
| 响应延迟 | P50 / P95 / P99 | P95 > 500ms 警告，> 1s 严重 |
| 异常数 | 未捕获异常 | 突增 > 50% |
| 进程状态 | 存活实例数 | 实例数 < 期望数 |

#### L4 业务指标层

**为什么业务也要监控？** 技术指标正常不代表业务正常。
比如：所有 API 都返回 200，但因为 bug，下单全失败了。技术监控看不到，业务监控能看到。

| 指标 | 说明 | 告警 |
|---|---|---|
| 核心转化漏斗 | 注册 → 激活 → 付费 | 转化率突降 > 20% |
| 关键业务量 | 订单量、发布量、创建量 | 同比 / 环比异常 |
| 功能使用率 | 核心功能 DAU / 使用次数 | 突降 |
| 用户增长 | 新增用户、活跃用户 | 异常波动 |

#### L5 用户体验层

- 真实用户监控（RUM）：页面加载时间、错误率
- 合成监控：全球多点主动探测
- 客服工单量：异常上升 = 可能有问题

## 告警分级与降噪

### 告警分级

| 级别 | 定义 | 响应时间 | 通知方式 | 谁来处理 |
|---|---|---|---|---|
| **P0 — 紧急** | 全服务不可用 / 数据丢失风险 | 立即（5 分钟内） | 电话 + 短信 + 所有渠道 | on-call 工程师 + 负责人 |
| **P1 — 高** | 核心功能故障 / 大面积影响 | 15 分钟内 | 短信 + 电话 | on-call 工程师 |
| **P2 — 中** | 非核心功能故障 / 性能下降 | 1 小时内 | 企业微信 / 钉钉 + 邮件 | 对应模块负责人 |
| **P3 — 低** | 轻微异常 / 趋势预警 | 工作日内处理 | 邮件 / 工单 | 对应团队 |

### 降噪策略

**1. 持续时间过滤**
- 瞬时抖动不告警，持续 N 分钟才告警
- 例：CPU > 80% 持续 5 分钟才告警

**2. 告警聚合**
- 同一根因的多个告警合并成一个
- 例：数据库挂了，所有服务都报错，只发一个"数据库故障"告警

**3. 依赖抑制**
- 底层故障了，上层的告警都抑制掉
- 例：机房断网了，不发 1000 个服务不可用告警

**4. 黑白时间**
- 发布期间的预期波动不告警
- 计划内维护期间静默相关告警

**5. 告警分级**
- 只有 P0/P1 才叫人起床，P2/P3 上班再说

## On-Call 机制

### On-Call 轮值

- 每个团队有 on-call 轮值表
- 主 on-call + 副 on-call（backup）
- 每周轮换
- 轮值期 24/7

### 响应流程

```
告警触发 → 通知 on-call
    ↓
on-call 确认收到（5 分钟内）
    ↓
评估级别，开始处理
    ↓
P0/P1 → 升级到负责人，启动故障响应
P2/P3 → 记录，工作时间处理
    ↓
故障恢复 → 关闭告警 → 复盘
```

### On-Call 文化

- on-call 不是惩罚，是责任
- on-call 期间有补贴或调休
- 第二天可以晚到 / 在家办公
- 频繁被叫醒说明系统有问题，要改进系统，不是怪 on-call

## 监控工具选型

### 常见工具栈

| 类别 | 开源方案 | 商业方案 | 云原生方案 |
|---|---|---|---|
| **指标监控** | Prometheus + Grafana | Datadog、New Relic | CloudWatch、云监控 |
| **日志** | ELK / Loki | Splunk、Sumo Logic | 云日志服务 |
| **APM** | SkyWalking、Pinpoint | Datadog APM、New Relic | - |
| **告警通知** | Alertmanager | PagerDuty、Opsgenie | 云告警 |
| **合成监控** | - | Pingdom、UptimeRobot | - |
| **RUM** | - | Datadog RUM、Sentry | - |

**推荐组合（中型团队）：**
- 指标：Prometheus + Grafana
- 日志：Loki + Grafana 或 ELK
- APM：SkyWalking（Java）或语言自带 profiling
- 告警：Alertmanager + 企业微信 / 钉钉
- 日志错误：Sentry

## 监控最佳实践

### Dashboard 设计

- **按层级组织：** 总览 → 服务 → 实例
- **总览看板：** 一眼能看出系统健康状况（红黄绿）
- **每个服务一个看板：** 四大黄金指标 + 关键业务指标
- **用颜色：** 正常绿色、警告黄色、异常红色

### 告警反模式（不要做）

❌ **不要设置"磁盘使用率 > 90%"这种告警** — 90% 和 91% 有本质区别吗？设成"剩余 < 10GB"或者"增长速度预测 7 天内会满"
❌ **不要用平均值告警** — 平均值会掩盖问题，用 P95 / P99
❌ **告警不写怎么处理** — 收到告警不知道该干嘛，等于没用
❌ **告警太多人** — @所有人 = 没人负责

### 告警质量标准

一个"好"的告警应该：
1. **有明确的严重级别** — P0/P1/P2/P3
2. **有明确的影响范围** — 影响什么功能、多少用户
3. **有处理指引** — 指向 runbook / 故障处理手册
4. **有明确的 owner** — 谁负责处理这个告警
5. **可行动** — 收到后知道该做什么

## 常见陷阱

| 陷阱 | 表现 | 规避方法 |
|---|---|---|
| 告警风暴 | 一次故障收到几百条告警，根本看不过来 | 告警聚合 + 依赖抑制 + 分级 |
| 狼来了 | 告警太多，都是噪音，真出问题没人理 | 定期清理无效告警，只留有用的 |
| 只看技术指标 | API 都是 200，但业务已经崩了 | 业务监控和技术监控同等重要 |
| 监控了但不看 | Dashboard 做了一堆，没人看 | 告警推到人面前，总览看板每日站会看 |
| 没有告警演练 | 告警来了不知道怎么处理 | 定期故障演练，更新 runbook |
| 监控系统自己挂了 | 监控挂了，真出问题不知道 | 监控系统也要有监控，双重保险 |
| 全靠工具 | 以为上了 Prometheus 就完事了 | 工具是基础，关键是人和流程 |
