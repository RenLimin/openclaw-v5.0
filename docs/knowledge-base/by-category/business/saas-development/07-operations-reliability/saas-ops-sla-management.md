# SLA 管理与可用性保障 SOP

## 适用场景

- SaaS 产品 SLA（服务等级协议）的定义与承诺
- 服务可用性的度量、报告与改进
- SLA 违约的赔偿与客户沟通
- 高可用架构与运维体系建设

---

## 核心原则

1. **承诺的必须做到** — SLA 不是营销话术，做不到的不要写进合同
2. **可测量才叫 SLA** — 无法度量的可用性承诺都是空话
3. **透明化** — SLA 达成情况公开透明，对客户和自己都诚实
4. **预防胜于救火** — 把精力放在提升可靠性上，不是放在赔多少钱上
5. **分层 SLA** — 不同客户等级有不同的 SLA 承诺，不搞一刀切

---

## SLA 指标体系

### 核心指标

| 指标 | 定义 | 计算公式 |
|---|---|---|
| **服务可用性** | 服务正常可用的时间比例 | 正常时间 / 总时间 × 100% |
| **故障响应时间** | 从故障发生到开始响应的时间 | 响应时间 - 发生时间 |
| **故障恢复时间（RTO）** | 从故障发生到完全恢复的时间 | 恢复时间 - 发生时间 |
| **数据丢失量（RPO）** | 故障导致的数据丢失时间窗口 | 最后一次有效备份到故障时间 |
| **首字节延迟（TTFB）** | 请求从发起到收到第一个字节的时间 | - |

### 可用性等级对照表

| 可用性等级 | 年停机时间 | 月停机时间 | 周停机时间 | 典型场景 |
|---|---|---|---|---|
| 99% | 3.65 天 | 7.2 小时 | 1.68 小时 | 内部工具、非关键系统 |
| 99.5% | 1.83 天 | 3.6 小时 | 50.4 分钟 | 普通 SaaS |
| 99.9% | 8.76 小时 | 43.2 分钟 | 10.1 分钟 | 企业级 SaaS |
| 99.95% | 4.38 小时 | 21.6 分钟 | 5.0 分钟 | 关键业务系统 |
| 99.99% | 52.6 分钟 | 4.3 分钟 | 1.0 分钟 | 金融级、电信级 |
| 99.999% | 5.26 分钟 | 25.9 秒 | 6 秒 | 极高可用性系统 |

**SaaS 行业基准：**
- 免费版：99%（没 SLA 承诺）
- 付费标准版：99.9%
- 企业版：99.95% ~ 99.99%
- 定制版 / 专属部署：可协商

## SLA 分层承诺

### 按客户等级

| 套餐 | 可用性承诺 | 响应时间 | 赔偿条款 |
|---|---|---|---|
| 免费版 | 无承诺，尽力而为 | 社区支持 | 无 |
| 基础版 | 99.9% | 24 小时响应 | 有（按月费比例） |
| 专业版 | 99.95% | 12 小时响应 | 有（更高比例） |
| 企业版 | 99.99% | 1 小时 / 7×24 | 有（定制化） |
| 旗舰版 | 可协商（99.99%+） | 30 分钟 / 专属对接 | 定制 |

### 服务范围

SLA 覆盖的服务范围要写清楚，避免扯皮：

| 包含 | 不包含 |
|---|---|
| 核心 API 可用性 | 客户网络问题 |
| Web 应用可用性 | 客户自身操作失误 |
| 数据存储服务 | 第三方依赖服务故障（如支付网关） |
| 管理后台 | 计划内维护（提前通知的） |
| - | Beta / 实验性功能 |
| - | 不可抗力（地震、火灾、运营商故障） |

## 可用性度量

### 度量方法

**三种常见度量方式：**

| 方法 | 说明 | 优缺点 |
|---|---|---|
| **探针监测** | 全球多点主动探测 | 接近真实用户体验，但成本高 |
| **错误率计算** | 基于服务端错误率 | 容易统计，但不反映网络问题 |
| **用户体验指标** | 基于真实用户数据（RUM） | 最真实，但实现复杂 |

**推荐组合：**
- 主指标：服务端成功率（请求成功数 / 总请求数）
- 辅助：主动探测 + 真实用户监控

### 统计口径

**可用性计算公式：**
```
可用性 = 1 - (故障时间 / 总时间) × 100%
```

**什么算"故障时间"：**
- 服务完全不可用 → 全算
- 部分功能不可用 → 按影响比例折算
- 性能严重下降（P95 > 5 秒）→ 部分折算
- 计划内维护 → 不算
- 第三方依赖故障 → 不算（如果我们没有 SLA 承诺的话）

**统计周期：** 自然月

### 透明化报告

- Status Page 实时展示当前状态
- 每月发布 SLA 报告（公开的）
- 内容：本月可用性、故障事件、改进措施
- 诚实：达不到就是达不到，不要造假

## SLA 赔偿机制

### 赔偿标准（示例）

| 可用性达成 | 赔偿比例 |
|---|---|
| ≥ 99.99% | 0%（达标） |
| 99.95% ~ 99.99% | 10% 月费 |
| 99.9% ~ 99.95% | 25% 月费 |
| 99% ~ 99.9% | 50% 月费 |
| < 99% | 100% 月费 |

### 赔偿流程

```
1. 月度 SLA 统计出炉
2. 未达标的客户自动生成赔偿
3. 赔偿方式：
   - 抵扣下次账单（推荐）
   - 原路退回（客户要求时）
4. 邮件通知客户
5. 财务处理
```

### 赔偿上限

- 每个月赔偿不超过当月服务费的 100%
- 年付客户按月折算
- 连续多个月不达标 → 客户可以无责解约

**注意：** SLA 赔偿是服务承诺，不是损失赔偿。间接损失（业务损失等）不赔，要写清楚。

## 高可用保障体系

### 多层高可用架构

```
L1 网络层高可用：多运营商 + BGP + CDN
     ↓
L2 接入层高可用：负载均衡 + 多可用区部署
     ↓
L3 应用层高可用：无状态 + 水平扩展 + 多副本
     ↓
L4 数据层高可用：主从复制 + 读写分离 + 多副本
     ↓
L5 灾备高可用：异地灾备 + 定期演练
```

### 关键技术措施

| 层级 | 措施 | 可用性提升 |
|---|---|---|
| 基础设施 | 多云 / 多可用区部署 | 从 99.9% → 99.95% |
| 应用 | 无状态设计，水平扩展 | 消除单点 |
| 数据库 | 主从 + 自动故障转移 | RTO < 30s |
| 缓存 | 集群 + 哨兵 / 集群模式 | 防止缓存雪崩 |
| 发布 | 灰度发布 + 快速回滚 | 减少发布故障 |
| 监控 | 全链路监控 + 告警 | 快速发现问题 |
| 预案 | 故障预案 + 定期演练 | 快速恢复 |

## 计划内维护

### 维护分类

| 类型 | 频率 | 是否停机 | 提前通知 |
|---|---|---|---|
| **例行维护** | 每月 1-2 次 | 一般不停机（灰度） | 3 天前通知 |
| **重大维护** | 每季度 1 次 | 可能短暂停机 | 7 天前通知 |
| **紧急维护** | 按需 | 可能 | 1 小时前通知（事后补详情） |

### 维护窗口

- 选在业务低峰期（一般是凌晨 2:00-6:00）
- 避开工作日和月底月初
- 不同地区客户按当地时间安排
- 维护时间计入 SLA 吗？提前通知的不算

## SLA 改进闭环

### PDCA 循环

```
Plan：设定 SLA 目标和改进计划
  ↓
Do：执行改进措施
  ↓
Check：监控 SLA 达成情况
  ↓
Act：分析故障根因，持续改进
```

### 故障复盘驱动改进

每次 P1/P0 故障后：
1. 出故障复盘报告（5 Whys + 根因分析）
2. 列出改进项（技术 + 流程）
3. 指定负责人和截止日期
4. 跟踪改进项落地
5. 下季度回顾

## 常见陷阱

| 陷阱 | 表现 | 规避方法 |
|---|---|---|
| SLA 吹牛逼 | 营销写 99.99%，实际 99.5% | 承诺你能做到的，做不到的别写 |
| 统计口径作弊 | 把故障时间算成"计划内维护" | 诚实统计，对客户和自己都诚实 |
| 只有 SLA 没有 SLO | 只盯着合同上的承诺，内部没有目标 | SLO（内部目标）要比 SLA（对外承诺）高一个等级 |
| 全靠技术 | 以为技术做好了就够了，流程和人不行 | 技术 + 流程 + 人，三位一体 |
| 只看可用性 | 99.99% 可用但每次都卡得要死 | 可用性 + 性能，都要达标 |
| 赔偿当收入损失 | 赔了钱就心疼，能不赔就不赔 | SLA 赔偿是承诺，该赔就赔，换来的是客户信任 |
| 没有状态页 | 出问题了客户到处问怎么回事 | 公开 Status Page，实时更新 |
