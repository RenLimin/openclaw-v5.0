# 故障响应与应急处理 SOP

## 适用场景

- SaaS 产品线上故障的发现、响应、处理、恢复
- 故障分级、升级、沟通机制
- 故障复盘与持续改进
- On-Call 团队的应急操作规范

---

## 核心原则

1. **先恢复，后排查** — 第一优先级是让服务回来，不是找根因
2. **明确指挥链** — 故障期间一个指挥，不能七嘴八舌
3. **透明沟通** — 内部外部都要及时同步，越瞒越慌
4. **每次故障都是学习机会** — 不追责，只改进，同样的错不犯第二次
5. **有预案不慌乱** — 常见故障有 runbook，照着做就行

---

## 故障分级

### 分级标准

| 级别 | 定义 | 影响范围 | 响应时间 |
|---|---|---|---|
| **P0 — 紧急** | 核心服务完全不可用，或有数据丢失风险 | 大面积 / 全量用户 | 立即响应（5 分钟内） |
| **P1 — 严重** | 核心功能严重受损，大量用户受影响 | 重要功能不可用 | 15 分钟内响应 |
| **P2 — 一般** | 非核心功能故障，或部分用户受影响 | 次要功能 / 少量用户 | 1 小时内响应 |
| **P3 — 轻微** | 轻微异常，不影响主要使用 | 体验问题 / 边缘功能 | 工作日处理 |

### 分级判定因素

判断故障级别时综合考虑：
1. **影响范围** — 多少用户 / 多少租户受影响
2. **功能重要性** — 是核心功能还是边缘功能
3. **持续时间** — 已经持续了多久
4. **数据风险** — 有没有数据损坏或泄露
5. **客户影响** — 有没有大客户受影响

**升级条件：** P2 故障持续超过 2 小时 → 升级为 P1

## 故障响应流程

### 六步响应法

```
1. 发现 → 2. 响应 → 3. 定位 → 4. 恢复 → 5. 沟通 → 6. 复盘
```

### 第一步：发现

**故障发现渠道（按优先级）：**
1. 监控告警（主动发现，最快）
2. 内部测试 / 员工发现
3. 客户报告（客服 / 客户成功）
4. 社交媒体 / 公开反馈

**目标：** 我们比客户先发现问题。

**度量：** MTTD（Mean Time to Detect，平均发现时间）

### 第二步：响应

**接到告警后：**
1. on-call 工程师 5 分钟内确认收到
2. 评估故障级别（P0/P1/P2/P3）
3. P0/P1 → 拉故障响应群 / 电话会议
4. 通知相关方（根据级别）
5. 指定 Incident Commander（IC，故障指挥官）

**角色分工：**

| 角色 | 职责 |
|---|---|
| **IC（指挥官）** | 总指挥，协调资源，做决策，对外沟通 |
| **技术负责人** | 技术排查，定位根因，制定恢复方案 |
| **操作执行** | 执行恢复操作 |
| **记录员** | 时间线记录，同步状态 |
| **客户沟通** | 对外沟通（Status Page、客户通知） |

**小团队可以一人多角色，但 IC 必须明确。**

### 第三步：定位

**定位思路（从外到内，从下往上）：**
1. 先确认是不是真的有问题（误报？）
2. 影响范围有多大（全量？部分？特定租户？）
3. 最近有没有变更（发布？配置变更？）
4. 从入口往里面查（网关 → 应用 → 数据库）
5. 看错误日志、看指标变化
6. 对比正常时候有什么不一样

**常见排查顺序：**
```
最新的变更？→ 错误率？→ 延迟？→ 资源使用？→ 依赖服务？→ 网络？
```

**黄金法则：** 优先怀疑最近的变更。80% 的故障是最近的变更导致的。

### 第四步：恢复（最重要）

**恢复优先于根因分析。**

**常见恢复手段（按速度排序）：**

| 手段 | 速度 | 适用场景 |
|---|---|---|
| **回滚** | 分钟级 | 发布导致的故障 |
| **切流** | 秒级 | 单机房 / 单可用区故障 |
| **重启** | 秒 ~ 分钟级 | 资源泄漏、死锁 |
| **扩容** | 分钟级 | 流量突增、容量不足 |
| **降级 / 熔断** | 秒级 | 依赖故障，保核心 |
| **修复代码** | 小时级 | 需要改代码的 bug |
| **恢复数据** | 小时 ~ 天级 | 数据损坏 |

**回滚是第一选项。** 不确定问题在哪就先回滚，回滚完了再慢慢查。

**恢复验证：**
- 核心指标恢复正常
- 错误率下降到正常水平
- 业务指标恢复
- 抽样验证功能正常

### 第五步：沟通

**内部沟通：**
- 故障群里实时同步（每 15-30 分钟同步一次状态）
- P0 故障通知管理层
- 恢复后发故障通知邮件

**外部沟通：**
- Status Page 实时更新状态
- P0/P1 故障主动通知大客户（CSM 对接）
- 故障中每隔一段时间同步进展
- 恢复后发详细的故障说明

**沟通原则：**
- 诚实：是什么说什么，不知道就说正在调查
- 及时：哪怕还不知道原因，也要说"我们知道了，正在查"
- 具体：说清楚影响什么、什么时候能恢复

### 第六步：复盘

故障恢复后 3 个工作日内完成复盘。

**复盘会议：**
- 参与人：所有相关人员
- 主持人：IC 或技术负责人
- 目标：找到根因，防止再发生，不是追责

**复盘报告内容：**
1. 故障概述（时间、影响、级别）
2. 时间线（精确到分钟）
3. 根因分析（5 Whys）
4. 处理过程（做了什么，哪些有效哪些无效）
5. 改进项（技术 + 流程，每项有负责人和 deadline）
6. 经验教训

**改进项跟踪：**
- 录入任务系统
- 定期 review 进度
- 下次复盘回顾上次的改进项有没有落地

## 常见故障 Runbook

### 场景一：服务 CPU / 内存飙升

1. 查看是哪个实例 / 哪个服务
2. 看错误日志有没有异常
3. 看流量是不是突增
4. 看最近有没有发布
5. 临时扩容顶住
6. 抓堆栈 / dump 分析
7. 有发布的话先回滚

### 场景二：数据库压力大

1. 看是 CPU 高还是 IO 高
2. 看慢查询日志，找到最耗时的 SQL
3. 看是不是某个租户的异常请求
4. 临时 kill 掉慢查询
5. 读写分离是否生效
6. 紧急情况：限流 / 降级非核心查询

### 场景三：发布后大量 5xx

1. 立即回滚（别犹豫）
2. 回滚后确认恢复
3. 再查原因
4. 修复后重新走发布流程

### 场景四：消息队列积压

1. 看消费速度是不是下降了
2. 看生产者是不是发多了
3. 看消费者有没有报错
4. 临时加消费者实例
5. 死信队列里的消息要处理

### 场景五：缓存故障（Redis 挂了）

1. 看是实例挂了还是集群问题
2. 自动故障转移有没有生效
3. 缓存雪崩？数据库能不能顶住
4. 紧急：限流 + 降级，保护数据库

## 度量指标

| 指标 | 定义 | 目标 |
|---|---|---|
| **MTTD** | 平均发现时间 | < 5 分钟 |
| **MTTA** | 平均响应时间 | < 15 分钟 |
| **MTTR** | 平均恢复时间 | < 1 小时 |
| **故障频率** | 每月 P0/P1 故障次数 | 持续下降 |
| **重复故障率** | 同样原因的故障占比 | < 10% |

## 常见陷阱

| 陷阱 | 表现 | 规避方法 |
|---|---|---|
| 边排查边想怎么恢复 | 找了半小时根因，服务还挂着 | 先恢复，后排查，恢复第一 |
| 人人都是指挥官 | 大家各说各的，没人拍板 | 指定 IC，一个人指挥 |
| 回滚犹豫 | "我再看看，说不定马上找到原因了" | 发布导致的故障，回滚是默认选项 |
| 不沟通 | 故障了闷头修，客户到处问 | 及时沟通，不知道原因也说一声 |
| 复盘变批斗 | 复盘会变成追责大会，没人敢说话 | 对事不对人，只找改进点，不找人背锅 |
| 改进项不落地 | 复盘写了一堆改进，最后都没做 | 改进项有负责人 + deadline，跟踪落地 |
| 没有演练 | 真出故障了手忙脚乱 | 定期故障演练，混沌工程 |
