# 容量规划与弹性伸缩 SOP

## 适用场景

- SaaS 产品的服务器容量规划与管理
- 自动弹性伸缩策略设计
- 流量高峰应对（如促销、发布会）
- 成本优化与资源利用率提升

---

## 核心原则

1. **留足余量，不要跑满** — 永远不要让资源使用率到 100%，留 30-50% 余量
2. **数据驱动，不是拍脑袋** — 基于历史数据和增长预测做规划
3. **自动优先，人工兜底** — 能自动伸缩的就自动，人工做审核和调整
4. **成本和性能平衡** — 不是资源越多越好，在满足 SLA 前提下控制成本
5. **定期复盘** — 容量规划不是一次性的，每季度 review 一次

---

## 容量规划基础

### 什么是容量规划

预测未来需要多少资源（CPU、内存、存储、带宽等），确保：
- 业务增长时系统能扛住
- 流量高峰时不崩
- 资源利用率合理，不浪费钱

### 关键资源维度

| 资源 | 衡量指标 | 预警阈值 | 扩容阈值 |
|---|---|---|---|
| **计算（CPU）** | CPU 使用率 | 70% | 80% 持续 5 分钟 |
| **内存** | 内存使用率 | 75% | 85% 持续 5 分钟 |
| **存储** | 磁盘使用率 | 70%（剩余 < 30%） | 80% |
| **数据库连接** | 连接数 / 最大连接数 | 70% | 80% |
| **带宽** | 网络流量 | 70% | 80% |
| **缓存命中率** | Redis 命中率 | 90%（低于就预警） | 85% |

### 容量单位

**不要只用"台数"来衡量容量，要用业务指标。**

好的容量单位：
- 每台应用服务器支撑多少 QPS
- 每个数据库实例支撑多少活跃租户
- 每 GB 内存支撑多少并发连接

这样才能根据业务增长预测资源需求。

## 弹性伸缩（Auto Scaling）

### 什么是弹性伸缩

根据负载自动增加或减少服务器数量。
- 流量上来了 → 自动加机器
- 流量下去了 → 自动减机器
- 省钱 + 省心

### 伸缩策略

#### 1. 基于指标的伸缩（最常用）

**触发条件：** CPU / 内存 / QPS 等指标达到阈值

**示例策略：**
```
扩容：CPU 使用率 > 70% 持续 5 分钟 → 加 1 台
缩容：CPU 使用率 < 30% 持续 10 分钟 → 减 1 台

最大实例数：20
最小实例数：3
冷却时间：扩容 5 分钟，缩容 10 分钟
```

**为什么缩容冷却时间更长？** 防止抖动 — 不能刚加了就又减，来回折腾。

#### 2. 基于时间的伸缩（可预期高峰）

**适用场景：** 有明显的业务规律
- 白天高，晚上低
- 工作日高，周末低
- 特定活动日（大促、发布会）

**示例：**
```
工作日 09:00 → 扩容到 10 台
工作日 21:00 → 缩容到 4 台
周末 → 保持 4 台
大促当天 → 提前扩容到 20 台
```

#### 3. 预测式伸缩（进阶）

- 基于历史数据 + 机器学习预测未来负载
- 提前扩容，而不是等压力上来了才加
- 适合流量模式稳定的业务

### 伸缩冷却与保护

**冷却时间（Cooldown）：** 一次伸缩后，等一段时间再看下一次，防止抖动

**保护机制：**
- 最小实例数：缩容不会低于这个数
- 最大实例数：扩容不会超过这个数（防失控）
- 手动干预优先：人工调整后，自动伸缩暂停一段时间
- 健康检查：新实例不健康的话不算，自动替换

### 各层伸缩策略

| 层级 | 伸缩方式 | 速度 |
|---|---|---|
| CDN / 边缘 | 自动（云厂商搞定） | 秒级 |
| API 网关 | 自动伸缩 | 秒 ~ 分钟级 |
| 应用服务 | 水平扩容（加实例） | 分钟级（启动时间） |
| 缓存 | 集群扩容 / 分片 | 分钟级 |
| 消息队列 | 消费者扩容 | 分钟级 |
| 数据库 | 读写分离 / 分库分表 | 小时 ~ 天级（最难） |

**数据库是伸缩的瓶颈。** 应用层可以快速加机器，数据库不行，所以数据库的容量规划要更提前。

## 数据库容量规划

### 为什么数据库最难

- 有状态，不能随便加实例
- 主从复制有延迟
- 分库分表是大工程
- 数据量大了迁移困难

### 数据库扩容路径

```
阶段 1：单库 + 读写分离
  → 读多写少的场景，加从库顶读压力

阶段 2：垂直分库
  → 按业务模块拆成多个数据库

阶段 3：水平分库（分片）
  → 同一张表的数据拆到多个库

阶段 4：NewSQL / 分布式数据库
  → 用 TiDB / CockroachDB 之类的分布式数据库
```

### 数据库容量预警

- 磁盘使用率 70% → 预警，开始规划扩容
- 磁盘使用率 80% → 必须扩容了
- 连接数 70% → 预警
- 慢查询增多 → 检查是不是容量问题
- 主从延迟增大 → 可能是主库压力大了

## 高峰应对流程

### 可预期高峰（大促、发布会等）

**T-7 天：容量评估**
- 预估峰值流量（基于历史数据 + 运营预估）
- 计算需要的资源量
- 预留资源（和云厂商确认有货）

**T-3 天：预扩容**
- 提前把机器加上去（不要等高峰来了再加）
- 数据库提前提升配置
- 缓存预热

**T-1 天：全链路压测**
- 模拟峰值流量压测
- 确认系统能扛住
- 发现瓶颈紧急优化

**T-0：高峰期间**
- 全员 on-call
- 实时监控大盘
- 有问题立即处理
- 准备降级预案

**T+1：高峰后**
- 逐步缩容（不要一下全撤）
- 复盘：实际流量 vs 预估，系统表现
- 总结经验，下次更好

### 突发流量（上热搜、被 DDoS 等）

1. 自动弹性伸缩先顶一波
2. 人工介入确认
3. 必要时启动限流 / 降级
4. 保护核心功能
5. 事后分析原因

## 成本优化

### 资源利用率目标

| 资源 | 目标利用率 | 说明 |
|---|---|---|
| 应用服务器 CPU | 40-60% | 太低浪费，太高顶不住高峰 |
| 数据库 CPU | 30-50% | 数据库更保守，留更多余量 |
| 内存 | 50-70% | 内存一般不是瓶颈，但也别浪费 |
| 存储 | 60-70% | 磁盘便宜，但也要有规划 |

### 成本优化手段

| 手段 | 节省比例 | 实现难度 |
|---|---|---|
| 自动缩容（闲时减机器） | 20-50% | 低 |
| 预留实例 / 包年包月 | 30-50% | 低 |
|  Spot 实例 / 抢占式实例 | 50-80% | 中（可被回收） |
| 冷热数据分离 | 30-60% | 中 |
| 代码层面优化 | 10-30% | 中高 |
| 微服务治理（合并服务） | 20-40% | 高 |

### 成本监控

- 每月云费用分析
- 按业务线 / 环境拆分成本
- 异常账单告警（突然涨了很多）
- 成本占收入比例跟踪

---

## 定期容量 Review

### 频率：每季度一次

### Review 内容

1. **当前容量使用情况**
   - 各资源的平均 / 峰值使用率
   - 是否有瓶颈
   - 最近的扩容 / 缩容记录

2. **业务增长预测**
   - 下季度用户增长预期
   - 有没有重大活动 / 发布
   - 新功能上线带来的负载变化

3. **下季度容量计划**
   - 需要新增多少资源
   - 有没有需要提前准备的（如数据库升级）
   - 预算预估

4. **成本优化**
   - 有没有浪费的资源
   - 可以优化的点
   - 下季度成本目标

## 常见陷阱

| 陷阱 | 表现 | 规避方法 |
|---|---|---|
| 拍脑袋扩容 | "感觉不够了，加 10 台吧" | 数据驱动，基于指标和历史数据 |
| 一直加不减 | 只扩容不缩容，机器越来越多 | 自动缩容 + 定期资源审计 |
| 只看应用层 | 应用层弹性做得很好，数据库顶不住了 | 数据库是瓶颈，重点规划 |
| 压测只测一半 | 压测了应用，没压数据库，结果数据库先崩 | 全链路压测，端到端 |
| 高峰到了才扩容 | 大促当天才加机器，启动慢顶不住 | 提前扩容 + 预热，不要临时抱佛脚 |
| 为了省钱压榨资源 | CPU 常年 90%，一来流量高峰就崩 | 留足余量，30-50% idle 是正常的 |
| 没有成本意识 | 机器随便开，月底账单吓一跳 | 成本监控 + 预算 + 定期优化 |
