# SaaS 需求收集与分级处理 SOP

## 适用场景

- SaaS 产品日常需求收集、归类、优先级判定
- 客户反馈 / 销售反馈 / 内部需求的统一入口管理
- 需求从提出到落地的全生命周期追踪

---

## 需求来源与入口

| 来源 | 入口工具 | 负责人 | SLA |
|---|---|---|---|
| 客户成功（客户反馈） | Linear / 内部工单 | CSM 团队 | 24h 内录入 |
| 销售（售前需求） | CRM 机会关联 | 销售运营 | 随机会同步 |
| 支持工单 | Zendesk / 工单系统 | 支持团队 | 自动同步 |
| 产品团队（洞察/规划） | Linear / PRD | PM | 直接录入 |
| 工程团队（技术债/架构） | Linear / 技术债项目 | Tech Lead | 双周同步 |
| 高管/战略 | Linear / 战略项目 | 产品负责人 | 直接录入 |

**统一原则：** 所有需求最终汇聚到 Linear（或等价工具），一个需求一个 ticket。

---

## 需求分级标准

### P0 — 阻塞型（必须立即处理）

**判定条件（满足任一）：**
- 影响核心功能不可用的 bug
- 安全漏洞或数据泄露风险
- 大客户（ARR Top 20）阻断性问题
- 合规要求导致的强制变更

**响应：**
- 进入当前 sprint，优先处理
- 产品负责人和技术负责人共同确认
- 48 小时内给出方案或临时 workaround

### P1 — 高价值（下个版本必做）

**判定条件（同时满足）：**
- 影响 ≥10% 活跃用户或 ≥20% ARR
- 有明确的业务指标提升预期（留存/转化/效率）
- 技术可行性高，effort < 2 人月

**响应：**
- 进入 Next 路线图（下季度）
- PM 负责产出 PRD
- 季度规划时统一排期

### P2 — 中等价值（排期池）

**判定条件：**
- 有价值但不紧急
- 影响范围中等（5-10% 用户）
- 或 effort 较大但 ROI 中等

**响应：**
- 进入 Later 池，每季度 review 一次
- 同类需求聚合后统一评估

### P3 — 低价值 / 待观察

**判定条件：**
- 单个客户的个性化需求
- 使用频率低、影响面小
- 价值不明确，需要验证

**响应：**
- 标记为 `needs-validation`
- PM 季度 review 时决定：升级 / 保持 / 关闭
- 保留数据，持续观察同类需求积累

## 处理流程

### 1. 需求录入

**必填字段：**
- 标题（一句话描述需求）
- 来源（哪个渠道提的）
- 关联客户 / 机会（如果有）
- 问题描述（用户遇到了什么问题，不是想要什么功能）
- 预期收益（解决后有什么价值）
- 提出人 / 对接人

**录入规范：**
> 描述问题，不是描述解决方案。
>
> ❌ "客户需要导出 Excel"
> ✅ "客户每月需要向财务汇报数据，目前只能手动截图，耗时 4 小时/月"

### 2. Triage 会议（每周一次）

**参会人：** 产品负责人 + 技术负责人 + 客户成功负责人

**议程：**
1. 回顾上周新增需求（P0/P1）
2. 讨论有争议的需求分级
3. 确认本周 P0 处理进展
4. 清理长期无人认领的需求

**输出：** 会议纪要 + 需求状态更新

### 3. 需求澄清

P1 及以上需求，PM 需要在 1 周内完成：
- 与提出人确认细节和真实场景
- 调研同类产品的做法
- 评估技术可行性（与 Tech Lead 沟通）
- 产出 PRD 或需求说明文档

### 4. 排期与开发

- P0：立即进入当前 sprint
- P1：季度规划时排期
- P2：季度 review 时决定是否升级
- P3：持续观察，不主动排期

### 5. 反馈与关闭

- 需求上线后，PM 通知提出人和相关客户
- 观察 2 周使用数据，验证预期效果
- 未达预期的需求，复盘原因，记录为经验
- 不做的需求，向提出人说明原因并关闭

## 需求量化模板

**RICE 快速评估表：**

| 维度 | 评分 | 说明 |
|---|---|---|
| Reach (影响用户数) | 1-5 | 1=<1% 用户，5=>50% 用户 |
| Impact (影响程度) | 0.25-3 | 微小/低/中/高/极高 |
| Confidence (信心) | 0.5-1 | 低/中/高 |
| Effort (工作量) | 1-5 | 1=<1 人周，5=>2 人月 |
| **RICE 得分** | = R×I×C/E | 越高优先级越高 |

---

## 常见误区

| 误区 | 问题 | 纠正 |
|---|---|---|
| 按声音大小排优先级 | 吵得凶的客户需求都做了，沉默的大多数被忽略 | 用数据校准，关注影响面 |
| 把需求当功能做 | 客户说要什么就做什么，不挖根因 | 五问法追问题本质 |
| 全部收下不拒绝 | 需求池越来越大，没人清 | 定期清理 P3，超过 1 年没人提的直接关 |
| 技术债不算需求 | 工程团队的需求永远排不上 | 每个季度留 20% 容量给技术债 |
| PM 一个人说了算 | 决策缺乏透明度，团队不服 | Triage 会议集体决策，留记录 |
