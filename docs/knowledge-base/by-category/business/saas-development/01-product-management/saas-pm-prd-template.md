# SaaS 产品需求文档（PRD）模板与编写规范

## 适用场景

- SaaS 产品功能需求的标准化文档撰写
- 产品、设计、研发、测试之间的需求对齐
- 需求评审、排期、验收的统一依据

---

## 核心原则

1. **写问题，不是写方案** — PRD 首先定义 "解决什么问题"，再讲 "怎么解决"
2. **可被验收** — 每个需求点都必须有可验证的验收标准
3. **完整不冗余** — 该说的说清楚，废话一句不多写
4. **活文档** — PRD 会迭代，变更要有记录，大家看到的永远是最新版
5. **协作文档** — 不是 PM 一个人写的，是团队共同确认的

---

## PRD 文档结构

### 1. 文档头（Frontmatter）

```markdown
---
feature-id: FEAT-2026-Q3-007
feature-name: 批量数据导入
owner: 张三（PM）
status: draft | review | approved | developing | shipped
created: 2026-09-01
updated: 2026-09-06
version: 1.2
---
```

**状态流转：**
```
draft → review → approved → developing → shipped
   ↓       ↓
  废弃   修订（回到 draft）
```

### 2. 背景与目标

**为什么做这个功能？要达到什么目标？**

```
## 背景

- 当前问题：客户每月需要手动录入 1000+ 条数据，耗时 8 小时/人月
- 数据支撑：30% 的客户反馈 "数据录入太麻烦" 是主要痛点；支持工单中 15% 与数据录入相关
- 竞品现状：竞品 A 和 B 都已有批量导入功能，这是我们的卡单点

## 目标

- 业务目标：提升新客户激活率 15%，降低 churn 5%
- 用户目标：将数据录入时间从 8 小时/月降到 1 小时/月
- 衡量指标：
  - 功能激活率：上线 3 个月内 ≥ 40% 的客户使用过
  - 使用率：活跃客户中 ≥ 25% 每月使用
  - NPS 中相关反馈下降 50%
```

**验收标准：** 读完这一节，团队知道 "为什么做" 和 "做成了怎么判断"

### 3. 用户故事与场景

**谁在什么情况下遇到什么问题，需要什么。**

```
## 用户故事

作为 [角色]，我想要 [功能]，以便 [达成的目标]。

| ID | 用户故事 | 优先级 |
|---|---|---|
| US-001 | 作为管理员，我想要批量导入用户数据，以便快速初始化团队 | P0 |
| US-002 | 作为普通用户，我想要批量导入业务数据，以便减少手动录入 | P0 |
| US-003 | 作为管理员，我想要查看导入历史记录，以便追溯谁什么时候导了什么 | P1 |
| US-004 | 作为用户，我想要导入失败时知道具体哪里错了，以便快速修正 | P1 |
```

**关键使用场景：**
- 场景 1：新客户首次 onboard，需要批量导入 500 个用户
- 场景 2：客户每月底批量导入上月业务数据（约 2000 条）
- 场景 3：导入过程中发现格式错误，下载错误报告，修正后重新导入

### 4. 功能需求

**具体做什么，分模块讲清楚。**

#### 4.1 功能范围

| 包含（In Scope） | 不包含（Out of Scope） |
|---|---|
| Excel / CSV 文件导入 | API 导入（后续版本） |
| 字段映射配置 | 定时自动导入（后续版本） |
| 导入预览与校验 | 数据去重（后续版本） |
| 导入结果报告 | - |

#### 4.2 用户流程

```
上传文件 → 选择类型 → 字段映射 → 预览与校验 → 确认导入 → 查看结果
   ↓         ↓          ↓          ↓           ↓          ↓
 支持拖拽   模板选择   自动匹配   错误提示   异步处理   成功/失败详情
```

#### 4.3 详细功能点

**P0 — 必须有：**
- 支持 .xlsx 和 .csv 格式，最大文件 50MB
- 最多支持 10,000 条数据单次导入
- 字段拖拽映射，支持自动识别相似字段名
- 导入前预览前 10 行数据 + 错误检查
- 异步导入，导入过程中可离开页面
- 导入完成后站内通知 + 结果详情

**P1 — 应该有：**
- 保存字段映射模板，下次直接用
- 导入失败时下载错误明细（Excel 格式，标注每行错误原因）
- 导入历史记录列表（最近 30 天）

**P2 — 可以有：**
- 导入前自动去重检测
- 支持定时导入
- API 方式导入

### 5. 非功能需求

```
## 非功能需求

### 性能
- 10,000 条数据导入时间 ≤ 5 分钟
- 导入过程不影响其他用户使用（资源隔离）
- 页面加载时间 P95 < 2s

### 安全
- 导入数据遵循租户隔离，不能越权访问
- 文件上传进行病毒扫描
- 敏感字段导入需二次验证

### 可用性
- 功能可用性 ≥ 99.9%
- 支持回滚到导入前状态（24 小时内）

### 兼容性
- 支持 Chrome / Firefox / Safari 最新两个版本
- 支持 Excel 2016+ / WPS 导出的 xlsx 格式
```

### 6. 数据埋点

```
## 数据埋点需求

| 事件名 | 触发时机 | 上报参数 |
|---|---|---|
| import_page_view | 打开导入页面 | source_page, user_role |
| import_file_upload | 上传文件 | file_size, file_type, row_count |
| import_mapping_complete | 字段映射完成 | mapping_fields_count, auto_matched_count |
| import_start | 开始导入 | row_count, file_size |
| import_success | 导入成功 | row_count, duration_seconds, success_count, fail_count |
| import_fail | 导入失败 | error_type, error_message |
| import_download_report | 下载错误报告 | fail_count |
```

### 7. 验收标准

**可量化、可验证。**

```
## 验收标准

### 功能验收
- [ ] 上传 10,000 行的 csv 文件，5 分钟内完成导入
- [ ] 字段映射页面能正确识别 80% 以上的标准字段名
- [ ] 导入 100 行全错误数据，能正确列出所有错误及行号
- [ ] 导入完成后，数据库中数据正确，无脏数据

### 性能验收
- [ ] 10,000 行导入 P95 < 5 分钟
- [ ] 导入期间核心 API P95 延迟波动 < 10%

### 安全验收
- [ ] A 租户导入的数据，B 租户无法访问
- [ ] 上传 exe 等危险文件被拦截
```

### 8. 风险与依赖

```
## 风险与依赖

### 依赖
- 依赖文件上传服务 v2（预计 9 月中上线）
- 依赖消息队列异步处理框架（已可用）

### 风险
| 风险 | 概率 | 影响 | 缓解措施 |
|---|---|---|---|
| 大文件导入导致数据库压力过高 | 中 | 高 | 分批导入 + 限流 + 错峰执行 |
| Excel 格式兼容问题多 | 高 | 中 | 提供标准模板 + 明确格式要求 + 友好提示 |
```

## 编写规范

- **语言：** 简洁明确，避免模糊词（"尽量"、"可能"、"大概"）
- **颗粒度：** 一个 PRD 对应一个完整功能模块，不是一个按钮也不是整个产品
- **配图：** 关键流程和复杂界面必须有原型图或流程图
- **可读性：** 多用列表和表格，少用长段落
- **更新：** 需求变更必须更新 PRD + 通知所有相关人 + 记录变更

---

## 常见陷阱

| 陷阱 | 表现 | 规避方法 |
|---|---|---|
| PRD 当设计文档写 | 像素级描述界面细节 | 交互细节交给设计，PRD 讲清楚规则和边界 |
| 只写 happy path | 只有正常流程，异常情况全靠研发猜 | 异常流程至少覆盖 80% 场景 |
| 没有验收标准 | 做完了不知道算不算做完 | PRD 必须有可量化的验收标准 |
| 写完就完了 | PRD 写好发出去就不管了 | PRD 是活文档，随评审和开发持续更新 |
| 太冗长 | 50 页 PRD，没人看完 | 能用表格别用段落，保持 5-15 页 |
