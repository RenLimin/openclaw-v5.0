# SaaS 版本发布管理 SOP

## 适用场景

- SaaS 产品功能版本的规划、发布、灰度、复盘全流程
- 大版本（major）、小版本（minor）、补丁版（patch）的分级发布管理
- 跨团队（产品/研发/测试/客户成功/销售）发布协同

---

## 核心原则

1. **小步快跑** — 优先小版本频繁发布，减少单次变更风险
2. **灰度优先** — 所有新功能先灰度，再全量，杜绝大爆炸式发布
3. **可回滚** — 每个版本必须有回滚方案，发布前确认回滚路径畅通
4. **谁发布谁负责** — 发布 owner 对发布质量和后果负责
5. **客户沟通前置** — 影响客户使用的变更，至少提前 3 个工作日通知

---

## 版本类型与节奏

| 版本类型 | 命名规则 | 发布频率 | 内容特点 | 审批级别 |
|---|---|---|---|---|
| **Major (大版本)** | vX.0.0 | 6-12 个月 | 架构级变更、核心功能重构 | CTO + 产品负责人 |
| **Minor (小版本)** | vX.Y.0 | 每 2-4 周 | 新功能、功能优化 | 产品负责人 + Tech Lead |
| **Patch (补丁版)** | vX.Y.Z | 按需，随时 | Bug 修复、安全补丁 | Tech Lead |
| **Hotfix (热修复)** | vX.Y.Z-hotfixN | 紧急情况 | 线上严重问题修复 | 值班负责人 |

## 发布流程

### 1. 发布规划（版本冻结前 2 周）

**输出物：**
- 版本功能清单（Feature List）+ 每个功能的 owner
- 发布风险评估表
- 灰度策略（哪些客户 / 百分比 / 分几批）
- 回滚预案
- 客户沟通计划（哪些客户需要通知）

**准入条件：**
- 版本功能清单 90% 以上已开发完成
- 核心功能测试通过
- 性能压测达标（P95 不劣于上一版本 10%）
- 安全评审通过（涉及权限/数据的功能）

### 2. 代码冻结（Freeze）

**冻结周期：** 大版本 7 天，小版本 3 天，补丁版 1 天

**冻结期间规则：**
- 只允许合入 Bugfix，不允许新功能
- 每次合入必须有对应的 issue / ticket
- Tech Lead 审核所有合入
- 冻结期间新增的 P0 Bug 自动推迟版本

### 3. 预发布与验收

**UAT 环境验证：**
- 产品经理 + QA 共同验收
- 核心业务流程回归测试通过
- 性能基线对比（与上一版本对比，波动 ≤10%）
- 数据迁移脚本 dry-run 通过

**预发布 Checklist：**
- [ ] 所有 P0/P1 Bug 已修复
- [ ] 产品文档 / 帮助中心已更新
- [ ] 客户成功团队已完成培训
- [ ] 销售团队已获知关键更新
- [ ] 监控告警已配置（新功能的关键指标）
- [ ] 回滚方案已演练

### 4. 灰度发布

**灰度批次（标准四步走）：**

| 批次 | 范围 | 观察期 | 通过标准 |
|---|---|---|---|
| **第 1 批** | 内部团队 + 种子客户（≤5 家） | 24 小时 | 无 P0 Bug，错误率 <0.1% |
| **第 2 批** | 10% 活跃租户 | 48 小时 | 错误率 <0.5%，无新增 P0 |
| **第 3 批** | 50% 活跃租户 | 48 小时 | 错误率 <1%，关键指标正常 |
| **全量** | 100% | - | 灰度期间无重大问题 |

**灰度期间监控：**
- 错误率（5xx / 整体请求量）
- 关键业务指标（登录成功率、核心功能调用量）
- 性能指标（P50 / P95 / P99 延迟）
- 客户工单量（对比基线）
- 资源使用率（CPU / 内存 / 数据库连接）

### 5. 全量发布

**发布时间选择：**
- 常规发布：工作日上午 10:00-12:00（团队都在，有问题能及时响应）
- 避免周五下午发布（没人修 bug）
- 避免客户高峰时段（如工作日早 9 点、月初月末）
- 大版本选择业务低谷期（节假日前后）

**全量后观察：**
- 发布后 2 小时密集监控，团队全员待命
- 发布当天不安排重大变更
- 发布后 24 小时出具发布报告

### 6. 发布复盘

**发布后 3 个工作日内完成复盘：**

| 维度 | 检查项 |
|---|---|
| **质量** | P0/P1 Bug 数、回滚率、线上问题数 |
| **效率** | 是否按计划时间发布、延期原因 |
| **过程** | 哪些流程顺畅、哪些卡点 |
| **数据** | 新功能使用率、关键指标变化 |
| **客户** | 客户反馈、工单量变化、是否有客诉 |

**输出：** 发布复盘报告 + 改进项（指派到人 + 截止日期）

## 回滚机制

**触发回滚的条件（满足任一立即回滚）：**
- 核心功能不可用超过 15 分钟
- 数据损坏或数据泄露风险
- P0 Bug 无法在 30 分钟内定位修复
- 错误率飙升超过 5% 且持续 10 分钟

**回滚方式：**
- **功能开关回滚** — 优先，秒级生效（有 feature flag 的功能）
- **版本回滚** — 回退到上一版本，分钟级
- **数据回滚** — 从备份恢复，仅在数据损坏时使用

**回滚后操作：**
- 确认系统恢复正常
- 通知所有相关方
- 排查根因，修复后重新走发布流程
- 24 小时内出具故障报告

## 客户沟通

| 变更类型 | 通知时间 | 通知对象 | 通知渠道 |
|---|---|---|---|
| 新功能上线 | 发布前 3 天 + 发布当天 | 全部客户 | 产品公告 / 邮件 / 帮助中心 |
| 界面重大调整 | 发布前 7 天 | 全部客户 | 邮件 + 站内通知 + 帮助中心 |
| API 变更（向下兼容） | 发布前 7 天 | 开发者客户 | 开发者文档 + 邮件 |
| API 变更（不兼容） | 发布前 90 天 | 受影响客户 | 定向邮件 + 一对一沟通 |
| 服务停机维护 | 维护前 48 小时 + 前 2 小时提醒 | 受影响客户 | 邮件 + Status Page |

## 常见陷阱

| 陷阱 | 表现 | 规避方法 |
|---|---|---|
| 周五发布 | 周五下班前上线，出问题没人修 | 硬性规定：周四周五不发布大版本 |
| 跳过灰度 | 觉得功能小，直接全量 | 所有功能必须走灰度，哪怕是 1% |
| 无回滚方案 | 发布前没想过怎么回去 | 发布 Checklist 强制包含回滚方案 |
| 发布即结束 | 发完就不管了，等客户报问题 | 发布后 24 小时密集监控，主动发现问题 |
| 文档不同步 | 功能上了，文档还没更 | 文档更新是发布准入条件之一 |
| 沉默发布 | 发了新功能，客户不知道 | 每个版本必须有 release note |
