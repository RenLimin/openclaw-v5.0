# PLG 功能启动与增长实验 SOP

## 适用场景

- Product-Led Growth（产品驱动增长）模式下的新功能上线
- 功能从内部验证到全面推广的分阶段启动
- 通过产品内实验驱动功能采用率和转化

---

## 核心原则

1. **先验证价值，再推广** — 没人用的功能做得再完美也没用
2. **数据说话** — 每个启动阶段都有明确的通过/失败指标
3. **小步迭代** — 用最小可用版本验证假设，快速学习
4. **产品内引导优于外部教育** — 用户在产品里学会用，比看文档有效 10 倍
5. **每个功能都是增长杠杆** — 设计时就考虑它如何驱动激活/留存/付费

---

## 功能启动五阶段

### 阶段 0：Pre-Launch — 内部狗食（Dogfooding）

**目标：** 在真实使用中发现问题，打磨体验

**参与者：** 内部团队全员

**时间：** 2-4 周

**准入条件：**
- 功能核心流程跑通
- 基础 UI 完成，无明显视觉 Bug
- 基本错误处理到位

**通过指标：**
- 内部用户周使用频次 ≥ 3 次
- NPS ≥ 30
- 无 P0/P1 Bug
- 核心任务完成率 ≥ 80%

**不通过怎么办：** 回炉重做，不进入下一阶段

### 阶段 1：Private Beta — 封闭测试

**目标：** 在真实客户环境中验证价值假设

**参与者：** 10-20 家种子客户（招募标准：高活跃度 + 高反馈意愿 + 非付费关键客户）

**时间：** 4-8 周

**招募方式：**
- 客户成功团队定向邀请
- 产品内申请入口（限额）
- 用户社群招募

**通过指标：**

| 指标 | 阈值 | 说明 |
|---|---|---|
| 功能激活率 | ≥ 40% | 尝试过功能的用户中，完成核心动作的比例 |
| 周留存率 | ≥ 30% | 第二周还在用的用户比例 |
| 用户满意度 | ≥ 4/5 | Beta 用户调研评分 |
| P0 Bug 数 | 0 | - |
| 性能 P95 | < 1s | 核心操作响应时间 |

**关键产出：**
- 用户使用数据报告
- 用户访谈记录（至少 10 位）
- 功能价值验证结论（过 / 不过 / 需要调整）

### 阶段 2：Public Beta — 开放测试

**目标：** 更大规模验证，打磨转化漏斗

**参与者：** 所有用户可选开启（feature flag 控制）

**时间：** 4-12 周

**关键动作：**
- 产品内功能入口开放（标注 Beta）
- 帮助文档上线
- 基础 onboarding 流程
- 埋点完善，全漏斗数据可追踪

**核心漏斗指标：**

```
发现 → 点击入口 → 首次使用 → 完成核心动作 → 第二周留存 → 付费转化
  ↓         ↓            ↓              ↓              ↓            ↓
 100%      15%          8%            5%            2%          0.5%
（示例数据，因产品类型而异）
```

**优化方向：**
- 每个环节转化率低于预期 → 针对性优化
- 流失最高的环节 → 下一阶段优化重点
- A/B 测试不同的引导文案、入口位置、交互设计

### 阶段 3：GA — 正式发布

**目标：** 最大化功能采用率和业务影响

**发布动作：**
- 功能全面开放，移除 Beta 标签
- 产品公告 + release note
- 客户成功团队推动重点客户使用
- 销售团队纳入产品卖点

**GA 准入条件：**
- Public Beta 期间核心指标达标
- 功能稳定性 ≥ 99.9%
- 文档和支持流程就绪
- 性能和可扩展性验证通过（预期 10 倍流量无压力）

### 阶段 4：增长优化 — 持续迭代

**目标：** 持续提升功能使用和业务价值

**持续动作：**
- 每月分析功能漏斗数据
- 每季度做 2-3 个增长实验
- 定期用户调研，跟踪满意度趋势
- 功能使用率纳入产品 OKR

## PLG 增长实验框架

### 实验类型

| 类型 | 目标 | 示例 |
|---|---|---|
| **激活实验** | 提升首次使用率 | 优化入口文案、简化首次使用流程 |
| **留存实验** | 提升重复使用率 | 功能提醒、使用习惯培养、新 use case |
| **转化实验** | 提升付费转化 | 付费墙位置、试用期设计、价值展示 |
| **传播实验** | 提升病毒传播 | 邀请机制、协作功能、分享产出物 |

### 实验流程

1. **假设提出** — 基于数据洞察或用户反馈，提出可验证的假设
   ```
   假设：把功能入口从二级页移到一级导航，可以提升点击率 30%
   ```
2. **实验设计** — 确定对照组、指标、样本量、实验周期
3. **开发上线** — A/B 测试框架配置，埋点确认
4. **数据收集** — 等样本量达标，不要中途看数据下结论
5. **结果分析** — 统计显著性检验（p < 0.05）
6. **决策执行** — 全量胜出版本 / 放弃 / 继续实验

### 实验记录模板

| 字段 | 内容 |
|---|---|
| 实验 ID | EXP-2026-Q3-001 |
| 假设 | 简化注册流程可以提升激活率 20% |
| 类型 | 激活实验 |
| 指标 | 注册完成率、次日留存率 |
| 样本量 | 每组 5000 用户 |
| 周期 | 2 周 |
| 结果 | 激活率 +18% (p<0.01)，次日留存 +5% (p=0.07) |
| 决策 | 全量上线 |
| Owner | 张三 |

## 常见陷阱

| 陷阱 | 表现 | 规避方法 |
|---|---|---|
| 功能建好了没人用 | 花了 3 个月做的功能，使用率 5% | 先做 MVP 验证，别一上来就做完整版 |
| 没有数据就决策 | 拍脑袋决定做什么、怎么优化 | 每个功能上线前必须埋点，数据驱动决策 |
| 实验太多太乱 | 同时跑 10 个实验，结果互相干扰 | 同一用户同一时段最多 2-3 个实验，注意正交 |
| 过早优化 | 功能还没验证价值就开始抠转化率 | 先验证 "有人用"，再优化 "用得多" |
| 忽略定性反馈 | 只看数据，不理解用户为什么用/不用 | 每阶段至少做 10 次用户访谈 |
| Beta 无限期 | Beta 做了半年还不 GA | 设定明确的通过标准和时间上限，不达标就砍 |
