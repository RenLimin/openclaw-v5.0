# 数据安全与隐私保护 SOP

## 适用场景

- SaaS 产品的数据全生命周期安全管理
- 个人信息保护与合规（GDPR、个人信息保护法）
- 数据分类分级、加密、脱敏
- 数据泄露应急响应

---

## 核心原则

1. **数据是客户的** — 我们只是托管者，不是所有者
2. **最小化收集** — 只收必须的，不要什么数据都要
3. **全生命周期保护** — 从产生到销毁，每一步都有安全措施
4. **默认安全** — 新功能默认用最安全的方式，不把安全当可选配置
5. **透明** — 告诉客户我们收集了什么、用来干嘛、存在哪

---

## 数据分类分级

### 数据分级

按敏感程度分成 4 级：

| 级别 | 名称 | 定义 | 示例 |
|---|---|---|---|
| **L4 — 极敏感** | 核心机密 | 泄露会造成严重损害，违法 | 密码、密钥、信用卡号 |
| **L3 — 敏感** | 个人敏感信息 | 泄露会对个人造成重大影响 | 身份证号、手机号、健康数据、财务数据 |
| **L2 — 内部** | 业务数据 | 公司内部使用，不能公开 | 客户名单、业务数据、内部文档 |
| **L1 — 公开** | 公开信息 | 可以对外公开 | 产品文档、营销材料 |

### 分级保护要求

| 措施 | L1 公开 | L2 内部 | L3 敏感 | L4 极敏感 |
|---|---|---|---|---|
| 传输加密（TLS） | ✅ | ✅ | ✅ | ✅ |
| 存储加密 | ❌ | ✅ | ✅ | ✅ |
| 字段级加密 | ❌ | ❌ | ✅（部分） | ✅ |
| 访问审计 | ❌ | ✅ | ✅ | ✅ |
| 脱敏展示 | ❌ | 按需 | ✅ | ✅ |
| 备份加密 | ❌ | ✅ | ✅ | ✅ |
| 数据留存期限 | - | 按业务需要 | 按合规要求 | 最短期限 |

## 数据生命周期管理

### 六阶段

```
1. 收集 → 2. 存储 → 3. 使用 → 4. 传输 → 5. 共享 → 6. 销毁
```

### 1. 数据收集

**原则：最小化、合法、透明**

- 只收集完成功能所必需的数据
- 有明确的收集目的
- 告知用户收集了什么、用来干嘛
- 取得用户同意（需要同意的场景）
- 不收集与业务无关的敏感数据

**反模式：** "先收了再说，以后可能用得上" → ❌

### 2. 数据存储

**加密策略：**

| 层级 | 措施 | 说明 |
|---|---|---|
| 传输层 | TLS 1.2+ | 所有 API、网页、内部通信 |
| 存储层 | 磁盘加密 / TDE | 云盘加密、数据库透明加密 |
| 字段级 | 敏感字段单独加密 | 手机号、身份证、密码等 |
| 备份 | 加密存储 | 备份文件加密 |

**密码存储：**
- 永远不要明文存密码
- 使用 bcrypt / Argon2 / scrypt 等慢哈希算法
- 加盐（salt），每个密码盐不同
- 不要自己造加密算法

### 3. 数据使用

**访问控制：**
- 最小权限原则 — 只给完成工作需要的最小权限
- 按角色授权（RBAC）
- 敏感数据访问单独审批
- 特权操作（导出、批量删除）二次验证

**数据脱敏：**
- 展示时脱敏（手机号 138****1234）
- 测试环境用脱敏数据（不用生产数据）
- 日志中脱敏（不打密码、token、完整手机号）
- 第三方分析用匿名化数据

### 4. 数据传输

- 所有外部通信强制 HTTPS
- 内部服务间通信也用 TLS（零信任）
- 密钥和敏感配置不走代码仓库，用密钥管理服务
- 文件传输用加密通道（SFTP / HTTPS，不用 FTP）

### 5. 数据共享

**与第三方共享数据前必须：**
1. 评估第三方安全性
2. 签署数据处理协议（DPA）
3. 最小化共享（只给需要的数据）
4. 用户同意（法律要求时）
5. 记录共享日志

**客户数据永远不能：**
- 卖给第三方
- 用于自己的广告投放
- 未经同意用于其他目的

### 6. 数据销毁

**什么时候销毁：**
- 客户注销账号后（保留期满）
- 数据超出留存期限
- 客户要求删除（被遗忘权）

**销毁方式：**

| 介质 | 销毁方式 |
|---|---|
| 硬盘 | 消磁 / 物理粉碎 / 多次覆写 |
| SSD | 安全擦除命令（ATA Secure Erase） |
| 云存储 | 删除 + 覆写（或依赖云厂商的机制） |
| 数据库 | 物理删除（不是软删除） |
| 备份 | 按备份策略轮转删除 |

**销毁后验证：** 确认数据确实被删了，不是还躺在某个地方。

## 个人信息保护（GDPR / 个保法）

### 数据主体权利支持

SaaS 产品需要支持用户行使自己的权利：

| 权利 | 实现方式 | SLA |
|---|---|---|
| **知情权** | 隐私政策（Privacy Policy） | - |
| **访问权** | 用户可导出自己的个人数据 | 30 天内 |
| **更正权** | 用户可修改自己的个人信息 | 实时 |
| **删除权（被遗忘权）** | 账号注销 + 数据删除 | 30 天内 |
| **限制处理权** | 暂停使用用户数据 | 30 天内 |
| **可携权** | 导出为通用格式（JSON / CSV） | 30 天内 |
| **反对权** | 用户可反对营销等用途 | 实时 |

### 隐私政策（Privacy Policy）

必须清楚说明：
- 收集哪些数据
- 收集的目的
- 数据存放在哪
- 数据保存多久
- 跟谁共享数据
- 用户的权利
- 如何联系我们

隐私政策不是摆设，是法律文件。要找律师审核。

## 数据泄露应急响应

### 什么是数据泄露

未经授权的访问、获取、修改、泄露、破坏数据的事件。

### 分级

| 级别 | 定义 | 通知要求 |
|---|---|---|
| **重大** | 大量用户敏感数据泄露（>1000 人） | 72 小时内通知监管 + 用户 |
| **较大** | 少量敏感数据泄露（<1000 人） | 通知用户 + 记录 |
| **一般** | 非敏感数据泄露 | 内部处理 + 记录 |
| **轻微** | 影响极小的信息泄露 | 记录 |

### 响应流程

```
发现 → 启动响应 → 遏制（止损）→ 评估影响 → 通知 → 修复 → 复盘
```

**通知时限（GDPR）：** 数据泄露后 **72 小时内** 通知监管机构。如果高风险，还要通知受影响的个人。

## 密钥管理

### 密钥管理原则

1. **密钥和数据分开存** — 不要把加密密钥和加密的数据放一起
2. **专人管理** — 不是所有人都能看密钥
3. **定期轮换** — 密钥定期更换
4. **可审计** — 谁什么时候用了密钥有记录
5. **备份密钥** — 密钥丢了数据也没了，但要安全备份

### 密钥管理服务（KMS）

用云厂商的 KMS 或自建：
- AWS KMS / 阿里云 KMS / 腾讯云 KMS
- HashiCorp Vault
- 自建 HSM（硬件安全模块）

**密钥分级：**
- 主密钥（Master Key）：加密密钥的密钥，最高保护
- 数据密钥（Data Key）：加密实际数据，用主密钥加密
- 定期轮换数据密钥，主密钥更谨慎轮换

## 常见陷阱

| 陷阱 | 表现 | 规避方法 |
|---|---|---|
| 数据能拿就拿 | 什么数据都收集，存着再说 | 数据最小化原则，只收必须的 |
| 明文存密码 | 数据库里密码是明文的 → 致命错误 | bcrypt / Argon2 哈希，加盐 |
| 测试用生产数据 | 测试环境直接拷贝生产数据 | 测试用脱敏 / 模拟数据 |
| 日志里打敏感数据 | 日志里有密码、token、手机号 | 日志脱敏，敏感字段不打日志 |
| 密钥放代码里 | Git 仓库里有 API Key、数据库密码 | 密钥管理服务 + CI 环境变量 + Secret 扫描 |
| 删除=软删除 | 客户删了账号数据还在数据库里 | 软删除 + 保留期 + 到期物理删除 |
| 不做数据分类 | 所有数据一样对待，要么都不保护要么都过度保护 | 数据分类分级，不同级别不同保护措施 |
| 隐私政策摆设 | 抄了一份隐私政策放那，实际做法不一致 | 政策要真实反映做法，定期更新 |
