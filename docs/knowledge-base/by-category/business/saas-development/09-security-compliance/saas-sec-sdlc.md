# 安全开发生命周期（SDL）SOP

## 适用场景

- SaaS 产品的安全开发生命周期建设
- DevSecOps 实践落地
- 安全需求、设计、编码、测试、部署全流程
- 开发团队的安全能力建设

---

## 核心原则

1. **安全左移** — 越早发现安全问题，修复成本越低
2. **开发者是第一道防线** — 不是安全团队盯着，是开发者自己就写出安全的代码
3. **自动化优先** — 安全检查融入流水线，不需要人记得做
4. **安全是每个人的事** — 不是安全团队的事，是所有人的事
5. **不拖慢开发** — 安全是加速器不是绊脚石，自动化 + 精准告警

---

## 什么是 SDL

SDL = Security Development Lifecycle，安全开发生命周期。

把安全考虑融入软件开发的每个阶段：需求 → 设计 → 开发 → 测试 → 部署 → 运维。

### 传统安全 vs SDL

| 传统安全 | SDL |
|---|---|
| 开发完了再测安全 | 每个阶段都考虑安全 |
| 安全团队负责 | 所有人负责 |
| 最后才发现一堆问题 | 边做边发现，成本低 |
| 安全和开发对立 | 安全融入开发流程 |

## SDL 各阶段实践

### 阶段 1：需求分析

**安全活动：**

| 活动 | 说明 |
|---|---|
| **安全需求识别** | 这个功能有什么安全风险？需要什么安全控制？ |
| **数据分类** | 涉及什么级别的数据？L2 / L3 / L4？ |
| **合规要求** | 有没有合规要求？（GDPR / 等保 / HIPAA） |
| **威胁建模准备** | 高风险功能需要做威胁建模 |

**安全需求示例：**
- 用户输入必须校验
- 敏感数据必须加密存储
- 必须有访问控制
- 操作必须有审计日志
- 必须防 CSRF / XSS / SQL 注入

### 阶段 2：设计阶段

**安全活动：**

| 活动 | 说明 |
|---|---|
| **威胁建模** | 系统地识别威胁和风险 |
| **安全设计评审** | 架构设计中的安全考量 |
| **隐私设计（Privacy by Design）** | 隐私保护从设计阶段就考虑 |

#### 威胁建模（Threat Modeling）

**STRIDE 模型：**

| 威胁 | 说明 | 对应的安全属性 |
|---|---|---|
| **S — Spoofing（伪造）** | 冒充他人身份 | 认证 |
| **T — Tampering（篡改）** | 修改数据或代码 | 完整性 |
| **R — Repudiation（抵赖）** | 做了坏事不认账 | 不可否认性 |
| **I — Information Disclosure（信息泄露）** | 不该看的看到了 | 保密性 |
| **D — Denial of Service（拒绝服务）** | 让系统用不了 | 可用性 |
| **E — Elevation of Privilege（提权）** | 普通用户变管理员 | 授权 |

**威胁建模步骤：**
1. 画数据流图（DFD）
2. 识别每个元素的威胁（用 STRIDE）
3. 评估风险等级
4. 设计缓解措施
5. 验证缓解措施是否有效

**什么时候做威胁建模：**
- 新的核心功能
- 涉及多租户隔离的
- 涉及支付 / 敏感数据的
- 架构重大变更
- 不是每个小功能都做，投入产出比要考虑

### 阶段 3：开发阶段

**安全活动：**

| 活动 | 说明 |
|---|---|
| **安全编码规范** | 团队遵守统一的安全编码标准 |
| **静态代码扫描（SAST）** | CI 中自动扫描 |
| **依赖安全扫描** | 第三方依赖漏洞检测 |
| **Secret 扫描** | 防止密钥提交到代码库 |
| **Code Review 安全检查清单** | CR 时关注安全点 |

#### 安全编码规范要点

**输入验证：**
- 所有输入都是不可信的
- 白名单校验（只允许什么），不是黑名单
- 类型、长度、格式、范围都校验

**输出编码：**
- 输出到 HTML → HTML 转义（防 XSS）
- 输出到 JavaScript → JS 编码
- 输出到 SQL → 参数化查询（防 SQL 注入）

**认证与会话管理：**
- 密码用强哈希（bcrypt / Argon2）
- Session ID 足够随机，长度足够
- 超时自动失效
- 敏感操作二次验证

**访问控制：**
- 默认拒绝
- 最小权限
- 每次访问都验证（不要只在前端检查）
- IDOR 防护（水平越权）

**错误处理：**
- 不要把详细错误信息返回给用户
- 生产环境不显示堆栈跟踪
- 错误日志要详细，但用户只看到通用错误

### 阶段 4：测试阶段

**安全活动：**

| 活动 | 说明 |
|---|---|
| **动态扫描（DAST）** | 运行时扫描应用漏洞 |
| **安全测试用例** | 功能测试包含安全场景 |
| **渗透测试** | 季度 / 年度 |
| **模糊测试（Fuzzing）** | 随机输入找崩溃和漏洞 |

**安全测试用例应该覆盖：**
- 认证绕过
- 越权访问（水平 + 垂直）
- SQL 注入
- XSS
- CSRF
- 文件上传漏洞
- 业务逻辑漏洞

### 阶段 5：部署阶段

**安全活动：**

| 活动 | 说明 |
|---|---|
| **容器镜像扫描** | 部署前扫镜像漏洞 |
| **基础设施即代码扫描** | Terraform 等配置的安全检查 |
| **部署权限最小化** | 部署账号最小权限 |
| **灰度发布** | 出问题影响小 |
| **快速回滚** | 发现安全问题能马上回退 |

### 阶段 6：运维阶段

**安全活动：**

| 活动 | 说明 |
|---|---|
| **安全监控** | 安全事件实时监控 |
| **漏洞管理** | 新漏洞及时修复 |
| **日志审计** | 安全日志分析 |
| **应急响应** | 安全事件快速响应 |
| **定期安全评估** | 定期检查安全状态 |

## DevSecOps 工具链

### CI/CD 中的安全检查

```
代码提交
   ↓
🔍 Secret 扫描（10s）
   ↓
🔍 SAST 静态扫描（1-2min）
   ↓
🔍 依赖漏洞扫描（30s）
   ↓
构建
   ↓
🔍 容器镜像扫描（1-2min）
   ↓
部署到测试环境
   ↓
🔍 DAST 动态扫描（10-30min）
   ↓
生产部署
```

**原则：快的放前面，慢的放后面。前面发现了就不用跑后面了。**

### 工具清单

| 类别 | 开源工具 | 商业工具 |
|---|---|---|
| SAST | SonarQube、Semgrep、CodeQL | Snyk Code、Checkmarx |
| SCA（依赖） | OWASP Dependency-Check、Dependabot | Snyk、WhiteSource |
| DAST | OWASP ZAP | Burp Suite、Acunetix |
| Secret 扫描 | gitleaks、truffleHog | GitGuardian |
| 容器扫描 | Trivy、Clair | Aqua、Twistlock |
| IaC 扫描 | Checkov、tfsec | Bridgecrew |

## 安全文化建设

### 培训

- **新员工安全培训** — 入职必学
- **年度安全意识培训** — 所有人
- **开发团队安全编码培训** — 技术团队
- **钓鱼演练** — 定期发钓鱼邮件测警惕性
- **安全分享会** — 每月 / 季度安全主题分享

### 激励

- 发现漏洞有奖励（内部 Bug Bounty）
- 安全做得好的团队表扬
- 安全 KPI 纳入绩效考核（但不要只看数量）

### 责任

- 安全是每个人的责任
- 业务负责人对产品安全负责
- 开发团队对代码安全负责
- 安全团队负责指导、支持、监督

## 安全度量

### 过程指标

| 指标 | 说明 |
|---|---|
| 安全需求覆盖率 | 需求中有安全考虑的比例 |
| 高风险功能威胁建模覆盖率 | 做了威胁建模的比例 |
| SAST / DAST 扫描覆盖率 | 被扫描的代码 / 功能比例 |
| 安全培训完成率 | 完成培训的员工比例 |

### 结果指标

| 指标 | 说明 |
|---|---|
| 高危漏洞数量 | 生产环境发现的高危漏洞 |
| 平均修复时间 | 漏洞从发现到修复的时间 |
| 漏洞复发率 | 修过的漏洞又出现的比例 |
| 安全事件数量 | 发生了多少次安全事件 |
| 安全事件 MTTR | 安全事件平均恢复时间 |

## 常见陷阱

| 陷阱 | 表现 | 规避方法 |
|---|---|---|
| 安全是安全团队的事 | 开发觉得安全是别人的事 | 安全左移，开发团队负责自己代码的安全 |
| 工具堆成山 | 上了 10 个安全工具，没人看结果 | 选 2-3 个关键的，用好，有结果追踪 |
| 什么都阻断 | CI 里什么漏洞都不让过，开发效率极低 | 只阻断高危，中低危可以先过，限期修 |
| 只看工具不看人 | 全靠扫描器，逻辑漏洞一个查不出来 | 工具 + 人工，威胁建模 + Code Review |
| 形式主义 | 走个过场，该怎么开发还怎么开发 | 要有实际效果，不要为了合规而做 |
| 安全拖慢进度 | 安全检查要等很久，发布延迟 | 自动化、并行化，减少人工卡点 |
| 培训没用 | 培训完就忘，没有实践 | 培训 + 实操 + 定期演练，才有用 |
