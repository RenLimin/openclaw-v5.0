# 多租户隔离模型选型与设计 SOP

## 适用场景

- SaaS 产品多租户架构选型
- 从单租户向多租户演进的架构规划
- 不同隔离模型的技术评估与决策
- 混合隔离策略的设计与落地

---

## 核心原则

1. **隔离是 SaaS 的生命线** — 任何设计都不能突破租户数据隔离边界
2. **业务决定模型** — 没有最好的模型，只有最适合业务的模型
3. **可演进** — 架构不是一成不变的，设计时要考虑未来 2-3 年的演进路径
4. **安全默认** — 隔离策略默认取最高安全级别，业务需要时再降级
5. **可审计** — 每一次跨租户操作都要有日志、可追溯

---

## 三种隔离模型对比

### 模型总览

| 维度 | Silo（独立部署） | Pool（共享资源池） | Hybrid（混合模式） |
|---|---|---|---|
| **部署模式** | 每个租户独立实例 + 独立数据库 | 所有租户共享一套实例和数据库 | 核心共享 + 关键租户独立 |
| **隔离级别** | 物理隔离 | 逻辑隔离 | 混合隔离 |
| **资源利用率** | 低（每个租户一套资源） | 高（资源池化复用） | 中高 |
| **运维复杂度** | 高（N 个实例管理） | 低（一套实例） | 中 |
| **成本** | 高（小租户不划算） | 低（边际成本递减） | 中 |
| **定制化能力** | 强（每个租户可独立改） | 弱（统一版本） | 中 |
| **数据安全** | 最高（物理隔离） | 依赖逻辑隔离保证 | 分层隔离 |
| **适合规模** | 大客户 / 合规要求高的行业 | 中小客户 / 标准化产品 | 混合客户群体 |
| **故障爆炸半径** | 单租户 | 可能影响全部 | 按层级区分 |

### Silo 模型（独立部署）

**架构示意：**
```
客户 A → 独立应用实例 → 独立数据库
客户 B → 独立应用实例 → 独立数据库
客户 C → 独立应用实例 → 独立数据库
```

**适用场景：**
- 金融、医疗、政府等强监管行业
- ARR > 50 万的大客户（值得单独部署）
- 有数据本地化要求（数据必须留在特定地区）
- 需要深度定制化的客户

**优势：**
- 物理隔离，数据安全性最高
- 性能完全独立，不受其他租户影响
- 可独立升级/回滚，不影响其他客户
- 故障影响范围仅限单租户

**劣势：**
- 运维成本高，租户多了管理不过来
- 资源利用率低，小客户成本不划算
- 版本碎片化，维护多版本成本高
- 扩容速度慢（需要新部署一套）

### Pool 模型（共享资源池）

**架构示意：**
```
客户 A ─┐
客户 B ─┼→ 共享应用集群 → 共享数据库（tenant_id 逻辑隔离）
客户 C ─┘
```

**适用场景：**
- PLG 模式、大量中小客户
- 产品高度标准化，定制化需求少
- 成本敏感，追求边际成本递减
- 快速迭代，统一版本发布

**优势：**
- 资源利用率高，成本最优
- 运维简单，一套系统管所有租户
- 版本统一，发布效率高
- 扩容灵活，按需增加节点

**劣势：**
- 逻辑隔离，一旦有 bug 可能跨租户泄露
- 性能互相影响（noisy neighbor 问题）
- 大客户定制需求难满足
- 数据库量大后性能优化挑战大

### Hybrid 模型（混合模式）

**常见混合策略：**

| 策略 | 说明 | 适用场景 |
|---|---|---|
| **按客户分层** | 大客户 Silo，中小客户 Pool | 客户分层明显，有头部大客户 |
| **按功能分层** | 核心数据 Silo，非核心功能 Pool | 部分功能数据敏感度高 |
| **按地域分层** | 不同地区独立部署 | 有数据主权 / 本地化要求 |

**推荐架构（按客户分层）：**
```
大客户 A → 独立实例 → 独立数据库    (Silo 层)
大客户 B → 独立实例 → 独立数据库    (Silo 层)
  ...
中小客户 → 共享集群 → 共享数据库    (Pool 层)
```

## 选型决策框架

### 决策矩阵

**评分标准：** 1-5 分，5 分表示该模型在此维度上最好

| 评估维度 | 权重 | Silo 得分 | Pool 得分 | Hybrid 得分 |
|---|---|---|---|---|
| 数据安全要求 | 高 | 5 | 2 | 4 |
| 客户规模（数量） | 高 | 1 | 5 | 3 |
| 客户价值（ARR） | 高 | 5 | 2 | 4 |
| 定制化需求 | 中 | 5 | 1 | 3 |
| 运维团队规模 | 中 | 1 | 5 | 3 |
| 成本敏感度 | 中 | 1 | 5 | 3 |
| 迭代速度要求 | 中 | 2 | 5 | 3 |
| 行业合规要求 | 高 | 5 | 2 | 4 |

**决策建议：**
- Silo 加权分最高 → 选 Silo
- Pool 加权分最高 → 选 Pool
- 差距不大 → 选 Hybrid，从 Pool 起步，大客户逐步 Silo

### 典型场景推荐

| 业务场景 | 推荐模型 | 理由 |
|---|---|---|
| 小微企业 SaaS，客单价 < $50/月 | Pool | 成本优先，大量小客户 |
| 中大型企业 SaaS，客单价 $500-5000/月 | Hybrid | 头部客户独立，腰部以下共享 |
| 金融/医疗 SaaS，合规要求高 | Silo + Hybrid | 核心数据 Silo，可共享的部分 Pool |
| 政府项目，本地化部署 | Silo | 物理隔离是硬性要求 |
| PLG 产品，免费 + 付费模式 | Pool → Hybrid | 初期 Pool 降本，做大后大客户 Silo |

## Pool 模型隔离设计要点

### 应用层隔离

**必须遵守的铁律：**
- 所有数据库查询必须带 `tenant_id` 条件
- 禁止使用不带 `tenant_id` 的全局查询（除非是运维操作且有审计）
- 缓存 key 必须包含 `tenant_id` 前缀
- 消息队列消息必须带 `tenant_id` 上下文
- 文件存储路径必须包含 `tenant_id`

**代码层面保障：**
```
// ❌ 禁止：直接查所有数据
List<Order> orders = orderMapper.selectAll();

// ✅ 必须：自动注入 tenant_id
List<Order> orders = orderMapper.selectByTenant(currentTenantId);
```

**推荐实现方式：**
- ORM 层拦截器 / 多租户插件（如 MyBatis-Plus 多租户插件）
- AOP 切面自动注入 tenant_id
- 静态代码扫描检查遗漏 tenant_id 的查询

### 数据库层隔离

| 隔离方式 | 实现 | 隔离强度 | 性能影响 | 运维复杂度 |
|---|---|---|---|---|
| **共享数据库 + 共享表** | 表中加 tenant_id 字段 | 弱（逻辑隔离） | 无 | 低 |
| **共享数据库 + Schema 隔离** | 每个租户独立 schema | 中 | 小 | 中 |
| **独立数据库** | 每个租户独立数据库 | 强（接近物理） | 连接池开销 | 高 |

**推荐：** 共享数据库 + 共享表 + 行级安全（RLS）

> PostgreSQL 支持行级安全策略（Row Level Security），可在数据库层面强制租户隔离，即使应用层漏了 tenant_id 也查不到其他租户数据。

### 网络与基础设施隔离

- 不同租户的流量共用同一个入口（API Gateway）
- 但管理后台 / 运维工具要有严格的权限控制
- 日志系统中所有日志必须带 `tenant_id` 标签

## 演进路径建议

### 路径一：从 Pool 到 Hybrid（最常见）

```
阶段 1：MVP 阶段
  → 纯 Pool，快速验证产品
  → 只有一个数据库，所有租户共享

阶段 2：客户增长阶段
  → 大客户出现，开始有定制需求
  → 引入租户分层概念
  → 为 Top 5 客户单独部署实例

阶段 3：规模化阶段
  → 正式 Hybrid 架构
  → 自动化部署工具支持一键 Silo
  → 统一控制面管理所有租户
```

### 路径二：从 Silo 到 Hybrid（企业级起步）

```
阶段 1：大客户定制
  → 每个项目独立部署
  → 像项目制，不像 SaaS

阶段 2：标准化
  → 抽象公共模块，统一代码库
  → 用 feature flag 控制差异
  → 运维工具化、自动化

阶段 3：混合架构
  → 中小客户走 Pool 模式
  → 大客户保留 Silo
  → 共用一套发布和监控体系
```

## 常见陷阱

| 陷阱 | 表现 | 规避方法 |
|---|---|---|
| 过早优化 | 10 个客户就搞 Hybrid，复杂度远超业务需要 | 先 Pool 跑通，到 100 个付费客户再考虑分层 |
| 隔离靠自觉 | 代码里全靠工程师记得加 tenant_id | 框架层强制 + 静态扫描 + RLS 兜底 |
| Silo 失控 | 每个客户一套代码，最后变成 N 个产品 | 统一代码库 + feature flag + 自动化测试矩阵 |
| Noisy Neighbor | 一个大客户把数据库打满，所有人卡 | 租户级限流 + 资源配额 + 读写分离 |
| 缓存串数据 | 缓存 key 忘记加 tenant_id，A 看到 B 的数据 | 缓存框架自动注入租户前缀 + 集成测试验证 |
| 迁移困难 | Pool 客户做大了想迁移到 Silo，迁不动 | 设计时就考虑租户迁移路径，提前做工具 |
