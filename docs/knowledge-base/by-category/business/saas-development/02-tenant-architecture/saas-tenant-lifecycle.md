# 租户生命周期管理 SOP

## 适用场景

- SaaS 租户从注册到注销的全生命周期管理
- 租户状态变更的标准化流程
- 租户数据的创建、保留、销毁策略
- 跨团队（产品/研发/客户成功/财务）协同

---

## 核心原则

1. **状态机驱动** — 租户状态变迁必须是确定性的状态机，不能是模糊的标记
2. **数据可追溯** — 每次状态变更都有日志、有操作人、有时间
3. **软删除优先** — 租户注销后先软删除，保留一段时间再彻底清除
4. **隔离不可逆** — 一旦租户数据销毁，不可恢复（除非有备份）
5. **合规对齐** — 数据保留和销毁策略需符合 GDPR、等保等合规要求

---

## 租户状态机

### 状态定义

| 状态 | 说明 | 可登录 | 数据可访问 | 计费 |
|---|---|---|---|---|
| **pending** | 已注册但未激活（邮箱未验证等） | 否 | 否 | 否 |
| **active** | 正常活跃 | 是 | 是 | 是（付费租户） |
| **trial** | 试用期 | 是（有限制） | 是 | 否 |
| **suspended** | 暂停（欠费/违规） | 否（或只读） | 是（只读） | 否 |
| **grace** | 宽限期（即将到期/欠费初期） | 是 | 是 | 是（计费继续） |
| **archived** | 已归档（租户主动注销） | 否 | 否（仅管理员可导出） | 否 |
| **deleted** | 已彻底删除 | 否 | 否 | 否 |

### 状态流转图

```
注册 → pending → 验证 → trial → 付费 → active
                ↓                    ↓
              验证失败              欠费
                ↓                    ↓
             deleted               grace
                                     ↓
                            补缴 ← active  逾期 → suspended
                                           ↓
                                      30 天不续费 → archived
                                           ↓
                                    保留期后 → deleted
```

### 状态变更触发条件

| 起始状态 | 目标状态 | 触发条件 | 触发方 |
|---|---|---|---|
| pending | trial | 邮箱验证通过 / 首次登录 | 系统自动 |
| pending | deleted | 7 天未验证 | 系统自动（定时任务） |
| trial | active | 付费成功 | 系统自动 |
| trial | archived | 试用结束 30 天未付费 | 系统自动 |
| active | grace | 订阅到期前 7 天 | 系统自动 |
| grace | active | 续费成功 | 系统自动 |
| grace | suspended | 到期未续费（宽限期 15 天） | 系统自动 |
| active | suspended | 违规 / 风控触发 | 人工（运营/安全） |
| suspended | active | 补缴 / 申诉通过 | 人工 + 系统 |
| suspended | archived | 暂停 30 天未恢复 | 系统自动 |
| * | archived | 租户主动注销 | 租户（需管理员确认） |
| archived | deleted | 归档 90 天后自动清除 | 系统自动 |

## 各阶段详细操作

### 1. 租户创建（Provisioning）

**自动创建流程：**
1. 用户注册 → 创建租户记录（status: pending）
2. 分配租户 ID（全局唯一，UUID 或雪花 ID）
3. 创建默认管理员账号
4. 初始化租户配置（默认套餐、默认设置）
5. 分配数据库资源（Pool 模式：创建租户行；Silo 模式：创建数据库）
6. 初始化示例数据（可选）
7. 发送验证邮件
8. 用户验证 → status: trial / active

**创建时必须完成的检查：**
- [ ] 租户名称唯一性校验
- [ ] 管理员邮箱有效性验证
- [ ] 数据隔离配置正确（tenant_id 注入验证）
- [ ] 初始配额设置正确（按套餐）
- [ ] 审计日志已开启
- [ ] 监控指标已注册

### 2. 活跃期管理

**租户配置项：**
- 套餐信息（plan_id, 功能开关, 资源配额）
- 基本信息（名称, 行业, 规模, 联系人）
- 安全设置（密码策略, SSO 配置, IP 白名单）
- 计费信息（发票抬头, 联系人, 支付方式）
- 定制化配置（CSS, 域名, 功能 flag）

**日常变更流程：**
- 套餐升降级 → 见计费模块
- 功能开关变更 → 运营后台操作 + 审计日志
- 数据配额调整 → 需审批 + 操作记录
- 租户转让 → 严格身份验证 + 双方确认

### 3. 暂停与恢复

**自动暂停触发场景：**
- 订阅逾期 15 天未续费
- 信用卡扣费连续失败 3 次
- 检测到严重违规行为
- 安全事件（数据泄露风险等）

**暂停操作内容：**
1. 租户状态改为 suspended
2. 登录页提示暂停原因和恢复方式
3. API 请求返回 402 / 403（带错误码和说明）
4. 后台任务暂停执行
5. 通知客户成功和财务团队

**恢复流程：**
1. 补缴费用 / 申诉通过
2. 状态改回 active
3. 恢复所有服务
4. 发送恢复确认通知
5. 客户成功跟进

### 4. 租户注销（Offboarding）

**触发方式：**
- 租户主动发起（管理员操作注销）
- 长期不活跃自动注销（试用期 90 天未登录 + 无付费记录）
- 违规强制注销

**主动注销流程：**
1. 管理员在设置中点击"注销账号"
2. 系统提示后果（数据将被删除，不可恢复）
3. **二次确认**：输入租户名称 + 手机验证码 / 邮箱验证码
4. 状态改为 archived
5. 系统自动发送确认邮件
6. **7 天反悔期**：期间管理员可登录恢复
7. 7 天后进入数据保留期（90 天，仅管理员可导出）
8. 90 天后彻底删除数据

**注销时必须做的清理：**
- [ ] 停止所有计费
- [ ] 回收 API Key / Token
- [ ] 取消所有定时任务
- [ ] 通知所有关联用户（邮件）
- [ ] 备份最终数据（归档到冷存储）
- [ ] 更新 CRM / 财务系统状态
- [ ] 客户成功团队记录流失原因

### 5. 数据销毁

**销毁范围：**
- 数据库中所有租户业务数据
- 对象存储中的文件
- 缓存中的数据
- 搜索引擎索引
- 日志（归档后保留，不销毁）
- 备份（按备份策略保留，到期后销毁）

**销毁验证：**
- 销毁后执行数据完整性检查（反向验证 — 确认查不到任何数据）
- 生成销毁报告（操作人、时间、销毁范围、验证结果）
- 符合合规要求的，出具数据销毁证明

## 数据保留策略

| 数据类型 | 保留时长 | 销毁方式 | 合规依据 |
|---|---|---|---|
| 业务数据（租户删除后） | 90 天 | 物理删除 | 企业内部策略 |
| 用户账号数据 | 删除后 30 天 | 物理删除 | GDPR 被遗忘权 |
| 审计日志 | 1 年 | 归档后逐步删除 | 等保 2.0 |
| 操作日志 | 6 个月 | 自动过期 | 内部策略 |
| 计费发票数据 | 10 年 | 永久保留（财务要求） | 会计法 / 税法 |
| 备份数据 | 3 个月 | 轮转覆盖 | 内部策略 |

## 常见陷阱

| 陷阱 | 表现 | 规避方法 |
|---|---|---|
| 删除即销毁 | 用户点了删除就立刻删数据，误删无法恢复 | 软删除 + 反悔期 + 定时销毁 |
| 清理不彻底 | 租户删了，但缓存、搜索索引里还留着数据 | 注销时运行完整清理脚本，覆盖所有数据存储 |
| 状态混乱 | 同时有多个字段标记状态，逻辑不清 | 单一状态机字段，明确的流转规则 |
| 没有审计 | 谁改了租户状态没人知道 | 所有状态变更必须写审计日志 |
| 注销流程复杂 | 用户想注销找不到入口，要联系客服 | 设置里明确的注销按钮 + 清晰的流程指引 |
| 备份忘记删 | 租户数据删了，但备份里还存着 | 备份策略纳入数据生命周期管理，定期清理 |
