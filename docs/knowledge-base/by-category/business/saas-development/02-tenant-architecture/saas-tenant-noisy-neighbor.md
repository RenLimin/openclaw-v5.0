# 多租户性能噪声（Noisy Neighbor）治理 SOP

## 适用场景

- Pool 模式下多租户共享资源的性能隔离
- 单个大租户消耗过多资源影响其他租户的治理
- 租户级限流、配额、资源隔离策略的设计与落地
- 性能问题排查中的租户维度定位

---

## 核心原则

1. **公平优先于极致** — 资源不够时大家都慢点，不能某个人快其他人卡死
2. **多级限流** — 从入口到数据库，每一层都有防护，一层漏了下一层兜
3. **可观测** — 每个租户用了多少资源，必须能精确度量
4. **差异化服务** — 大客户有更高配额，但不能无限占用
5. **提前预防 > 事后救火** — 常态化监控 + 自动限流，不要等出了故障再处理

---

## 什么是 Noisy Neighbor 问题

**定义：** 共享资源池中，某个租户（通常是大客户或异常流量）消耗了不成比例的资源，导致其他租户的性能下降。

**典型表现：**
- 数据库 CPU 突然飙升，排查发现是某个租户的批量操作
- 一个租户的爬虫把 API 网关打满，其他人请求超时
- 消息队列被某个租户的大任务占满，其他租户的任务排队
- 缓存被某个租户的大量 key 占满，其他租户缓存命中率下降

**影响范围：**

| 资源层 | 受影响程度 | 典型场景 |
|---|---|---|
| API 网关 | 中高 | 突发流量、爬虫、攻击 |
| 应用服务 | 中 | 重计算操作、批量任务 |
| 缓存（Redis） | 中高 | 大 key、热 key、缓存穿透 |
| 数据库 | 高 | 慢 SQL、大批量写入、表扫描 |
| 对象存储 | 低 | 大文件上传下载 |
| 消息队列 | 中高 | 单租户大量消息挤占消费能力 |

## 四层限流防护体系

### 第一层：API 网关限流

**目标：** 在入口处挡住异常流量，保护后端服务

**限流策略：**

| 维度 | 限流方式 | 默认阈值（示例） | 说明 |
|---|---|---|---|
| 租户级 QPS | 令牌桶 | 基础版 100/s，专业版 500/s，企业版 2000/s | 按套餐动态调整 |
| 用户级 QPS | 令牌桶 | 20/s | 防止单个账号异常 |
| IP 级 QPS | 漏桶 | 100/s | 防爬虫和攻击 |
| 全局 QPS | — | 集群总容量 80% | 兜底保护 |

**实现：**
- Nginx / Kong / APISIX 的限流插件
- 基于 Redis 的分布式限流（多实例共享计数）
- 限流后返回 429 Too Many Requests + Retry-After 头

### 第二层：应用服务隔离

**目标：** 单个租户的重操作不影响其他租户的请求处理

**策略：**

**1. 租户级线程池隔离**
```
公共线程池（处理普通请求）：80% 线程
租户 A 专用线程池：5%
租户 B 专用线程池：5%
  ...（大客户独立池）
弹性池：10%（按需分配）
```

**2. 异步任务队列隔离**
- 每个租户有独立的任务队列（或逻辑队列）
- 消费端按租户公平调度（轮询 / 权重轮询）
- 防止一个租户的 1 万个任务把队列占满

**3. 请求超时控制**
- 所有请求有严格的超时（默认 30s，慢操作走异步）
- 超时直接返回，不占用连接
- 慢查询自动告警

### 第三层：缓存隔离

**目标：** 防止单租户占满缓存空间

**策略：**

| 策略 | 说明 | 实现 |
|---|---|---|
| **内存配额** | 每个租户最多占用多少缓存内存 | Redis 多租户配额管理 / 按租户 key 前缀统计 |
| **Key 数量限制** | 每个租户最多多少个缓存 key | 写入时计数，超了拒绝或 LRU 淘汰 |
| **过期时间策略** | 防止永不过期的 key 堆积 | 所有缓存 key 必须有 TTL，最长不超过 7 天 |
| **大 Key 检测** | 单个 value 过大阻塞 Redis | 定期扫描大 key，拆分或降级到数据库 |

### 第四层：数据库隔离

**目标：** 最核心也最脆弱的一层，必须重点防护

**策略：**

**1. 连接池隔离**
- 每个租户分配独立的数据库连接数（配额）
- 基础版：最多 10 个连接
- 专业版：最多 30 个连接
- 企业版：最多 100 个连接
- 连接数满了就排队，超时就报错

**2. 查询超时与 kill**
- 所有 SQL 设置超时（默认 5s，报表类 30s）
- 超过 kill 阈值的慢查询自动 kill
- 被 kill 的查询记录到慢查询日志并告警

**3. 读写分离**
- 主库只处理写入和强一致读
- 从库处理查询和报表
- 大客户可以分配专属从库

**4. 资源组隔离（数据库层面）**
- PostgreSQL: pg_cgroups / 进程级资源限制
- MySQL: 资源组（Resource Group）
- 为不同等级租户分配不同的 CPU/IO 优先级

## 租户级可观测性

### 必须采集的指标

| 层级 | 指标 | 采集方式 |
|---|---|---|
| API 层 | 每租户 QPS / 错误率 / 延迟 | 网关日志 + 聚合 |
| 应用层 | 每租户请求数 / 线程池使用率 / 任务队列长度 | APM + 自定义 metrics |
| 缓存层 | 每租户内存使用 / key 数量 / 命中率 | Redis INFO + 前缀统计 |
| 数据库层 | 每租户连接数 / QPS / 慢查询数 / CPU 占用 | 数据库监控 + SQL 审计 |
| 存储层 | 每租户存储空间 / 请求数 | 对象存储 metrics |

### 监控看板

**租户资源使用排行榜（Top 20）：**
- 按 API 调用量排序
- 按数据库 CPU 占用排序
- 按缓存使用量排序
- 按存储使用量排序

**告警阈值：**

| 指标 | 警告阈值 | 严重阈值 | 自动动作 |
|---|---|---|---|
| 租户 QPS 超过配额 80% | 80% | 100% | 限流（严重） |
| 租户数据库连接 > 配额 80% | 80% | 100% | 拒绝新连接（严重） |
| 单租户占总 CPU > 30% | 30% | 50% | 限流 + 通知 |
| 单租户占缓存内存 > 20% | 20% | 30% | 触发淘汰 + 通知 |
| 慢查询数（10 分钟内） | 10 次 | 50 次 | 自动 kill + 通知 |

## 异常流量处理流程

### 检测与分级

| 级别 | 判定条件 | 响应 |
|---|---|---|
| **P3 — 关注** | 单租户资源使用 > 阈值 80%，但系统整体正常 | 记录观察，不主动干预 |
| **P2 — 警告** | 单租户资源使用超配额，或开始影响整体性能 | 自动限流，通知运维 |
| **P1 — 严重** | 单租户导致整体 SLA 下降，或数据库主库压力 > 80% | 升级限流 + 临时封禁高消耗接口 + 通知客户成功 |
| **P0 — 紧急** | 系统不可用或接近不可用 | 紧急隔离租户 + 故障响应流程 |

### 处理步骤

1. **自动检测** — 监控系统发现异常，触发告警
2. **自动限流** — 达到阈值自动启用限流策略
3. **人工确认** — 运维 on-call 确认是否需要升级处理
4. **客户通知** — 如果是客户正常使用（非攻击），客户成功联系客户
5. **根因分析** — 为什么会出现这种情况？是正常增长还是异常？
6. **优化措施** —
   - 正常增长：升级套餐 / 迁移 Silo / 优化查询
   - 异常使用：联系客户调整使用方式 / 提供 API 方案
   - 攻击/爬虫：封禁 IP / 加强验证
7. **复盘改进** — 更新策略、调整阈值、优化架构

## 差异化服务策略

### 按套餐分层

| 套餐 | API QPS | 数据库连接 | 缓存配额 | 存储配额 | 优先级 |
|---|---|---|---|---|---|
| 免费版 | 20/s | 5 | 100MB | 1GB | 低 |
| 基础版 | 100/s | 10 | 500MB | 10GB | 中 |
| 专业版 | 500/s | 30 | 2GB | 100GB | 高 |
| 企业版 | 2000/s | 100 | 10GB | 1TB | 最高 |
| 定制版 | 协商 | 独立池 | 独立 | 独立 | 专属资源 |

### 大客户处理策略

对于 ARR Top 20 的客户：
1. **资源预留** — 确保大客户有足够的资源配额，不被小客户挤占
2. **独立从库** — 查询走专属从库，不影响主库和其他租户
3. **独立缓存实例** — 大客户的数据放独立 Redis
4. **优先支持** — 性能问题优先响应
5. **定期巡检** — 每月检查大客户资源使用趋势，提前扩容
6. **Silo 建议** — 当大客户资源使用超过共享池的 20%，建议迁移到独立部署

## 常见陷阱

| 陷阱 | 表现 | 规避方法 |
|---|---|---|
| 只在入口限流 | 网关限流了，但内部异步任务还是把数据库打满 | 每一层都有限流策略，纵深防御 |
| 限流粒度太粗 | 全局限流，正常小客户也被误伤 | 按租户限流，每个租户有独立配额 |
| 没有度量就限流 | 不知道每个租户用了多少，凭感觉设阈值 | 先上监控，数据驱动调整阈值 |
| 大客户无限特权 | 大客户要多少给多少，最后成为系统巨婴 | 大客户也要有上限，超过就建议 Silo |
| 一限了之 | 限流了不通知客户，客户一头雾水 | 限流有明确的错误码 + 客户成功主动沟通 |
| 缓存无限膨胀 | 没有租户级缓存配额，大客户占满整个 Redis | 缓存配额管理 + 定期清理过期 key |
