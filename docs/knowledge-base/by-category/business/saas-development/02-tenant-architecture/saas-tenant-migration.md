# 租户跨环境迁移与升级 SOP

## 适用场景

- 租户从 Pool 迁移到 Silo（或反向）
- 租户跨地域 / 跨集群迁移
- 客户套餐升级涉及的架构变更
- 企业版客户的私有化部署迁移

---

## 核心原则

1. **零停机优先** — 能不停机就不停机，必须停机的尽量短
2. **可回滚** — 迁移前做好备份，出问题能切回去
3. **数据一致性** — 迁移前后数据必须完全一致，不能丢不能错
4. **透明化** — 迁移过程和影响提前告知客户，不偷偷摸摸搞
5. **演练先行** — 生产迁移前必须在测试环境完整演练一遍

---

## 迁移类型与场景

| 迁移类型 | 触发场景 | 复杂度 | 停机时间 |
|---|---|---|---|
| **Pool 内升级** | 套餐升级，只改配额和功能开关 | 低 | 0（在线变更） |
| **Pool → Silo** | 大客户增长到需要独立部署 | 高 | 分钟级（停机迁移）/ 秒级（双写） |
| **Silo → Pool** | 客户降级或合并到共享池 | 高 | 分钟级 |
| **跨集群迁移** | 数据中心迁移、负载均衡调整 | 高 | 分钟 ~ 小时级 |
| **跨地域迁移** | 客户要求数据存放在特定地区 | 很高 | 小时级 |
| **公有云 → 私有化** | 企业客户要求本地部署 | 很高 | 天级（项目制） |

## Pool → Silo 迁移流程（最常见）

### 阶段一：迁移评估与准备

**评估清单：**
- 客户数据量有多大？（数据库 + 文件存储）
- 业务可用性要求？（能不能停机？能停多久？）
- 有没有定制化代码？（Silo 环境需要同步部署）
- 集成了哪些外部系统？（API / Webhook / SSO 等）
- 迁移窗口期？（一般选周末凌晨）

**准备工作：**

| 任务 | 负责方 | 完成标准 |
|---|---|---|
| 目标环境搭建 | 运维 | Silo 环境部署完成，版本与源一致 |
| 网络连通性测试 | 运维 | 源和目标环境网络互通，带宽满足 |
| 数据一致性校验脚本 | 研发 + 测试 | 能逐项对比源和目标的数据 |
| 迁移脚本开发 | 研发 | 导出 → 传输 → 导入全流程脚本化 |
| 演练测试 | 测试 | 在测试环境完整演练至少 1 次 |
| 客户沟通 | 客户成功 | 客户确认迁移时间和影响 |
| 回滚方案确认 | 运维 + 研发 | 明确回滚触发条件和操作步骤 |

### 阶段二：停机迁移方案（简单但有 downtime）

**适用场景：** 数据量 < 100GB，能接受 30-60 分钟停机

**流程（预计总耗时 60-90 分钟）：**

```
T-30min: 通知客户迁移即将开始，准备进入只读模式
T-0min:   切换源租户为只读模式，停止写入
T+5min:   开始全量数据导出
T+20min:  导出完成，开始传输到目标环境
T+30min:  传输完成，开始导入目标环境
T+50min:  导入完成，数据一致性校验
T+55min:  校验通过，切换流量到 Silo 环境
T+60min:  验证功能正常，通知客户迁移完成
```

**关键检查点：**
- 导出后数据量核对（行数、文件数、存储大小）
- 导入后数据一致性校验（抽样对比 + 关键字段全量对比）
- 功能冒烟测试（核心流程跑一遍）
- 性能对比（响应时间不能比源环境差 10% 以上）

**回滚触发条件：**
- 数据一致性校验失败，无法在 30 分钟内修复
- 导入后关键功能不可用
- 性能严重下降（P95 > 2 倍源环境）

**回滚操作：**
1. 流量切回 Pool 环境
2. 解除只读模式
3. 确认服务恢复
4. Silo 环境数据保留（用于排查问题）

### 阶段二（进阶）：双写迁移方案（零停机）

**适用场景：** 数据量大、对可用性要求高的客户

**流程：**

```
阶段 1：全量同步
  → 源环境全量导出 → 导入到目标环境
  → （源环境继续正常服务）

阶段 2：增量同步（双写）
  → 开启双写：写入操作同时写到源和目标
  → 增量数据追平
  → 持续验证两边一致性

阶段 3：流量切换
  → 读流量切到目标（写还是双写）
  → 观察 24-48 小时
  → 一切正常，停掉源环境的写入
  → 迁移完成
```

**双写实现方式：**
- 应用层双写（改代码，最可控）
- 数据库 binlog 同步（如 Canal / Debezium）
- 中间件层双写（代理层）

**风险点：**
- 双写不一致（一边成功一边失败）→ 需要补偿机制
- 数据冲突（两边同时改同一条）→ 必须停写再切
- 双写期间性能下降 → 需要评估容量

### 阶段三：迁移后验证

**验证清单：**

| 验证项 | 方法 | 通过标准 |
|---|---|---|
| 数据完整性 | 行数对比、抽样对比 | 100% 一致 |
| 功能正确性 | 核心流程冒烟测试 | 全部通过 |
| 性能 | 基准测试 + 监控对比 | P95 ≤ 源环境 × 1.1 |
| 安全性 | 权限、隔离性测试 | 隔离正确，无越权 |
| 集成 | API、Webhook、SSO 测试 | 全部正常 |
| 监控告警 | 指标采集、告警触发 | 正常工作 |

### 阶段四：迁移后清理

**迁移成功后 7 天，确认无问题：**
1. 源环境数据归档（备份到冷存储）
2. 源环境资源回收（释放 Pool 中的租户配额）
3. 更新租户信息（部署模式、所在集群）
4. 更新 CRM / 财务系统信息
5. 迁移文档归档，总结经验教训

## 数据一致性校验

### 校验层级

| 层级 | 校验方法 | 速度 | 准确度 |
|---|---|---|---|
| **L1 — 行数对比** | 每张表 count 对比 | 快 | 低（只能发现丢了，发现不了错了） |
| **L2 — 校验和对比** | 按主键范围计算 checksum | 中 | 中（能发现不一致的范围） |
| **L3 — 逐字段对比** | 抽样 / 全量逐字段对比 | 慢 | 高（精确定位差异） |

### 推荐策略

1. **迁移前** — 记录源环境 L1 基线
2. **导入完成后** — 先 L1 快速检查，如果不一致直接定位问题
3. **L1 通过后** — L2 校验和对比，发现不一致的表和范围
4. **关键业务表** — L3 全量逐字段对比
5. **非关键表** — L3 抽样对比（1% 数据量）

### 校验工具

- 数据库自带：`pt-table-checksum`（MySQL）、`pg_comparator`（PostgreSQL）
- 自研脚本：按业务场景定制校验逻辑
- 数据对比平台：如 AWS DMS Validation、阿里云 DTS 校验

## 迁移项目管理

### 迁移项目 Checklist

- [ ] 迁移申请与审批（客户确认 + 内部审批）
- [ ] 迁移方案评审（技术方案评审会）
- [ ] 测试环境演练（至少 1 次完整演练）
- [ ] 客户沟通（迁移时间、影响、配合事项）
- [ ] 备份确认（迁移前源环境全量备份）
- [ ] 回滚方案确认（明确回滚条件和步骤）
- [ ] 人员安排（各环节 on-call 人员）
- [ ] 迁移时间窗确认（一般选周末凌晨）
- [ ] 迁移后监控计划（7 天重点监控）
- [ ] 迁移报告（成功/失败、数据量、耗时、问题）

### 人员分工

| 角色 | 职责 |
|---|---|
| **迁移负责人** | 整体协调，进度跟踪，决策升级 |
| **研发工程师** | 迁移脚本开发与执行，问题排查 |
| **运维工程师** | 环境准备，资源分配，网络配置 |
| **测试工程师** | 验证方案，功能测试，数据校验 |
| **客户成功经理** | 客户沟通，进度同步，反馈收集 |
| **DBA** | 数据库层面优化与支持 |

## 常见陷阱

| 陷阱 | 表现 | 规避方法 |
|---|---|---|
| 低估数据量 | 以为只有 10GB，实际加上日志和附件 100GB | 迁移前详细盘点所有数据存储位置 |
| 没有演练就上生产 | 第一次跑就是生产，各种意外 | 测试环境完整演练，踩过坑再上 |
| 只迁业务数据 | 业务数据迁了，配置、权限、缓存忘了 | 完整的数据清单，逐项 check |
| 回滚是空话 | 说能回滚，但真出问题发现回不去 | 迁移前演练回滚操作，确认可行 |
| 迁移后性能下降 | 迁过去发现比之前还慢 | 迁移前做性能基线，迁完对比 |
| 客户沟通不到位 | 迁完了客户才知道，出了问题投诉 | 提前沟通，中间同步，事后确认 |
| 大对象拖慢迁移 | 附件 / 图片等大文件传输慢 | 大对象单独迁移，业务数据先迁 |
