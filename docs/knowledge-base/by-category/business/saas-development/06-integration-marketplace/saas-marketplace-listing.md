# 应用市场上架与合作伙伴 SOP

## 适用场景

- SaaS 产品应用市场（App Marketplace）的建设与运营
- 第三方应用的上架审核流程
- 合作伙伴对接与生态扩展
- 应用的质量、安全、合规管理

---

## 核心原则

1. **生态大于功能** — 好的生态比自己做所有功能更有价值
2. **质量门槛** — 上架的应用要保证质量，一颗老鼠屎坏了一锅粥
3. **开发者成功** — 帮助开发者成功，生态才能起来
4. **安全合规底线** — 第三方应用不能成为安全漏洞，不能违法
5. **Win-Win** — 平台和开发者都要赚钱，单方面收割做不长久

---

## 为什么要做应用市场

### 价值

| 对平台 | 对客户 | 对开发者 |
|---|---|---|
| 扩展产品边界 | 满足个性化需求 | 获得用户和收入 |
| 增强客户粘性 | 不用切换多个系统 | 利用平台流量获客 |
| 构建生态壁垒 | 数据互通，效率提升 | 专注自己擅长的领域 |
| 新的收入来源（分成） | - | - |

### 什么时候做

**不是所有阶段都适合做应用市场：**

| 阶段 | 要不要做 | 原因 |
|---|---|---|
| PMF 之前 | 不要 | 自己产品还没做好，没人来接 |
| PMF 之后 | 可以开始 | 有了基础用户，开发者有动力 |
| 规模化阶段 | 重点做 | 生态成为竞争壁垒 |

**前提条件：**
- 产品有稳定的 API
- 有一定的客户基数（至少 1 万+ 活跃用户）
- 有专门的团队做生态

---

## 应用市场类型

### 按商业模式分

| 类型 | 说明 | 收入模式 | 示例 |
|---|---|---|---|
| **免费应用** | 开发者免费提供 | 免费，提升产品价值 | Slack 大多数集成 |
| **付费应用** | 应用单独收费 | 平台分成（一般 70/30 或 80/20） | Shopify App Store |
| **原生集成** | 平台官方做的集成 | 免费，作为产品功能的一部分 | Zapier 集成 |
| **合作伙伴** | 战略合作伙伴的深度集成 | 互导流量 / 收入分成 | 大厂之间的合作 |

### 按集成深度分

| 层级 | 说明 | 技术方式 |
|---|---|---|
| **L1 — 数据互通** | 同步数据，单向或双向 | API + Webhook |
| **L2 — 嵌入 UI** | 第三方界面嵌入到产品中 | iFrame / SDK |
| **L3 — 工作流** | 在产品内调用第三方能力 | 插件系统 / 扩展点 |
| **L4 — 平台级** | 完整的开发者平台，可构建完整应用 | 完整的 PaaS 能力 |

## 上架流程

### 开发者入驻

```
1. 开发者注册账号
2. 签署开发者协议
3. 提交开发者资料（公司 / 个人）
4. 审核通过 → 获得开发者身份
5. 接入开发者平台
```

### 应用提交流程

```
1. 开发者在后台创建应用
2. 配置应用信息（名称、图标、描述、截图）
3. 开发与测试
4. 提交审核
5. 平台审核（功能 + 安全 + 合规）
6. 审核通过 → 上架
7. 审核不通过 → 说明原因，修改后重新提交
```

### 审核标准

**必须通过的审核项：**

| 类别 | 检查项 |
|---|---|
| **功能质量** | 应用能正常运行，无明显 Bug |
|  | 描述和实际功能一致，不夸大 |
|  | 用户体验良好，不粗糙 |
| **安全审核** | 不请求不必要的权限 |
|  | 数据传输使用 HTTPS |
|  | 不存储用户明文密码 |
|  | 通过安全扫描 |
| **合规审核** | 不违反法律法规 |
|  | 有隐私政策 |
|  | 有服务条款 |
|  | 不侵犯知识产权 |
| **品牌规范** | 不滥用平台品牌 |
|  | 图标和截图符合规范 |
|  | 名称不误导用户 |

### 审核 SLA

| 审核阶段 | 目标时间 |
|---|---|
| 初审（资料完整性） | 1 个工作日 |
| 安全审核 | 3 个工作日 |
| 功能审核 | 3 个工作日 |
| 总审核时间 | 5-7 个工作日 |

## 开发者支持

### 开发者资源

| 资源 | 说明 | 优先级 |
|---|---|---|
| **开发文档** | 完整的 API 文档、SDK、指南 | P0 |
| **沙箱环境** | 测试用的独立环境，测试数据 | P0 |
| **示例代码** | 常见场景的 demo 应用 | P1 |
| **开发者论坛** | 提问、交流 | P1 |
| **技术支持** | 开发者专属技术支持渠道 | P1 |
| **设计规范** | UI 设计指南，保持体验一致 | P2 |

### 开发者成功团队

**职责：**
- 帮助重点开发者解决技术问题
- 协助优质应用优化体验
- 收集开发者反馈，改进平台
- 推动生态增长

**服务分层：**
- 普通开发者：文档 + 论坛 + 工单
- 重点开发者：专属对接人 + 优先支持
- 战略合作伙伴：联合项目 + 深度支持

## 商业化与分成

### 收入模式

| 模式 | 说明 | 适用场景 |
|---|---|---|
| **收入分成** | 应用收入按比例分（如 70% 开发者 / 30% 平台） | 付费应用 |
| **固定费用** | 开发者交上架费 / 年费 | 筛选质量 |
| **免费 + 流量变现** | 免费上架，广告位收费 | 生态早期 |
| **互导流量** | 互相导流，不涉及现金 | 战略合作 |

**常见分成比例：**
- 平台拿 20-30%，开发者拿 70-80%
- 开发者越多，平台分越少（规模效应）
- 头部开发者可谈更优比例

### 结算与支付

- 按月结算
- 平台统一向用户收费，再和开发者结算
- 开发者开发票（或平台代扣代缴）
- 最低结算金额（如 $100，低于这个累计到下月）

## 应用运营

### 应用发现

应用市场里怎么让用户找到好应用：

| 方式 | 说明 |
|---|---|
| **分类浏览** | 按功能分类（销售、营销、财务、开发等） |
| **搜索** | 关键词搜索 |
| **精选推荐** | 编辑推荐的优质应用 |
| **排行榜** | 安装量 / 评分排行 |
| **个性化推荐** | 基于用户行为推荐 |
| **场景解决方案** | 按使用场景组合推荐 |

### 质量与评价

- 用户评分（1-5 星）
- 用户评价和反馈
- 应用活跃度（安装量、使用率）
- 平均响应时间（支持响应速度）
- 安全评分

**下架条件：**
- 严重安全漏洞，限期未修复
- 长期不更新（6 个月以上无更新）
- 用户评分持续低于 2 星
- 违反开发者协议
- 违法违规

## 安全与合规

### 数据安全

**核心原则：** 用户数据是用户的，不是平台的，也不是第三方的。

**必须做到：**
1. **授权机制** — 用户明确授权应用访问哪些数据
2. **最小权限** — 应用只能拿到完成功能必需的数据
3. **可撤销** — 用户随时可以撤销授权
4. **数据使用透明** — 应用要说明用了哪些数据、用来干嘛
5. **安全审计** — 定期审计第三方应用的数据使用

### 合规要求

- 所有应用必须有隐私政策（Privacy Policy）
- 必须有服务条款（Terms of Service）
- 符合 GDPR / CCPA 等数据保护法规
- 敏感行业（医疗、金融）有额外要求
- 数据出境合规

## 常见陷阱

| 陷阱 | 表现 | 规避方法 |
|---|---|---|
| 生态做太早 | 产品本身还没 PMF，没人来做应用 | 先把产品做好，有了用户基础再做生态 |
| 审核放水 | 什么应用都能上，质量参差不齐 | 严格审核，宁可少不要烂 |
| 开发者工具烂 | 文档不全、SDK 难用，开发者跑了 | 把开发者当客户，做好 DX |
| 平台和开发者抢食 | 平台自己做了某个功能，开发者活不下去 | 明确平台边界，什么做什么不做 |
| 安全事件 | 第三方应用泄露用户数据，平台背锅 | 严格安全审核 + 权限最小化 + 审计 |
| 分成比例谈不拢 | 开发者嫌分的少，平台觉得亏 | 行业标准比例 + 阶梯分成 + 头部特谈 |
| 只有数量没有质量 | 1000 个应用，900 个没人用 | 聚焦质量，扶持头部应用 |
