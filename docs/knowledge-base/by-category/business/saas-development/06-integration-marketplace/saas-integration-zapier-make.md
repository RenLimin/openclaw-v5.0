# 无代码集成平台对接 SOP（Zapier / Make 等）

## 适用场景

- SaaS 产品与 Zapier / Make / n8n 等无代码自动化平台的对接
- 让用户可以不写代码就能把产品和其他工具串联
- 无代码集成的设计、开发、运营
- 触发（Trigger）和动作（Action）的设计规范

---

## 核心原则

1. **用户用无代码，不是我们用无代码** — 底层 API 要扎实，无代码只是壳
2. **Trigger + Action 范式** — 所有无代码集成平台都是这个套路，设计一次到处能用
3. **用户不用懂 API** — 字段命名要友好，描述要清楚，不用技术术语
4. **做就要做好** — 做一半的集成比不做还糟糕，用户失望
5. **主流平台优先** — 先做用户最多的平台，再考虑其他

---

## 为什么对接无代码平台

### 价值

| 对产品 | 对用户 |
|---|---|
| 快速扩展几百个集成 | 不用写代码就能和其他工具打通 |
| 不用自己一个个做集成 | 自己搭自动化流程 |
| 降低集成门槛 | 非技术人员也能用 |
| 获得曝光（平台流量） | 提升工作效率 |

### 主要平台对比

| 平台 | 市场定位 | 用户量 | 开发难度 | 推荐优先级 |
|---|---|---|---|---|
| **Zapier** | 大众向，最知名 | 最大 | 低 | ⭐⭐⭐⭐⭐ |
| **Make（Integromat）** | 中端，功能强 | 大 | 中 | ⭐⭐⭐⭐ |
| **n8n** | 开源，自托管 | 增长快 | 中 | ⭐⭐⭐ |
| **Power Automate** | 微软生态，企业 | 大 | 中 | ⭐⭐⭐（企业客户多就做） |
| **Airtable Automations** | Airtable 生态 | - | 低 | ⭐⭐（看产品定位） |

**建议：** 先做 Zapier（用户最多，最成熟），Make 第二。

## 核心概念

### Trigger vs Action

| 概念 | 说明 | 示例 |
|---|---|---|
| **Trigger（触发器）** | "当什么什么发生时" — 事件驱动 | 当有新用户注册时 |
| **Action（动作）** | "做什么什么" — 执行操作 | 创建一个任务 |
| **Search（搜索）** | "查找什么什么" — 查询操作 | 查找用户 |

**典型工作流：**
```
Trigger: 新订单产生（我们的产品）
   ↓
Action: 发送 Slack 通知（Slack）
   ↓
Action: 创建 Google Sheets 行（Google）
```

---

## Trigger 设计

### 触发方式

| 方式 | 说明 | 实时性 | 资源消耗 |
|---|---|---|---|
| **Polling（轮询）** | 每隔几分钟查一次有没有新数据 | 低（1-15 分钟延迟） | 高（大量请求） |
| **Webhook（推送）** | 有事件主动推送 | 高（实时） | 低（有事件才发） |

**推荐：优先 Webhook，Polling 作为备选。**

### Trigger 设计要点

**每个 Trigger 需要：**
1. **Trigger Key** — 唯一标识，如 `new_user_created`
2. **名称** — 人类可读的名字，如"新用户创建"
3. **描述** — 一句话说明什么时候触发
4. **输入字段** — 用户需要配置的参数（如筛选条件）
5. **输出字段** — 触发后提供的数据（所有用户字段）
6. **示例数据** — 供用户配置时预览的样本数据

### 常见 Trigger 类型

| 类型 | 示例 | 说明 |
|---|---|---|
| **新建记录** | 新用户创建、新订单生成 | 最常见 |
| **更新记录** | 用户信息更新、订单状态变更 | 注意：更新太频繁会触发太多次 |
| **删除记录** | 用户删除、任务删除 | 用的较少 |
| **特定事件** | 支付成功、任务完成 | 业务事件触发 |

### 去重机制

轮询方式必须去重，不然会重复触发：
- 用记录的唯一 ID 去重
- 平台会记录上次处理过的 ID
- 每次只返回上次之后的新数据

## Action 设计

### Action 类型

| 类型 | 说明 | 示例 |
|---|---|---|
| **Create** | 创建一条记录 | 创建用户、创建任务 |
| **Update** | 更新一条记录 | 更新用户信息 |
| **Delete** | 删除一条记录 | 删除任务 |
| **Search** | 查找记录 | 按邮箱查找用户 |
| **Create or Update** | 有就更新，没有就创建 | UPSERT |

### Action 设计要点

**每个 Action 需要：**
1. **Action Key** — 唯一标识
2. **名称 + 描述** — 用户能看懂是干嘛的
3. **输入字段** — 操作需要的参数
4. **输出字段** — 操作完成后返回的数据
5. **错误处理** — 各种错误情况和提示

### 字段设计规范

**字段类型：**
- string — 字符串
- number — 数字
- boolean — 布尔值
- datetime — 日期时间
- array — 数组
- object — 对象

**字段属性：**
- required — 是否必填
- label — 显示名称（友好的名字，不是变量名）
- helpText — 帮助说明（这个字段是干嘛的）
- default — 默认值
- choices — 下拉选项（枚举值）

**命名原则：**
- 用业务语言，不用技术术语
- ❌ "tenant_id" → ✅ "租户 ID"
- ❌ "is_active" → ✅ "是否激活"
- 描述要具体，不要模糊

### 动态字段（Dynamic Fields）

有些字段需要动态加载：
- 关联数据的下拉选项（如"选择项目"，要列出用户的所有项目）
- 依赖于其他字段的选项（选了项目后才能选任务）
- 自定义字段

实现方式：平台提供的动态下拉 / 动态字段 API。

## 开发流程

### 对接 Zapier 为例

```
1. 注册 Zapier 开发者账号
2. 创建 Integration
3. 配置认证方式（API Key / OAuth）
4. 开发 Trigger（每个一个）
5. 开发 Action（每个一个）
6. 测试每个 Trigger 和 Action
7. 提交审核
8. 审核通过 → 公开发布
```

### 开发工作量估算

| 工作项 | 工作量 |
|---|---|
| 认证对接 | 1-2 天 |
| 每个 Trigger | 0.5-1 天 |
| 每个 Action | 0.5-1 天 |
| 测试 + 文档 | 1-2 天 |
| 审核 + 修改 | 1 周（等审核时间） |

**建议首发：5-10 个 Trigger + 10-15 个 Action**，覆盖最常用的场景。

## 认证方式

### API Key vs OAuth 2.0

| 方式 | 用户体验 | 安全性 | 开发难度 | 推荐场景 |
|---|---|---|---|---|
| **API Key** | 中（用户要复制粘贴 key） | 中 | 低 | 快速上线 / MVP |
| **OAuth 2.0** | 好（一键授权） | 高 | 中高 | 正式版，推荐 |

**推荐：OAuth 2.0，体验好也安全。**

### OAuth 授权范围（Scope）

用户授权时要让用户知道应用能做什么：
- `read` — 只读数据
- `write` — 创建和更新数据
- `delete` — 删除数据
- `admin` — 管理员权限

粒度越细，用户越放心。

## 测试与质量

### 测试要点

| 测试项 | 说明 |
|---|---|
| **认证测试** | 能正常连接、断开连接 |
| **Trigger 测试** | 事件能正确触发，数据正确 |
| **Action 测试** | 各种输入都能正确处理 |
| **错误处理** | 认证失败、参数错误等情况有友好提示 |
| **字段映射** | 输出字段能被后续步骤正确引用 |
| **示例数据** | 配置时的示例数据有代表性 |

### 常见坑

- 日期格式不统一（有的是 ISO 字符串，有的是时间戳）
- 嵌套数据结构太复杂，用户不会映射字段
- 错误信息是技术术语，用户看不懂
- 没有示例数据，用户配置的时候不知道会拿到什么
- Trigger 去重有问题，重复触发

## 运营与维护

### 推广与发现

- 在应用市场 / 集成页面列出
- 文档站添加集成教程
- 博客 / 邮件介绍常见使用场景
- 和平台联合推广（Zapier 博客推荐等）

### 数据与指标

- 活跃集成数（有多少用户在用）
- 每个 Trigger / Action 的使用量
- 成功率（失败率高的要优化）
- 平均执行时间
- 用户评分

### 维护

- 定期更新（API 版本升级同步更新）
- 响应用户反馈
- 监控错误率
- 平台政策变更及时跟进

---

## 常见陷阱

| 陷阱 | 表现 | 规避方法 |
|---|---|---|
| 做了一堆没人用的 Action | 做了 20 个 Action，80% 的人只用 3 个 | 先做最常用的 10 个，根据数据再加 |
| 字段命名太技术 | 用户不知道 "status_id" 是什么 | 用业务语言，写清楚帮助说明 |
| 错误信息不友好 | "Invalid request body" 用户一头雾水 | 人性化错误提示，告诉用户怎么改 |
| 轮询太频繁 | 5 分钟一次，把 API 打挂了 | 合理的轮询间隔 + 限流保护 |
| 不维护 | 上线了就不管了，API 变了集成就挂了 | API 变更同步更新集成，监控成功率 |
| 认证做不好 | 用户连不上，第一步就卡住 | OAuth 流程顺滑，文档清楚，有排错指引 |
