# 多因素认证与无密码登录 SOP

## 适用场景

- SaaS 产品的 MFA（多因素认证）功能设计
- 无密码登录（Passkey / 魔法链接 / 生物识别）实现
- 企业级安全策略的强制 MFA 配置
- MFA 故障与恢复流程

---

## 核心原则

1. **安全与体验平衡** — 不能为了安全把用户逼疯，也不能为了方便裸奔
2. **多种方式可选** — 不同用户有不同偏好，给选择
3. **强制策略灵活** — 企业版可以强制开启 MFA，个人版建议开启
4. **恢复路径清晰** — 丢了 MFA 设备要有靠谱的恢复方式
5. **渐进式安全** — 根据风险等级动态调整认证强度

---

## MFA 方式对比

### 常见 MFA 类型

| 方式 | 安全性 | 用户体验 | 成本 | 普及率 | 推荐度 |
|---|---|---|---|---|---|
| **TOTP（Authenticator App）** | 高 | 中 | 低 | 高 | ⭐⭐⭐⭐⭐ |
| **WebAuthn / Passkey** | 极高 | 好 | 低 | 快速增长 | ⭐⭐⭐⭐⭐ |
| **短信验证码** | 低 | 好 | 中 | 高 | ⭐⭐（不推荐） |
| **邮件验证码** | 低 | 中 | 低 | 高 | ⭐⭐（仅备选） |
| **硬件密钥（YubiKey）** | 极高 | 中 | 高 | 低（企业用） | ⭐⭐⭐⭐ |
| **推送通知** | 中高 | 好 | 中 | 中 | ⭐⭐⭐ |
| **生物识别** | 高 | 极好 | 中 | 增长中 | ⭐⭐⭐⭐ |

### 详细说明

#### TOTP（基于时间的一次性密码）

**代表：** Google Authenticator、Authy、Microsoft Authenticator

**原理：**
- 服务端生成密钥，存到用户手机
- 每 30 秒生成一个 6 位数字验证码
- 基于时间 + 密钥哈希计算

**优点：**
- 免费，无短信费用
- 离线可用（不需要网络）
- 安全性较高（比短信强很多）
- 标准协议（RFC 6238），实现简单

**缺点：**
- 换手机要重新绑定
- 用户需要装 App
- 容易被钓鱼（伪基站假网站输入验证码）

#### WebAuthn / Passkey

**代表：** Apple Passkey、Google Passkey、Windows Hello、YubiKey

**原理：**
- 基于公钥密码学
- 私钥存在用户设备上，公钥存在服务端
- 认证时设备用私钥签名，服务端用公钥验证
- 支持生物识别（指纹、面容）解锁

**优点：**
- 安全性最高（防钓鱼、防中间人攻击）
- 用户体验好（指纹 / 面容一键登录）
- 不需要记密码
- 跨设备同步（iCloud 钥匙串、Google 密码管理器）

**缺点：**
- 浏览器兼容性（老浏览器不支持）
- 实现相对复杂
- 生态还在完善中

#### 短信验证码

**优点：** 用户不需要装 App，所有人都会

**缺点：**
- 安全性最低（SIM 劫持、短信劫持）
- 有短信费用
- 依赖运营商，送达率不是 100%
- 不推荐作为主要 MFA 方式

## MFA 产品设计

### MFA 开启流程

```
用户进入安全设置
    ↓
点击「开启两步验证」
    ↓
选择方式（TOTP / Passkey / 短信）
    ↓
按引导完成绑定
    ↓
生成恢复码（10 个，让用户保存）
    ↓
确认开启成功
```

### 强制 MFA（企业版功能）

管理员可以设置：
- 强制所有用户开启 MFA
- 指定必须的 MFA 方式（如"必须用 TOTP 或硬件密钥"）
- 宽限期（开启后 7 天内必须设置，否则锁定）
- 豁免用户（特定用户可以不用，如服务账号）

### 登录流程

**MFA 登录步骤：**
```
1. 输入邮箱 + 密码（或 SSO）
2. 验证通过，进入 MFA 步骤
3. 根据用户设置的方式，展示对应验证界面
4. 用户完成验证
5. 登录成功
```

**记住设备：**
- 用户可以选择"在此设备上记住 30 天"
- 30 天内此设备登录不需要 MFA
- 用 Cookie + 签名实现，安全性和体验平衡

### 风险自适应 MFA（进阶）

根据风险等级决定是否需要 MFA：

| 风险等级 | 判断条件 | 认证要求 |
|---|---|---|
| **低风险** | 常用设备 + 常用地点 + 正常时间 | 密码 / SSO 即可 |
| **中风险** | 新设备 / 新地点 | 需要 MFA |
| **高风险** | 多次失败 / 异常 IP / 异常行为 | 强制 MFA + 邮件通知用户 |

## 无密码登录

### 方式一：魔法链接（Magic Link）

**流程：**
1. 用户输入邮箱
2. 系统发送一封包含登录链接的邮件
3. 用户点击链接，自动登录

**优点：**
- 不需要记密码
- 实现简单
- 用户体验还行

**缺点：**
- 依赖邮箱，邮箱被盗就完了
- 每次登录都要收邮件，有点慢
- 有些人不看邮件

**适用场景：** 低频使用的产品、B2B 产品的备选登录方式

### 方式二：Passkey（推荐）

**流程：**
1. 用户在登录页选择"使用 Passkey 登录"
2. 浏览器弹出生物识别验证
3. 指纹 / 面容验证通过，直接登录

**优点：**
- 最快（一秒登录）
- 最安全（防钓鱼、防暴力破解）
- 体验最好（不输密码、不输验证码）

**缺点：**
- 老设备不支持
- 用户教育成本（不知道什么是 Passkey）
- 跨平台同步依赖平台厂商（Apple / Google / Microsoft）

**推荐策略：**
- 作为高级选项，懂的用户自然会用
- 慢慢培养用户习惯，未来会成为主流
- 和 TOTP 并存，不要只做 Passkey

## MFA 恢复机制

### 恢复码（Recovery Codes）

**最基本的恢复方式，必须有。**

- 开启 MFA 时生成 10 个恢复码
- 每个恢复码只能用一次
- 让用户打印 / 复制保存
- 用了一个少一个，用完了可以重新生成

**注意：**
- 恢复码和密码一样重要，要提醒用户妥善保存
- 不要存在同一个设备上（手机 MFA，恢复码存手机 = 白给）
- 建议打印出来放安全的地方，或者存在密码管理器里

### 备用方式

| 方式 | 说明 | 安全性 |
|---|---|---|
| **备用手机号** | 绑定第二个手机号，短信验证码登录 | 低 |
| **备用邮箱** | 发恢复链接到备用邮箱 | 中 |
| **多个 MFA 设备** | 绑定两个 TOTP / 两个硬件密钥 | 高 |
| **管理员重置** | 找管理员帮忙关闭 MFA | 中（看管理员流程） |

### 管理员重置流程

**企业客户：**
- 用户联系自己公司的管理员
- 管理员在后台帮用户关闭 MFA
- 用户登录后重新设置

**个人用户：**
- 身份验证（邮箱 + 手机号 + 其他信息）
- 人工审核（高风险账号）
- 关闭 MFA，让用户重新设置

## 安全注意事项

### 必须有的安全措施

1. **限流** — MFA 验证失败也要限流，防止暴力破解验证码
2. **通知** — MFA 状态变更（开启 / 关闭 / 换设备）要通知用户
3. **审计** — 所有 MFA 相关操作记入审计日志
4. **防钓鱼** — 教育用户不要在陌生网站输入验证码
5. **设备管理** — 用户可以看到自己的登录设备，踢掉可疑设备

### 常见攻击与防御

| 攻击方式 | 防御 |
|---|---|
| **暴力破解验证码** | 限流 + 锁定 + 验证码有效期短（30s） |
| **SIM 劫持（短信）** | 不推荐短信 MFA，优先 TOTP / Passkey |
| **钓鱼网站** | WebAuthn 防钓鱼；教育用户；域名提示 |
| **设备丢失** | 恢复码 + 管理员重置 + 远程登出 |
| **中间人攻击** | WebAuthn 防中间人；TOTP 也能防（只要密钥没泄露） |

---

## 常见陷阱

| 陷阱 | 表现 | 规避方法 |
|---|---|---|
| MFA 只支持短信 | 安全等级低，SIM 劫持就能绕过 | 支持 TOTP 和 Passkey，短信仅作备选 |
| 没有恢复机制 | 用户手机丢了就登不上号了 | 恢复码 + 备用方式 + 管理员重置 |
| 强制 MFA 太激进 | 一上来就强制，用户反弹 | 先建议开启，给缓冲期，逐步强制 |
| 恢复码用户不保存 | 生成了恢复码，用户直接关掉没保存 | 强制验证步骤：输入一个恢复码确认保存了 |
| 只做 MFA 忘了密码安全 | MFA 很强，但密码还是 123456 | 密码强度要求 + 防常用密码 |
| 过度依赖生物识别 | 指纹就是一切，手指划破了登不上 | 多种方式并存，总有一个能用 |
