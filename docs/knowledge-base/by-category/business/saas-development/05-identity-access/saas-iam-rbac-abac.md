# RBAC 与 ABAC 权限模型设计 SOP

## 适用场景

- SaaS 产品的权限系统设计
- 角色与权限的建模与管理
- 复杂场景下的属性级权限控制
- 权限系统的演进路径规划

---

## 核心原则

1. **最小权限原则** — 只给完成工作必需的权限，不给更多
2. **职责分离** — 关键操作需要不同角色的人共同完成（如审批）
3. **可审计** — 谁有什么权限、什么时候改的，都有记录
4. **可扩展** — 权限模型要能适应未来 2-3 年的业务发展
5. **用户体验** — 权限配置不能太复杂，管理员要能用得明白

---

## 权限模型演进

### 三阶段演进路径

```
阶段 1：简单角色       阶段 2：标准 RBAC       阶段 3：RBAC + ABAC
3-5 个固定角色    →   自定义角色 + 权限点   →   细粒度属性级权限
初创期 / MVP           成长期                   规模化 / 企业级
```

### 各阶段对比

| 维度 | 阶段 1：简单角色 | 阶段 2：RBAC | 阶段 3：RBAC + ABAC |
|---|---|---|---|
| **角色数** | 固定 3-5 个 | 可自定义，几十个 | 可自定义，无上限 |
| **权限粒度** | 粗（模块级） | 细（操作级） | 极细（数据级 / 属性级） |
| **复杂度** | 低 | 中 | 高 |
| **用户体验** | 好 | 中 | 需要学习 |
| **适用规模** | < 100 客户 | 100-1000 客户 | 1000+ 客户 / 企业级 |
| **开发成本** | 低 | 中 | 高 |

## 阶段 2：RBAC 详解

### 核心概念

**RBAC = Role-Based Access Control，基于角色的访问控制**

```
用户 → 角色 → 权限
   多对多    多对多
```

| 概念 | 说明 |
|---|---|
| **权限（Permission）** | 可以做什么操作，如"创建项目"、"删除用户" |
| **角色（Role）** | 一组权限的集合，如"管理员"、"成员" |
| **用户（User）** | 系统中的使用者，被分配角色 |
| **会话（Session）** | 用户登录后的会话，激活的角色 |

### 权限建模

#### 权限命名规范

推荐用 `资源:操作` 格式：

```
project:create        创建项目
project:read          查看项目
project:update        编辑项目
project:delete        删除项目
user:invite           邀请用户
user:remove           移除用户
billing:view          查看账单
billing:manage        管理计费
settings:read         查看设置
settings:write        修改设置
```

#### 权限粒度

| 粒度 | 示例 | 说明 |
|---|---|---|
| **模块级** | `project:*` | 能管理整个项目模块 |
| **操作级** | `project:create` | 能执行某个操作 |
| **字段级** | `project:read:budget` | 能看到某个字段 | 进阶，ABAC 做 |
| **数据级** | 只能看自己创建的项目 | 数据行级权限 | 进阶，ABAC 做 |

### 角色设计

#### SaaS 标准角色模板

| 角色 | 典型权限 | 说明 |
|---|---|---|
| **所有者（Owner）** | 所有权限 + 不可删除 | 每个租户一个，创建者默认 |
| **管理员（Admin）** | 用户管理、设置、计费、所有数据 | 可以有多个 |
| **经理（Manager）** | 项目管理、团队管理，但不能改设置 | 中层管理者 |
| **成员（Member）** | 正常使用功能，不能管理 | 普通员工 |
| **访客（Viewer）** | 只读，不能修改 | 外部协作者、客户 |
| **审计员（Auditor）** | 只读 + 审计日志 | 合规审计用 |

#### 自定义角色

企业版客户通常需要自定义角色：
- 客户可以自己创建角色
- 从权限列表中勾选需要的权限
- 给角色起名字、写描述
- 分配给用户

**注意：** 自定义角色不要无限灵活，否则客户会搞出奇怪的角色组合，支持成本很高。

### RBAC 实现要点

#### 前端控制（展示层）

- 没有权限的按钮 / 菜单不显示
- 没有权限的页面 403
- 注意：前端隐藏只是体验优化，安全靠后端

#### 后端控制（真正的安全）

- 每个 API 接口都有权限校验
- 推荐注解 / 装饰器方式
- 无权限返回 403 Forbidden

```python
# 示例：装饰器方式
@require_permission("project:delete")
def delete_project(project_id):
    ...
```

#### 缓存策略

- 用户权限缓存在会话 / Token 中
- 权限变更时，相关用户的会话需要刷新
- 实时性要求高的走数据库查

## 阶段 3：ABAC 详解

### 什么是 ABAC

**ABAC = Attribute-Based Access Control，基于属性的访问控制**

通过各种属性（用户属性、资源属性、环境属性）的组合来判断是否有权限。

```
能不能做 = f(用户属性, 资源属性, 环境属性, 操作)
```

### 什么时候需要 ABAC

RBAC 搞不定的场景：
- "部门经理只能看自己部门的数据"
- "项目负责人可以编辑自己创建的项目"
- "工作时间内可以访问，晚上不行"
- "客户数据只能在公司网络内访问"
- "敏感字段只有管理员能看到"

这些都涉及到**数据级 / 字段级 / 上下文相关**的权限判断，RBAC 做不了这么细。

### 属性类型

| 属性类型 | 示例 |
|---|---|
| **用户属性** | 部门、职位、级别、地区 |
| **资源属性** | 创建者、所属部门、密级、标签 |
| **环境属性** | 时间、IP 地址、设备、网络 |
| **操作** | 读、写、删除、导出 |

### 策略示例

```
策略 1：用户只能查看自己部门的数据
条件：
  - 操作 = read
  - 资源.部门 = 用户.部门

策略 2：项目创建者可以编辑项目
条件：
  - 操作 = update
  - 资源.创建者 = 用户.ID

策略 3：敏感字段只有管理员能看
条件：
  - 操作 = read
  - 资源字段 = 敏感字段
  - 角色包含 admin

策略 4：工作时间外不能导出数据
条件：
  - 操作 = export
  - 当前时间 in [9:00, 18:00]
  - 当前日期 is 工作日
```

## 推荐架构：RBAC + ABAC 混合

### 为什么混合

- **RBAC 管粗粒度**（能不能进这个模块）
- **ABAC 管细粒度**（能看到哪些数据、哪些字段）
- 纯 RBAC 太粗，纯 ABAC 太复杂难理解
- 混合模式兼顾灵活性和可理解性

### 架构示意

```
API 请求
   ↓
认证（你是谁）
   ↓
RBAC 权限校验（你有没有这个操作的权限）
   ↓
ABAC 数据范围校验（你能看到哪些数据）
   ↓
执行业务逻辑
   ↓
ABAC 字段过滤（返回结果中过滤无权字段）
   ↓
返回响应
```

### 实践建议

1. **先做 RBAC，再做 ABAC** — 不要上来就搞 ABAC，复杂度太高
2. **ABAC 从数据权限开始** — 最常见的需求是"只能看自己的数据"
3. **策略不要太灵活** — 给客户的是预设好的策略选项，不是写表达式
4. **性能是关键** — ABAC 判断不能成为性能瓶颈，要缓存、要优化

## 权限管理后台

### 功能清单

| 功能 | 管理员可用 | 说明 |
|---|---|---|
| 角色列表 | ✅ | 查看所有角色和权限 |
| 创建 / 编辑角色 | ✅（企业版） | 自定义角色 |
| 给用户分配角色 | ✅ | 用户管理中操作 |
| 权限矩阵查看 | ✅ | 一目了然每个角色有什么权限 |
| 权限变更日志 | ✅ | 谁什么时候改了谁的权限 |
| 模拟登录 | ✅ | 管理员模拟用户视角排查问题 |

### 权限申请流程（进阶）

大企业客户需要：
- 用户申请某个角色 / 权限
- 上级审批
- 自动生效
- 到期自动回收
- 定期 review（每季度 review 一次权限）

## 审计与合规

### 权限审计日志

记录所有权限相关操作：
- 谁被授予了什么角色
- 谁的角色被移除了
- 谁创建 / 修改了角色
- 操作时间、操作人、IP

### 定期审计

- 每季度导出权限清单 review
- 检查是否有权限过大的账号
- 离职用户账号是否已禁用
- 管理员权限人数是否合理（最少够用原则）

## 常见陷阱

| 陷阱 | 表现 | 规避方法 |
|---|---|---|
| 角色爆炸 | 每个人一个角色，管理混乱 | 角色按岗位设，不要按人设 |
| 权限粒度过细 | 几百个权限点，配置起来头大 | 按模块聚合，90% 场景操作级足够 |
| 前端隐藏 = 安全 | 以为按钮藏了就安全了 | 后端权限校验才是真安全，前端只是体验 |
| 超级用户泛滥 | 一半人都是管理员 | 最小权限原则，定期 review 管理员列表 |
| ABAC 过度设计 | 让客户写策略表达式，没人会用 | 预设策略选项，可视化配置，不要写代码 |
| 权限变更不通知 | 给人加了权限本人不知道 | 权限变更发邮件 / 站内信通知 |
| 没有审计日志 | 出了问题不知道谁改的权限 | 完整的权限审计日志，合规必需 |
