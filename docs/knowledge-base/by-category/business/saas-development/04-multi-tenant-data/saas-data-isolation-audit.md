# 多租户数据隔离审计 SOP

## 适用场景

- Pool 模式下多租户数据隔离的定期审计
- 新功能上线前的隔离性验证
- 安全合规检查（SOC 2、等保）中的数据隔离项
- 数据泄露风险排查

---

## 核心原则

1. **零容忍** — 跨租户数据泄露是 SaaS 的致命伤，一次都不能有
2. **纵深防御** — 应用层、数据库层、缓存层、日志层，层层设防
3. **定期审计** — 隔离性不是一次性的，需要持续验证
4. **自动化优先** — 能自动检查的就不要人工，提高频率和覆盖率
5. **防御性编程** — 假设开发者会忘加 tenant_id，系统层面兜底

---

## 隔离风险层级

### 风险分级

| 级别 | 定义 | 影响 | 响应时效 |
|---|---|---|---|
| **P0 — 严重** | 可稳定复现的跨租户数据访问 | 数据泄露，客户信任崩塌 | 立即修复，全面排查 |
| **P1 — 高危** | 特定条件下可跨租户访问 | 潜在泄露风险 | 24 小时内修复 |
| **P2 — 中危** | 防御有缺口但需要特定条件 | 理论风险 | 7 天内修复 |
| **P3 — 低危** | 防御措施不足但无直接风险 | 长期隐患 | 下个版本修复 |

### 常见风险点

| 层级 | 风险点 | 严重程度 |
|---|---|---|
| **应用层** | 某个 API 没校验 tenant_id | P0 |
| **应用层** | 管理后台越权查看其他租户数据 | P0 |
| **数据库层** | 直接访问数据库绕过应用层 | P0 |
| **缓存层** | 缓存 key 没加 tenant_id 前缀 | P0 |
| **搜索层** | ES 查询没加 tenant_id filter | P0 |
| **日志层** | 日志中包含其他租户的敏感数据 | P1 |
| **消息队列** | 消息没带 tenant_id，消费时串了 | P1 |
| **文件存储** | 文件路径没区分租户，可遍历下载 | P0 |
| **导出功能** | 导出数据没限制租户范围 | P0 |
| **批量任务** | 定时任务没按租户隔离，串数据 | P1 |

---

## 防御体系（五层防护）

### 第一层：框架层自动注入

**目标：** 开发者不需要手动写 tenant_id，框架自动加

**实现方式：**
- ORM 多租户插件（如 MyBatis-Plus TenantLineInnerInterceptor）
- JPA / Hibernate 过滤器（@Filter）
- 自定义 AOP 切面
- SQL 解析 + 自动改写

**验证点：**
- [ ] 新增 SQL 自动带 tenant_id
- [ ] 更新操作自动带 tenant_id
- [ ] 删除操作自动带 tenant_id
- [ ] 关联查询自动带 tenant_id
- [ ] 原生 SQL 能检测和提醒

### 第二层：数据库行级安全（RLS）

**目标：** 即使应用层出了 bug，数据库层面也兜住

**实现：** PostgreSQL Row Level Security / MySQL 企业版 TDE + VPD

**配置示例（PostgreSQL）：**
```sql
-- 启用 RLS
ALTER TABLE orders ENABLE ROW LEVEL SECURITY;

-- 创建策略
CREATE POLICY tenant_isolation ON orders
  USING (tenant_id = current_setting('app.tenant_id')::uuid);
```

**注意：**
- 应用连接数据库使用普通用户，不能是超级用户（超级用户绕过 RLS）
- 每个请求设置 current tenant_id
- 管理后台用专门的管理角色，有更宽的权限但有审计

### 第三层：缓存层隔离

**目标：** 缓存数据也不能串

**措施：**
- 所有缓存 key 必须包含租户前缀：`{tenant_id}:{业务key}`
- 缓存框架自动注入前缀（和数据库层一样）
- 缓存清理按租户隔离
- 禁止使用无租户维度的全局缓存（除非是公共数据）

**验证方法：**
- 扫描 Redis 中不带 tenant_id 的 key
- 检查缓存工具类是否强制要求 tenant_id

### 第四层：访问控制

**目标：** 每个请求都明确知道是哪个租户的，不能模糊

**措施：**
- API 请求必须带租户上下文（Token 中 / Header 中 / URL 路径中）
- 后台管理操作必须记录操作的租户
- 定时任务按租户执行，明确上下文
- 消息队列消息必须带 tenant_id

### 第五层：审计与监控

**目标：** 及时发现异常访问

**措施：**
- 所有跨租户操作（如管理后台查询）必须有审计日志
- 异常访问模式告警（如某个 IP 连续查询多个租户的数据）
- 定期安全扫描
- 渗透测试

## 审计方法

### 自动化安全测试

**在 CI/CD 中集成：**

| 测试类型 | 说明 | 频率 |
|---|---|---|
| **SQL 注入测试** | 测试是否能通过注入访问其他租户数据 | 每次提交 |
| **越权访问测试** | 用 A 租户的 Token 访问 B 租户的数据 | 每次提交 |
| **API 权限扫描** | 扫描所有 API 是否有权限校验 | 每日 |
| **集成测试** | 多租户场景下的业务流程测试 | 每次提交 |

**越权测试模板（每个 API 都要跑）：**
```
测试用例 1：A 租户用户访问 B 租户的资源 → 应返回 404 或 403
测试用例 2：未登录用户访问需要租户上下文的接口 → 应返回 401
测试用例 3：低权限用户访问高权限数据 → 应返回 403
测试用例 4：修改租户 ID 参数 → 应被拒绝或忽略
```

### 代码静态扫描

**扫描规则：**
- 检测没有 tenant_id 的数据库查询
- 检测缓存 key 构造是否包含租户前缀
- 检测 API 是否有鉴权注解
- 检测是否有直接拼接 SQL 的风险

**工具：**
- SonarQube 自定义规则
- Semgrep 自定义 pattern
- CodeQL

### 人工审计

**审计频率：** 每季度一次，或重大功能上线前

**审计范围：**
- 新增的数据库查询（确认都有 tenant_id）
- 新增的 API 接口（确认有权限校验）
- 缓存使用（确认 key 有租户前缀）
- 文件存储（确认路径有租户隔离）
- 后台管理功能（确认有审计日志）

**审计输出：**
- 审计报告
- 问题清单（分级）
- 整改计划
- 复测计划

### 渗透测试

**频率：** 每年至少 1 次，或重大架构变更后

**测试范围：**
- 水平越权（A 租户 → B 租户）
- 垂直越权（普通用户 → 管理员）
- SQL 注入
- 缓存污染
- 文件上传 / 下载漏洞
- API 遍历

---

## 审计检查清单

### 数据库层

- [ ] 所有业务表都有 tenant_id 字段
- [ ] 所有查询都带 tenant_id 条件（通过 ORM 插件保证）
- [ ] 数据库启用了 RLS（或等价机制）
- [ ] 数据库账号权限最小化（应用账号不能建表、不能删表）
- [ ] 超级用户仅限 DBA 使用，应用不用
- [ ] 索引包含 tenant_id（性能 + 正确性）

### 缓存层

- [ ] 所有缓存 key 有租户前缀
- [ ] 缓存框架自动注入租户前缀
- [ ] 没有租户维度的全局缓存（公共数据除外）
- [ ] 缓存清除按租户隔离

### 应用层

- [ ] 所有 API 有鉴权校验
- [ ] 所有业务操作有租户上下文
- [ ] 管理后台操作有审计日志
- [ ] 文件上传下载有租户隔离
- [ ] 导出功能有租户范围限制
- [ ] 消息队列消息带 tenant_id

### 运维层

- [ ] 生产数据库访问有审批流程
- [ ] 直接访问数据库有审计
- [ ] 备份数据有加密
- [ ] 日志中敏感数据已脱敏
- [ ] 定时任务按租户隔离执行

## 事件响应

### 发现隔离漏洞怎么办

**P0 级（可复现的跨租户访问）：**
1. 立即下线相关功能（feature flag 关闭）
2. 评估影响范围（哪些数据可能泄露）
3. 通知安全团队和管理层
4. 紧急修复，全面排查
5. 检查历史日志，确认是否已被利用
6. 修复后回归测试
7. 复盘，根因分析，改进措施

**P1/P2 级：**
1. 纳入缺陷跟踪，按优先级修复
2. 评估是否有在野利用
3. 修复后验证
4. 加入回归测试用例

## 常见陷阱

| 陷阱 | 表现 | 规避方法 |
|---|---|---|
| 只靠开发者自觉 | 全靠代码 review 保证加 tenant_id | 框架层自动注入 + 数据库 RLS 兜底 |
| 管理后台是法外之地 | 后台接口权限松，随便查数据 | 后台操作更严格的审计和权限控制 |
| 缓存忘了隔离 | 数据库查不到，缓存里能取到别的租户的 | 缓存框架自动加租户前缀 |
| 导出功能漏网 | 列表接口有权限，导出接口忘了加 | 导出和列表共用同一个数据查询层 |
| 日志泄露 | 日志里打了敏感数据，谁都能看 | 日志脱敏，访问日志有权限控制 |
| 定时任务串数据 | 定时任务切换租户时上下文没清干净 | 任务执行前明确设置租户上下文，执行后清理 |
| 测试只测 happy path | 只测正常流程，不测越权场景 | CI 集成越权自动化测试，每个 API 必跑 |
