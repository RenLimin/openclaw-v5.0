# 多租户数据分片策略 SOP

## 适用场景

- Pool 模式下多租户共享数据库的分片方案设计
- 数据量增长后的水平扩展策略
- 租户数据定位与路由机制
- 分片迁移与再平衡

---

## 核心原则

1. **租户是天然分片键** — 多租户场景下 tenant_id 几乎是所有查询的必备条件，天然适合做分片键
2. **分片数量提前规划** — 扩容比缩容容易，但跨分片迁移成本高，初始分片数要留足空间
3. **均匀分布** — 数据量和访问量尽量均匀分布，避免热点分片
4. **最小化跨分片查询** — 设计时尽量避免需要跨分片 join 的场景
5. **数据就近访问** — 同一租户的数据尽量在同一个分片，减少网络开销

---

## 分片方案对比

### 方案一：单库单表 + tenant_id 索引

**架构：** 所有租户数据在同一个库同一张表，靠 tenant_id 区分

```
database_01
  ├── table_orders (含 tenant_id)
  ├── table_users (含 tenant_id)
  └── ...
```

| 维度 | 评价 |
|---|---|
| 实现难度 | 极低 |
| 可扩展性 | 低（单库瓶颈） |
| 查询性能 | 依赖索引，数据量大后下降 |
| 运维复杂度 | 低 |
| 适用规模 | < 100 万行 / < 1000 租户 |

**适用场景：** 产品早期，数据量不大，快速迭代优先

### 方案二：按租户 ID 哈希分片

**架构：** 按 tenant_id 哈希取模，分布到多个分库分表

```
database_shard_01   database_shard_02   database_shard_N
  ├── orders_01       ├── orders_02       ├── orders_N
  ├── users_01        ├── users_02        ├── users_N
  └── ...             └── ...             └── ...
```

**分片算法：** `shard_id = hash(tenant_id) % N`

| 维度 | 评价 |
|---|---|
| 实现难度 | 中 |
| 可扩展性 | 中（扩容需要数据迁移） |
| 查询性能 | 好（单分片数据量小） |
| 运维复杂度 | 中高 |
| 适用规模 | 100 万 ~ 1 亿行 / 1000 ~ 10 万租户 |

**优点：**
- 数据分布均匀
- 查询定位简单，一次哈希就知道去哪个分片
- 横向扩展能力较强

**缺点：**
- 扩容需要迁移数据（N 变 2N 时，约 50% 数据需要迁移）
- 跨分片查询复杂（如统计、报表）
- 大租户可能占满一个分片

### 方案三：按租户大小分层（Lookup 分片）

**架构：** 维护一张租户-分片映射表，根据租户大小动态分配分片

```
           ┌─────────────────────┐
           │  tenant_shard_map   │  ← 路由表（独立库 / 缓存）
           └──────────┬──────────┘
                      │
        ┌─────────────┼─────────────┐
        ▼             ▼             ▼
   shard_01       shard_02       shard_N
  （小租户）      （中租户）    （大客户独立）
```

| 维度 | 评价 |
|---|---|
| 实现难度 | 高 |
| 可扩展性 | 高（按需扩容，灵活分配） |
| 查询性能 | 好 |
| 运维复杂度 | 高 |
| 适用规模 | 大型 SaaS，租户大小差异大 |

**优点：**
- 大客户可以独占分片，隔离性好
- 小租户挤一挤，资源利用率高
- 扩容灵活，按需新增分片
- 可按地区 / 行业分配分片

**缺点：**
- 需要维护路由表，增加复杂度
- 路由表本身成为单点（需缓存 + 高可用）
- 运维复杂，需要数据迁移工具

### 方案四：一致性哈希 + 虚拟节点

**架构：** 用一致性哈希环分配租户，新增分片只影响相邻节点

```
     租户A  租户B   租户C  租户D
       │      │       │      │
       ▼      ▼       ▼      ▼
┌───────┬───────┬───────┬───────┐  ← 哈希环
│shard_1│shard_2│shard_3│shard_4│
└───────┴───────┴───────┴───────┘
```

| 维度 | 评价 |
|---|---|
| 实现难度 | 高 |
| 可扩展性 | 很高（新增节点只迁 1/N 数据） |
| 查询性能 | 好 |
| 运维复杂度 | 高 |
| 适用规模 | 超大规模，频繁扩容 |

**优点：**
- 扩容影响小，新增分片只迁移少量数据
- 分布相对均匀（虚拟节点优化）

**缺点：**
- 实现复杂
- 数据分布可能不均匀（需要虚拟节点调优）

## 推荐方案与演进路径

### 四阶段演进

```
阶段 1：初创期          阶段 2：成长期          阶段 3：规模期          阶段 4：成熟期
单库单表 + 索引   →   按 tenant_id 哈希分片  →   Lookup 路由表分片   →   混合架构（大客户独立）
< 1000 租户             1000-10000 租户          1 万-10 万租户           10 万+ 租户
```

### 各阶段选型建议

| 阶段 | 租户规模 | 数据量级 | 推荐方案 |
|---|---|---|---|
| MVP / 早期 | < 1000 | < 100 万行 | 单库 + tenant_id 索引 |
| 快速增长 | 1k ~ 10k | 100 万 ~ 1 亿 | 哈希分片（8~16 个分片） |
| 规模化 | 10k ~ 100k | 1 亿 ~ 10 亿 | Lookup 路由 + 按需分配 |
| 成熟 | > 100k | > 10 亿 | 混合架构（大客户独立 + 小租户共享） |

## 分片设计要点

### 分片键选择

**最佳分片键：tenant_id**

为什么：
- 90% 以上的查询都会带 tenant_id
- 同一租户的数据天然在一起，事务、join 都在分片内
- 租户数量是可预期的增长维度

**不推荐的分片键：**
- 用户 ID：同一租户的用户分散在不同分片，跨片查询多
- 时间：数据倾斜（近期数据全在一个分片）
- 自增 ID：业务上无意义，路由需要查表

### 分片数量规划

**初始分片数建议：**
- 预期最大租户数 ÷ 单分片承载租户数 × 2（留一倍余量）
- 建议是 2 的幂次（2, 4, 8, 16, 32, 64），方便翻倍扩容
- 初始宁多勿少（多分片比少分片好迁）

**单分片承载能力参考：**
- PostgreSQL：单表 1000 万~5000 万行性能尚可
- MySQL：单表 500 万~2000 万行建议考虑分片
- 具体取决于字段数、索引数、查询模式

### 跨分片查询处理

**必须跨分片的场景：**
- 全局统计（总用户数、总订单数）
- 全局搜索（按非 tenant_id 字段查询）
- 后台管理（运营跨租户查询）

**解决方案：**

| 方案 | 说明 | 适用场景 |
|---|---|---|
| **分散-聚集** | 每个分片查，应用层聚合 | 统计类、简单聚合 |
| **ES / 搜索引擎** | 数据同步到 ES，ES 做全局检索 | 全文搜索、复杂查询 |
| **数仓 / OLAP** | 同步到 ClickHouse / 大数据平台 | 复杂分析、报表 |
| **全局表** | 小表每个分片存一份（如字典表） | 数据量小、变更少的表 |

### 分布式事务

**尽量避免跨分片事务。**

如果必须跨分片（极少见）：
- 最终一致性（消息队列 + 补偿）
- TCC 模式
- Seata / 分布式事务框架
- 但真的建议：重新设计数据模型，避免跨分片事务

## 分片路由实现

### 路由层设计

**位置：** DAO 层 / ORM 插件 / 中间件（ShardingSphere / MyCat / Citus）

**路由过程：**
```
SQL → 解析 tenant_id → 计算分片号 → 路由到对应分片 → 执行 SQL → 返回结果
```

### 路由表缓存

对于 Lookup 方案，路由表需要缓存：
- 本地缓存（Caffeine / LRU）+ 分布式缓存（Redis）
- 租户分片关系变更不频繁，缓存时间可设较长（1 小时）
- 变更时主动失效缓存

### 非分片查询处理

如果 SQL 中没有 tenant_id（如后台全局查询）：
- 走全分片查询（所有分片查一遍再聚合）
- 或走搜索引擎 / 数仓
- 这类查询必须限流，不能随便跑

## 分片迁移与再平衡

### 什么时候需要迁移

- 某个分片数据量超过阈值（如单表 > 5000 万行）
- 某个租户增长太快，需要独立分片
- 新增分片，需要重新分布数据
- 大客户要求独立部署

### 迁移流程

参考《租户跨环境迁移 SOP》，主要步骤：
1. 评估迁移范围和影响
2. 准备目标分片
3. 全量数据迁移
4. 增量同步（双写）
5. 切换路由
6. 验证与清理

### 再平衡策略

- 定期检查各分片数据量和负载
- 超过阈值的分片拆分
- 低于阈值的分片合并（较少见）
- 目标：各分片数据量差异 < 30%

## 常见陷阱

| 陷阱 | 表现 | 规避方法 |
|---|---|---|
| 过早分片 | 100 个租户就搞分片，复杂度远超收益 | 先单库跑，到瓶颈再分，不要过度设计 |
| 分片太少 | 分了 2 个片，一年后就不够了，迁起来痛苦 | 初始分片数留足，建议 8~16 起步 |
| 跨分片事务 | 到处都要跨分片事务，性能差还复杂 | 以 tenant_id 为分片键，90% 查询在片内 |
| 分片键选错 | 选了时间做分片键，热点全在最新分片 | 选 tenant_id 做分片键，分布均匀 |
| 没有迁移工具 | 需要迁数据了发现没工具，手动搞容易出错 | 提前开发迁移工具，定期演练 |
| 后台查询拖垮生产 | 运营跑个全量统计，所有分片都慢 | 后台查询走从库 / 走数仓，和生产隔离 |
