# 多租户数据备份与恢复 SOP

## 适用场景

- SaaS 产品的数据备份策略制定
- 租户级数据恢复（误删、数据损坏）
- 灾难恢复（数据库级 / 机房级）
- 备份策略优化与成本控制

---

## 核心原则

1. **备份是底线** — 出了问题能恢复，比什么都重要
2. **定期演练** — 没经过恢复验证的备份等于没有备份
3. **租户级恢复** — 多租户环境下，大多数恢复场景是单租户的，不是全库回滚
4. **3-2-1 原则** — 3 份备份，2 种介质，1 份异地
5. **RTO/RPO 驱动** — 备份策略由业务需求决定，不是拍脑袋

---

## 关键指标定义

| 指标 | 定义 | 说明 |
|---|---|---|
| **RPO** | Recovery Point Objective，恢复点目标 | 最多能接受丢失多久的数据 |
| **RTO** | Recovery Time Objective，恢复时间目标 | 最多能接受停机多久 |
| **备份窗口** | 每次备份的时间长度 | 不能影响业务正常运行 |
| **保留周期** | 备份保存多长时间 | 合规要求 + 业务需求 |

### SaaS 典型 RPO/RTO 目标

| 场景 | RPO | RTO | 说明 |
|---|---|---|---|
| **标准 SaaS** | 1 小时 | 4 小时 | 大多数 B2B SaaS |
| **高可用 SaaS** | 5 分钟 | 30 分钟 | 企业级 / 关键业务 |
| **单租户误删恢复** | 秒 ~ 分钟级 | 分钟 ~ 小时级 | 用 binlog / 回收站 |
| **全量灾难恢复** | 1 小时 | 4 ~ 8 小时 | 整个数据库挂了 |
| **归档数据恢复** | 天级 | 天级 | 冷备份恢复 |

---

## 备份策略体系

### 三层备份架构

```
第一层：实时 / 准实时备份（秒级 RPO）
  → Binlog / WAL 归档
  → 主从复制（从库作为热备）
  → 适用：误操作、小范围数据损坏

第二层：定期全量备份（天级 RPO）
  → 每日全量备份
  → 每小时增量备份
  → 适用：大范围数据损坏、逻辑错误

第三层：归档备份（周 / 月级）
  → 每周 / 每月全量备份归档到冷存储
  → 长期保存（1~7 年）
  → 适用：合规要求、历史数据回溯
```

### 详细备份策略

| 备份类型 | 频率 | 保留周期 | 存储介质 | RPO |
|---|---|---|---|---|
| **Binlog / WAL 归档** | 实时（每 5 分钟刷一次） | 7 天 | 对象存储 | 5 分钟 |
| **增量备份** | 每小时 | 7 天 | 对象存储 | 1 小时 |
| **每日全量备份** | 每天凌晨 | 30 天 | 对象存储 | 1 天 |
| **每周全量备份** | 每周日 | 3 个月 | 冷存储 | 1 周 |
| **每月全量备份** | 每月 1 号 | 1 年 | 冷存储 | 1 月 |
| **年度备份** | 每年年底 | 7 年 | 归档存储 | 1 年 |

### 租户级备份补充

除了数据库级备份，还应该支持租户级的备份能力：

| 能力 | 说明 | 用途 |
|---|---|---|
| **租户数据回收站** | 删除的数据先放回收站，保留 30 天 | 用户误删，自助恢复 |
| **租户快照** | 一键创建租户数据快照 | 大操作前手动备份 |
| **时间点恢复** | 恢复到某个时间点的租户数据 | 数据损坏回退 |
| **租户导出备份** | 用户自助导出全部数据 | 客户自己备份 |

## 数据库备份方案

### PostgreSQL

**工具：** pg_basebackup + WAL 归档 + pg_dump

**策略组合：**
```
每日全量：pg_basebackup（物理备份）  → 恢复快，体积大
WAL 归档：持续归档 WAL 文件         → 支持 PITR 任意时间点恢复
逻辑备份：pg_dump（SQL 格式）        → 单表 / 单租户恢复，灵活
```

**PITR（Point-in-Time Recovery）：**
- 基于基础备份 + WAL 日志，可以恢复到任意时间点
- 最小粒度：一个事务
- RPO：5 分钟（取决于 WAL 归档频率）

### MySQL

**工具：** mysqldump + XtraBackup + binlog

**策略组合：**
```
每日全量：XtraBackup（物理备份）     → 热备，不锁表
增量备份：XtraBackup incremental    → 只备份变化的
binlog 归档：持续归档                → 支持 PITR
逻辑备份：mysqldump                  → 单表 / 单租户恢复
```

### 备份验证

**每日自动验证：**
- 随机选一个最近的备份恢复到临时实例
- 检查数据完整性（行数、校验和）
- 检查数据库能否正常启动
- 记录验证结果，失败告警

**每季度演练：**
- 完整的灾难恢复演练
- 从备份开始计时，到完全恢复可用
- 记录实际 RTO，与目标对比
- 输出演练报告和改进项

## 恢复场景与流程

### 场景一：单条 / 少量数据误删

**触发：** 用户误删了一条数据，找客服恢复

**恢复方式：** 回收站（软删除）

**流程：**
1. 用户 / 客服在回收站找到数据
2. 点击恢复
3. 数据恢复到原位
4. 记录操作日志

**时间：** 分钟级

### 场景二：单租户大面积数据损坏

**触发：** 客户误操作 / 程序 bug 导致某个租户数据损坏

**恢复方式：** PITR 恢复单个租户的数据

**流程：**
1. 评估影响范围和数据量
2. 确认损坏时间点（要恢复到之前）
3. 在临时实例恢复数据库到指定时间点
4. 提取该租户的所有数据
5. 对比差异，生成恢复 SQL
6. 在生产执行恢复（先备份当前数据！）
7. 验证数据完整性
8. 通知客户

**时间：** 几小时（取决于数据量）

### 场景三：全库逻辑错误 / 误删

**触发：** 发布 bug 导致全表数据错了 / 删错了表

**恢复方式：** 全库 PITR

**流程：**
1. 停止业务（防止更多数据写入）
2. 确认故障时间点
3. 在备库 / 新库恢复到故障前时间点
4. 验证数据
5. 切换流量
6. 追补故障期间的数据（如果有）
7. 恢复业务
8. 复盘

**时间：** 小时级（取决于数据量）

### 场景四：数据库硬件故障 / 机房故障

**恢复方式：** 主从切换 / 灾备切换

**流程：**
1. 检测到故障
2. 自动 / 手动切换到从库 / 灾备库
3. 验证服务恢复
4. 修复原主库
5. 重新建立主从关系

**时间：** 分钟级（主从切换）~ 小时级（灾备）

## 备份成本优化

### 数据分层存储

| 存储层 | 适用备份 | 价格比 | 恢复时间 |
|---|---|---|---|
| **热存储** | 最近 7 天的备份 | 1x | 分钟级 |
| **低频存储** | 7 天 ~ 3 个月 | 0.3x ~ 0.5x | 小时级（需要先解冻） |
| **冷存储 / 归档** | 3 个月以上 | 0.05x ~ 0.2x | 小时 ~ 天级 |

### 优化手段

1. **分级存储** — 旧的备份移到冷存储，成本降一个数量级
2. **去重压缩** — 备份压缩 + 去重，减少存储量
3. **增量备份** — 不是每次都全量，只备份变化的
4. **合理保留周期** — 不需要永久保留的定期清理
5. **自动化生命周期管理** — 用云厂商的生命周期策略自动转存和删除

---

## 备份安全

1. **加密** — 备份文件必须加密存储（AES-256）
2. **访问控制** — 只有 DBA 和指定人员能访问备份
3. **异地备份** — 至少一份备份在不同地域的机房
4. **防篡改** — 备份文件不能被修改（WORM 存储 / 校验和）
5. **删除审批** — 删除备份需要审批，不能随便删

## 常见陷阱

| 陷阱 | 表现 | 规避方法 |
|---|---|---|
| 备份了但没试过恢复 | 出问题了发现备份是坏的，恢复不了 | 定期恢复演练，每日自动验证 |
| 只有全量备份 | 想恢复 2 小时前的数据，只能回到昨天 | 加 binlog / WAL 归档，支持 PITR |
| 备份在同一个机房 | 机房挂了备份也没了 | 异地备份，至少跨可用区 |
| 租户恢复困难 | 一个租户数据坏了，要恢复整个库，影响其他租户 | 支持单租户恢复能力（逻辑备份 + 租户级导出） |
| 备份费用失控 | 备份越攒越多，费用比数据库还贵 | 分级存储 + 生命周期管理 + 定期清理 |
| 备份窗口太长 | 备份时数据库压力大，影响业务 | 用物理热备工具，选低峰期，限流 |
| 忘了测试库备份 | 测试数据丢了无所谓？其实重建很费时间 | 测试环境也要有备份策略，可以简单点 |
