# 订阅计费引擎架构设计 SOP

## 适用场景

- SaaS 产品订阅计费系统的架构设计
- 从简单按月计费到复杂用量计费的演进
- 计费系统与订单、支付、发票、财务的集成
- 多币种、多地区、多税率的计费架构

---

## 核心原则

1. **计费是核心交易系统，不能错** — 多收了客户投诉，少收了公司亏损，一分钱都不能差
2. **可审计可追溯** — 每一笔账单的每一项都能追溯到源数据
3. **Idempotent（幂等）** — 重复触发计费不会重复出账
4. **解耦设计** — 计费规则与业务逻辑解耦，改定价不改代码
5. **提前演练** — 每次计费规则变更，必须在测试环境跑对账

## 计费系统总体架构

### 核心模块

```
┌──────────────────────────────────────────────────────────────┐
│                       Billing Engine                         │
├─────────────┬─────────────┬────────────┬───────────────────┤
│  订单管理    │  订阅管理    │  计费引擎   │  发票管理          │
│  Order Mgmt │  Subscription│  Rating    │  Invoice          │
├─────────────┼─────────────┼────────────┼───────────────────┤
│  支付管理    │  税务计算    │  催收管理   │  财务对账          │
│  Payment    │  Tax Engine │  Dunning   │  Finance Reconcile │
└─────────────┴─────────────┴────────────┴───────────────────┘
          │              │              │               │
          ▼              ▼              ▼               ▼
     ┌─────────┐   ┌──────────┐   ┌──────────┐   ┌──────────┐
     │ 用户系统 │   │ 用量采集  │   │ 支付网关  │   │ 财务系统  │
     └─────────┘   └──────────┘   └──────────┘   └──────────┘
```

### 各模块职责

| 模块 | 职责 | 关键数据 |
|---|---|---|
| **订单管理** | 处理购买、升级、降级、续费、取消 | 订单记录、订单状态流转 |
| **订阅管理** | 管理订阅生命周期、状态、周期 | 订阅记录、套餐、有效期 |
| **计费引擎** | 根据定价规则计算费用 | 账单明细、计费项目 |
| **发票管理** | 生成发票、管理发票状态 | 发票记录、PDF 文件 |
| **支付管理** | 对接支付渠道、处理扣款/退款 | 支付记录、交易流水 |
| **税务引擎** | 计算各地区税率、税号校验 | 税率规则、税务配置 |
| **催收管理** | 逾期提醒、重试、暂停/终止 | 催收记录、通知记录 |
| **财务对账** | 与支付渠道/财务系统对账 | 对账记录、差异处理 |

## 定价模型支持

### 常见定价模型

| 模型 | 说明 | 复杂度 | 示例产品 |
|---|---|---|---|
| **Flat Rate** | 固定月费/年费 | 低 | 基础版 ¥99/月 |
| **Per Seat** | 按席位/用户数计费 | 中 | CRM、协作工具 |
| **Usage-based** | 按用量计费（API 调用、存储、计算） | 高 | 云服务、数据平台 |
| **Tiered** | 阶梯定价（用量越多单价越低） | 高 | 短信、邮件服务 |
| **Freemium** | 免费版 + 付费版 | 中 | 大多数 PLG 产品 |
| **Feature-based** | 按功能模块计费 | 中高 | 企业版各种 add-on |
| **Hybrid** | 混合模型（基础费 + 用量 + 席位） | 很高 | 复杂企业 SaaS |

### 计费引擎核心能力

**支持的计费维度：**
- 时间维度：月付 / 季付 / 年付 / 一次性
- 数量维度：席位、设备、项目数等
- 用量维度：API 调用次数、存储量、流量
- 功能维度：功能模块开关、高级功能
- 层级维度：不同套餐不同价格和功能

**计费周期与结算：**
- 自然月结算（每月 1 号）vs 周期月结算（注册日起算）
- 预付费 vs 后付费
- 计费周期与账期的关系

## 订阅生命周期管理

### 订阅状态机

| 状态 | 说明 | 计费 | 服务可用 |
|---|---|---|---|
| **trialing** | 试用中 | 否 | 是（可能有限制） |
| **active** | 正常付费中 | 是 | 是 |
| **past_due** | 逾期未付 | 是（计费继续） | 是（宽限期内） |
| **paused** | 暂停 | 否 | 否（或只读） |
| **canceled** | 已取消 | 否 | 否（到期后） |
| **expired** | 已过期 | 否 | 否 |

### 关键操作

#### 新订（New Subscription）
1. 选择套餐和周期
2. 选择支付方式
3. 生成订单
4. 首次支付
5. 支付成功 → 订阅生效
6. 发送订单确认邮件 + 发票

#### 续费（Renewal）
1. 到期前自动生成续费订单
2. 自动扣款（提前 X 天）
3. 成功 → 续期
4. 失败 → 进入 dunning 流程

#### 升级（Upgrade）
- 立即生效，按比例补差价
- 例：月中从 ¥99 基础版升级到 ¥299 专业版，剩余 15 天补差价 ¥100
- 计费方式见 "按比例计费（Proration）SOP"

#### 降级（Downgrade）
- 下个计费周期生效
- 当前周期享受原套餐
- 到期后按新套餐计费

#### 取消（Cancel）
- 立即取消（不退费）或 到期取消
- 取消后进入取消挽留流程（见客户成功模块）
- 数据保留策略见租户生命周期

## 按比例计费（Proration）

### 计算规则

**基本公式：**
```
应退/应补 = (新价格 - 旧价格) × 剩余天数 / 总天数
```

**升级场景（从低价到高价）：**
- 立即生效
- 收取差价的按比例金额

**降级场景（从高价到低价）：**
- 下个周期生效
- 不退款（避免退款流程复杂性）
- 如果客户要求退款，走人工退款流程

### 计费精确性

| 维度 | 建议 |
|---|---|
| **时间精度** | 按天计算（不要按小时/分钟，太复杂） |
| **金额精度** | 分（保留 2 位小数） |
| **舍入规则** | 四舍五入（需明确写在服务条款中） |
| **最小变更单位** | 1 天（不满 1 天按 1 天算） |

## 用量计费（Usage-based Billing）

### 采集 → 聚合 → 计费 流水线

```
用量采集 → 数据校验 → 聚合汇总 → 费用计算 → 账单生成
   ↓          ↓           ↓           ↓          ↓
 事件流    去重/校验    按租户聚合   套用价目表   生成明细
```

### 各环节要点

**1. 用量采集**
- 事件驱动：每次使用发一个事件（埋点 / API 调用计数）
- 定时上报：定期上报用量数据
- 准确性要求：99.9% 以上（允许极少量丢失，但不能重复）
- 延迟要求：T+1 计费即可，不需要实时

**2. 数据校验**
- 去重：每个事件有唯一 ID，防止重复计费
- 完整性：检查时间序列是否有缺口
- 异常检测：用量突增突减触发告警

**3. 聚合与计费**
- 按租户 + 计费周期聚合
- 套用定价规则（阶梯、封顶、包量等）
- 生成计费明细
- 对账：与采集数据对账，确保金额正确

## 对账与财务

### 日对账流程

**每日自动对账：**
1. 拉取支付渠道交易流水
2. 与内部支付记录对比
3. 找出差异（金额不一致 / 状态不一致 / 单边账）
4. 生成对账差异报告
5. 财务人员处理差异

**对账频率：** 每日一次（T+1）

**对账差异处理时效：**
- P0（金额差异 > 1%）：24 小时内处理
- P1（少量单边账）：3 个工作日内处理

### 财务集成

**需要同步到财务系统的数据：**
- 收入确认（按权责发生制，不是按收付实现制）
- 应收账款
- 税金
- 退款
- 坏账

**收入确认：**
- 订阅收入在服务期内线性确认
- 一次性费用在服务交付时确认
- 使用量费用在使用发生的当月确认

## 技术选型建议

### 自建 vs 第三方

| 方案 | 优点 | 缺点 | 适用场景 |
|---|---|---|---|
| **Stripe Billing** | 功能全、稳定、国际支付 | 费用高（0.5%+）、国内支付弱 | 出海 SaaS、中小团队 |
| **Chargebee / Recurly** | 专业计费、功能强大 | 费用高、配置复杂 | 中大型 SaaS、复杂定价 |
| **国内计费 SaaS** | 符合国内支付/税务 | 质量参差不齐 | 国内市场为主 |
| **自研** | 完全可控、深度集成 | 开发维护成本高 | 复杂定价、数据敏感 |

**建议：**
- 早期 / 定价简单 → 用 Stripe / 支付平台自带的订阅功能
- 定价复杂 / 合规要求高 → 考虑专业计费系统或自研核心 + 第三方支付

## 常见陷阱

| 陷阱 | 表现 | 规避方法 |
|---|---|---|
| 计费算错 | 多收少收，对账对不上 | 详细的单元测试 + 集成测试 + 日对账 |
| 重复扣款 | 网络超时重试导致扣了两次 | 幂等设计 + 订单唯一号 + 对账发现差异 |
| Proration 逻辑混乱 | 升级降级费用客户看不懂 | 清晰的公式 + 透明的账单明细 + 预览 |
| 税务搞不定 | 不同国家/地区税率不一样，vat/gst 算错 | 用专业税务服务（如 TaxJar / Avalara） |
| 计费性能差 | 月底批量出账跑几个小时 | 分批处理 + 增量计算 + 优化数据库 |
| 没有沙箱 | 改个计费规则都不敢上线 | 完整的沙箱环境 + 预发布对账 |
| 账单看不懂 | 客户收到账单不知道钱花在哪 | 清晰的明细 + 用量图表 + 分级展示 |
