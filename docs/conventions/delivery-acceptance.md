# 交付验收方法（7 步法）

> 建立：2026-09-16
> 触发场景：任何"宣称完成"的长任务，无论自己做的还是 subagent 做的
> 来源：BDMS 交付教训 —— 昨晚自我汇报"全部完成"，今早独立审计挖出 3 个真实缺陷

## 为什么需要它

**自己验证自己的产出天然有结构盲点。**

BDMS 实例：昨晚汇报"CLI 7 个子命令实测"——实际只测了能跑通的那几个，崩溃的那个恰好没覆盖。报告是"我以为的状态"，不是"实际的状态"。

问题不在粗心，在方法：**验证覆盖率比验证结论更值得怀疑**。

## 7 步

### Step 1 — 清空上下文，独立审计
- 不读自己的总结、不读进度卡、不读 commit message
- 从代码现状 + 用户原始需求出发
- 目的：干掉确认偏差

### Step 2 — 契约对齐检查
- 核对设计文档（DESIGN.md / MODULE-CONTRACT.md）承诺的每个接口
- 文件系统里模块结构是否齐全
- 常见盲点：有入口函数但缺 service 层；CLI flag 被解析但业务代码从没用

### Step 3 — 全入口覆盖执行
- CLI：每个子命令**实际运行**，不是只看 `--help`
- Web：每个 API 端点**实际请求**，不是只看首页 200
- 必须覆盖成功路径之外：空输入、边界值、异常月份
- **规则：参数被解析 ≠ 参数生效**

### Step 4 — 黄金基准对比
- 有手工报表/历史数据的，必须做同口径对比
- 注意口径截断（预测月份 vs 实际月份）
- 没有黄金基准的，造一个最小验证集

### Step 5 — 幂等性测试
- 同一操作连跑 3 次，结果必须稳定
- 写入操作不能累积重复行
- 覆盖全模式：auto / read / regenerate

### Step 6 — Bug 修复的调用点扫描
- 修一个 bug 时，grep 全代码库找所有调用点
- 不能只修报错的那个入口
- 方法名/接口变更：全局搜旧名，确认没有漏网之鱼

### Step 7 — 回归测试锁定
- 每个新发现的 bug，必须写对应回归测试
- 测试要能复现 bug（修之前失败，修之后通过）
- **规则：新增测试数 ≥ 修复 bug 数**

## 验收通过标准

7 项同时满足才叫"全部完成"，缺任何一项都算有遗留：

| # | 检查项 | 判定 |
|---|---|---|
| 1 | 契约对齐 | 模块数 / 接口数 / 文件数 100% 一致 |
| 2 | 全入口执行 | CLI + Web + 直接调用 均无崩溃 |
| 3 | 黄金基准 | 零差异（如有基准） |
| 4 | 幂等测试 | 连跑 3 次结果稳定 |
| 5 | 单元测试 | 全绿，含新增回归 |
| 6 | 凭据扫描 | 无明文密钥 |
| 7 | Git 工作树 | 干净，无未提交改动 |

## 反面模式（都是真实踩过的）

| 反面模式 | 真实案例 | 正确做法 |
|---|---|---|
| 收参数不用参数 | `has_data(month)` 从不使用 month | 参数必须参与判定逻辑 |
| 参数被解析 ≠ 生效 | `--mode` 被 argparse 接受但未传给引擎 | 端到端跑一遍看行为 |
| 只修报错入口 | 同一方法名漂移，只修了 Web 漏了 CLI | grep 全调用点 |
| 测帮助文本代替实测 | "7 个子命令实测"实际没全覆盖 | 每个入口实际执行 |
| 只看首页 200 | 7 页面全 200，但下钻返回空数组 | 每个端点验数据内容 |
