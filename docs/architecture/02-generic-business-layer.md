## 1. 定位

### 1.1 L3 在分层架构中的位置

```
横切关注点（安全 · 合规 · 可观测 · 成本 · 组织协作 · 知识管理）
┌─────────────────────────────────────────────────────────────┐
│  L4  专有业务层 — 继承 L3 + 专有规则/数据/流程               │
├─────────────────────────────────────────────────────────────┤
│  L3  通用业务层 ★ 本文件                                     │
│      跨场景通用业务能力：业务知识 + 业务逻辑 + 角色定义       │
│      运行时无关                                              │
├─────────────────────────────────────────────────────────────┤
│  L2  基础设施层 — 配置/凭据/可观测/持久化/知识库...          │
├─────────────────────────────────────────────────────────────┤
│  L1  运行时抽象层 — OpenClaw                                │
├─────────────────────────────────────────────────────────────┤
│  L0  系统安装层                                              │
└─────────────────────────────────────────────────────────────┘
```

### 1.2 核心问题

**L2 解决"系统能跑"，L3 解决"系统能做什么业务"。**

| 问题 | 不建 L3 的后果 |
|------|---------------|
| AI agent 不懂业务 | 只能做通用问答，无法执行专业业务逻辑 |
| 业务知识散落各处 | 每次对话都要重复解释业务背景 |
| 无法复用 | 每个项目/客户都要从零开始 |
| 角色定义缺失 | Agent 不知道自己在业务场景中的身份和职责 |

### 1.3 与 L2 的边界

| 关注点 | L2 | L3 |
|---|---|---|
| 性质 | 技术基础设施 | 业务能力 |
| 举例 | "如何存储配置" | "项目管理中如何使用配置" |
| 变更频率 | 低（稳定后很少改） | 中（随业务演进而调整） |
| 可移植性 | 换业务场景无需改 | 换业务场景需要调整 |
| 依赖方向 | 不感知上层业务 | 依赖 L2 基础设施 |

## 2. 设计原则

| 原则 | 说明 |
|---|---|
| **知识驱动** | L3 的核心是业务知识 + 角色定义，不是代码 |
| **维度独立** | 各业务维度独立建设，互不阻塞 |
| **渐进式** | 先最小可用（知识库 + 角色），再逐步丰富 |
| **可被 L4 继承** | L3 能力必须可被 L4 直接复用，L4 只叠加差异 |
| **开源参考** | 参考业界成熟的业务角色库（agency-agents-zh 等） |
| **知识库配套** | 每个业务维度必须有配套的业务知识库 |

### 3.2 我们的维度选择策略

**不照搬 20 个部门**。基于 Rex 的场景（全栈 + 管理 + AI 系统建设），首批选择 3 个维度：

| 优先级 | 维度 | 理由 | 配套知识库 |
|--------|------|------|-----------|
| **P0** | 项目管理 | Rex 核心日常场景；有 PMBOK 等成熟知识体系 | `knowledge-base/by-category/business/project-management/` |
| **P0** | 系统建设 | 与 L2 基础设施直接关联；AI 系统建设方法论 | `knowledge-base/by-category/business/system-engineering/` |
| **P1** | 技术管理 | CTO/技术负责人视角；架构决策、技术债、团队效能 | `knowledge-base/by-category/business/tech-management/` |

### 3.3 维度间关系

```
项目管理 ←→ 系统建设 ←→ 技术管理
    ↕           ↕           ↕
  PMBOK       DevOps       技术债
  敏捷开发    架构决策      团队效能
  风险管理    可观测性      研发流程
```

维度间通过**共享上下文**（项目状态、系统健康、团队负载）协作，不直接依赖。

## 4. 角色定义模型

### 4.1 角色模板

每个业务角色由 4 个文件定义（对齐 agency-agents-zh 的 OpenClaw 集成格式）：

```
knowledge-base/by-category/business/<dimension>/<role>/
├── SOUL.md       # 身份人设：角色定位、核心能力、行为边界
├── AGENTS.md     # 业务能力：工作流程、交付物、工具使用
├── IDENTITY.md   # 简介：一句话定位、适用场景、能力边界
└── references/   # 参考知识：业务知识库索引
```

### 4.2 角色示例：项目经理

**SOUL.md** 核心内容：
- 角色定位：PMP/PMI-ACP 认证的项目管理者
- 核心能力：范围管理、进度管理、风险管理、干系人管理
- 行为边界：不代替技术决策，不做代码评审，关注交付物质量
- 方法论：PMBOK 7th + 敏捷混合

**AGENTS.md** 核心内容：
- 工作流：启动 → 规划 → 执行 → 监控 → 收尾
- 交付物：WBS、甘特图、风险登记册、状态报告
- 工具：exec（运行项目脚本）、read/write（管理项目文件）、memory（跟踪上下文）

### 4.3 角色激活机制

```
用户自然语言输入
  ↓
意图识别（关键词 + 上下文）
  ↓
匹配业务维度 → 加载角色 SOUL.md + AGENTS.md
  ↓
Agent 以该角色身份执行任务
  ↓
交付物写入项目空间
```

### 5.2 知识库与现有三维模型的关系

现有知识库按 **层级(L1~L4) × 阶段(design/develop/manage) × 类别(业界/理论/经验)** 组织。

L3 业务知识库按 **业务维度** 组织，是现有模型的**横向扩展**：

```
原三维模型（技术视角）          新增业务视角
         ↓                          ↓
  层级 × 阶段 × 类别       ×    业务维度 × 角色
         ↓                          ↓
  "L2 可观测性设计"          "项目管理中的可观测性"
  "L2 凭据管理开发"          "技术管理中的凭据策略"
```

两者通过**交叉引用**关联：
- 技术文档中引用业务场景（"在项目管理中，可观测性用于..."）
- 业务文档中引用技术实现（"项目状态追踪依赖 L2 持久化组件"）

### 5.3 知识库存储形式

**当前阶段：Markdown + frontmatter**（与现有知识库一致）

理由：
- 零依赖，与现有工具链（kb_index.py）兼容
- 人机共读，Rex 可直接编辑
- 版本控制友好

**未来演进**：当业务知识量 >100 篇时，评估自建知识库系统（ADR-003 阶段 3）

## 6. 与其他层的关系

### 6.1 L3 → L2 依赖

| L3 需求 | L2 提供的能力 |
|---------|--------------|
| 业务知识存储 | 知识库能力（kb_index.py + Markdown 索引） |
| 项目状态持久化 | 持久化适配（SQLite + Repository） |
| 配置管理 | 配置管理（快照 + 四步流程） |
| 健康监控 | 可观测性（日志 + 指标） |
| 凭据引用 | 凭据管理（SecretRef） |
| 定时任务 | L1 调度器（cron） |

### 6.2 L3 → L4 继承

```
L4 专有业务（如：RenLimin/openclaw-v5.0 项目开发）
  ├── extends L3 项目管理（通用项目管理能力）
  ├── extends L3 系统建设（通用架构设计能力）
  └── adds 专有规则：
      - 本项目的 ADR 流程
      - 本项目的 commit 规范
      - 本项目的架构约束（4 层分层）
```

### 6.3 L3 → L1 交互

L3 通过 L2 间接使用 L1 能力，不直接调用运行时 API：
- 需要定时任务 → 通过 L2 调度组件
- 需要记忆检索 → 通过 L2 记忆语义检索组件
- 需要工具执行 → 通过 L1 抽象契约（L2 适配层）

## 8. 验证标准

| 维度 | 标准 | 验证方式 |
|------|------|----------|
| 知识库完整性 | 每个维度 ≥ 10 篇知识文档 | `kb_index.py --stats` |
| 角色可用性 | 角色加载后能正确执行任务 | 端到端测试 |
| 知识检索 | 业务问题能召回相关知识 | `memory_search` 实测 |
| L4 可继承性 | L4 项目可直接引用 L3 角色 | 继承测试 |
| 维度独立性 | 新增维度不影响已有维度 | 回归测试 |

## 9. 风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| 知识库内容质量低 | 中 | 高 | 基于权威来源（PMBOK/Scrum Guide），不编造 |
| 角色定义过于宽泛 | 中 | 中 | 明确边界（SOUL.md 中定义"不做"清单） |
| 维度间耦合 | 低 | 高 | 维度间通过交叉引用关联，不直接依赖 |
| 知识过时 | 中 | 低 | 标注来源版本 + 定期 review |
