## 1. 定位

### 1.1 L3 在分层架构中的位置

```
横切关注点（安全 · 合规 · 可观测 · 成本 · 组织协作 · 知识管理）
┌─────────────────────────────────────────────────────────────┐
│  L4  专有业务层 — 继承 L3 + 专有规则/数据/流程               │
├─────────────────────────────────────────────────────────────┤
│  L3  通用业务层 ★ 本文件                                     │
│      跨场景通用业务能力：业务知识 + 业务逻辑 + 角色定义       │
│      运行时无关                                              │
├─────────────────────────────────────────────────────────────┤
│  L2  基础设施层 — 配置/凭据/可观测/持久化/知识库...          │
├─────────────────────────────────────────────────────────────┤
│  L1  运行时抽象层 — OpenClaw                                │
├─────────────────────────────────────────────────────────────┤
│  L0  系统安装层                                              │
└─────────────────────────────────────────────────────────────┘
```

### 1.2 核心问题

**L2 解决"系统能跑"，L3 解决"系统能做什么业务"。**

| 问题 | 不建 L3 的后果 |
|------|---------------|
| AI agent 不懂业务 | 只能做通用问答，无法执行专业业务逻辑 |
| 业务知识散落各处 | 每次对话都要重复解释业务背景 |
| 无法复用 | 每个项目/客户都要从零开始 |
| 角色定义缺失 | Agent 不知道自己在业务场景中的身份和职责 |

### 1.3 与 L2 的边界

| 关注点 | L2 | L3 |
|---|---|---|
| 性质 | 技术基础设施 | 业务能力 |
| 举例 | "如何存储配置" | "项目管理中如何使用配置" |
| 变更频率 | 低（稳定后很少改） | 中（随业务演进而调整） |
| 可移植性 | 换业务场景无需改 | 换业务场景需要调整 |
| 依赖方向 | 不感知上层业务 | 依赖 L2 基础设施 |

## 2. 设计原则

| 原则 | 说明 |
|---|---|
| **知识驱动** | L3 的核心是业务知识 + 角色定义，不是代码 |
| **维度独立** | 各业务维度独立建设，互不阻塞 |
| **渐进式** | 先最小可用（知识库 + 角色），再逐步丰富 |
| **可被 L4 继承** | L3 能力必须可被 L4 直接复用，L4 只叠加差异 |
| **开源参考** | 参考业界成熟的业务角色库（agency-agents-zh 等） |
| **知识库配套** | 每个业务维度必须有配套的业务知识库 |
| **方法论沉淀** | 建设过程形成可复用的方法论，沉淀为独立知识库 |

## 3. 业务维度划分

### 3.1 业界参考：agency-agents-zh 的部门分类

开源项目 [agency-agents-zh](https://github.com/jnMetaCode/agency-agents-zh) 定义了 **20 个部门、276 个专家角色**，覆盖工程、设计、营销、产品、游戏、安全、GIS、金融等。

关键启示：
- **按业务域划分**，不按技术栈划分
- **每个角色有明确定义**：身份人设 + 工作流程 + 交付物 + 行为边界
- **支持多工具集成**：SOUL.md + AGENTS.md + IDENTITY.md 三文件模型

### 3.2 Rex 的实际业务场景

基于 Rex 的业务需求，定义 3 大业务领域、7 个业务维度：

#### A. 软件行业 — 交付管理

| 维度 | 说明 | 核心知识体系 | 优先级 |
|------|------|-------------|--------|
| **项目管理** | 项目全生命周期管理 | PMBOK 7th / 敏捷 / 风险管理 | **P0** |
| **售后管理** | 客户支持、问题跟踪、SLA 管理 | ITIL / 客户成功方法论 | **P1** |
| **实施管理** | 软件部署、数据迁移、用户培训 | 实施方法论 / 变更管理 | **P1** |

#### B. 个人业务 — 家庭理财管理

| 维度 | 说明 | 核心知识体系 | 优先级 |
|------|------|-------------|--------|
| **家庭理财** | 预算、投资、保险、税务、退休规划 | CFP / 标准普尔家庭资产象限 / 国内税法 | **P0** |

#### C. 软件行业 — SaaS 系统开发

| 维度 | 说明 | 核心知识体系 | 优先级 |
|------|------|-------------|--------|
| **产品设计** | 产品策略、需求分析、用户体验 | 精益产品 / Jobs-to-be-Done / 设计思维 | **P0** |
| **系统架构** | 架构设计、技术选型、可扩展性 | DDD / 微服务 / 事件驱动 / SOLID | **P0** |
| **前端开发** | Web/Mobile UI 开发、性能优化 | React / Vue / 性能优化 / 可访问性 | **P1** |
| **后端开发** | API 设计、数据库、业务逻辑 | RESTful / GraphQL / 数据库设计 / 缓存策略 | **P1** |
| **DevOps/SRE** | CI/CD、部署、可观测性、可靠性 | SRE / GitOps / 混沌工程 | **P2** |
| **数据工程** | 数据管线、数据仓库、分析 | ETL / 数据建模 / BI | **P2** |
| **安全工程** | 应用安全、合规、审计 | OWASP / 等保 / GDPR | **P2** |
| **测试工程** | 测试策略、自动化、质量保障 | TDD / 测试金字塔 / 自动化测试框架 | **P2** |

### 3.3 维度全景图

```
                    ┌─────────────────────────────────────┐
                    │        软件行业 — 交付管理           │
                    │  项目管理 ←→ 售后管理 ←→ 实施管理    │
                    └──────────────┬──────────────────────┘
                                   │ 共享：客户、合同、项目状态
                                   ▼
┌──────────────────┐    ┌─────────────────────┐    ┌──────────────────┐
│  个人业务        │    │  SaaS 系统开发       │    │  方法论知识库     │
│  家庭理财管理    │◄──►│  产品设计            │    │  L3 建设方法论   │
│                  │    │  系统架构            │    │  角色定义规范    │
│  预算/投资/保险  │    │  前端开发            │    │  知识库标准      │
│  税务/退休       │    │  后端开发            │    │  验证流程        │
└──────────────────┘    │  DevOps/SRE          │    └──────────────────┘
                        │  数据工程            │
                        │  安全工程            │
                        │  测试工程            │
                        └─────────────────────┘
```

### 3.4 维度间协作关系

| 场景 | 涉及维度 | 协作方式 |
|------|----------|----------|
| 交付 SaaS 项目 | 项目管理 + 系统架构 + 产品设计 + 前后端开发 | 项目驱动，各角色按阶段介入 |
| 售后问题排查 | 售后管理 + 后端开发 + DevOps | 问题驱动，技术角色支持交付 |
| 家庭理财咨询 | 家庭理财 | 独立场景，不涉及其他维度 |
| 实施部署 | 实施管理 + DevOps + 后端开发 | 部署驱动，实施主导技术配合 |

## 4. 角色定义模型

### 4.1 角色模板（4 文件标准）

每个业务角色由 4 个文件定义（对齐 agency-agents-zh 的 OpenClaw 集成格式）：

```
knowledge-base/by-category/business/<dimension>/<role>/
├── SOUL.md       # 身份人设：角色定位、核心能力、行为边界
├── AGENTS.md     # 业务能力：工作流程、交付物、工具使用
├── IDENTITY.md   # 简介：一句话定位、适用场景、能力边界
└── references/   # 参考知识：业务知识库索引
```

### 4.2 角色定义规范

**SOUL.md** 必须包含：
- **角色定位**：一句话定义（"我是谁"）
- **核心能力**：3-5 项关键能力
- **行为边界**：明确"不做"清单（防止角色越界）
- **方法论**：遵循的知识体系/标准
- **沟通风格**：专业但易懂，避免过度术语

**AGENTS.md** 必须包含：
- **工作流程**：标准工作步骤（启动 → 执行 → 交付）
- **交付物清单**：每次交互的产出物
- **工具使用**：需要哪些 L2 工具能力
- **决策树**：常见场景的处理逻辑
- **质量标准**：交付物应满足的标准

**IDENTITY.md** 必须包含：
- **一句话定位**：20 字以内的角色描述
- **适用场景**：3-5 个典型使用场景
- **能力边界**：能做什么、不能做什么
- **前置条件**：激活该角色需要什么上下文

### 4.3 角色示例：项目经理

**SOUL.md**：
```markdown
# 项目经理 — 身份人设

## 角色定位
PMP/PMI-ACP 认证的项目管理者，负责软件交付项目的全生命周期管理。

## 核心能力
1. 范围管理：需求拆解、WBS 编制、变更控制
2. 进度管理：甘特图、关键路径、里程碑追踪
3. 风险管理：风险识别、评估、应对策略
4. 干系人管理：沟通计划、期望管理、冲突解决
5. 质量管理：验收标准、质量门禁、回顾改进

## 行为边界
- ✅ 做：项目规划、进度跟踪、风险预警、资源协调
- ❌ 不做：技术方案决策（由架构师负责）、代码评审（由 Tech Lead 负责）、
  预算审批（由管理层负责）

## 方法论
- PMBOK 第 7 版（12 条原则 + 8 个绩效域）
- 敏捷混合方法（Scrum + Kanban）
- 风险管理：ISO 31000

## 沟通风格
- 专业但易懂，对非技术干系人避免术语
- 主动预警，不等问题恶化才报告
- 数据驱动，用数字说话（完成率、风险等级、偏差百分比）
```

### 4.4 角色激活机制

```
用户自然语言输入
  ↓
意图识别（关键词 + 上下文 + 历史会话）
  ↓
匹配业务维度 → 加载角色 SOUL.md + AGENTS.md
  ↓
Agent 以该角色身份执行任务
  ↓
交付物写入项目空间
```

激活方式：
1. **显式激活**：用户说"以项目经理身份..."或"帮我管理这个项目"
2. **隐式激活**：根据关键词自动匹配（如"WBS"、"甘特图"→ 项目管理）
3. **上下文激活**：当前会话已加载项目上下文时自动关联

### 5.3 与现有三维模型的关系

现有知识库按 **层级(L1~L4) × 阶段(design/develop/manage) × 类别(业界/理论/经验)** 组织。

L3 业务知识库按 **业务维度** 组织，是现有模型的**横向扩展**：

```
原三维模型（技术视角）          新增业务视角
         ↓                          ↓
  层级 × 阶段 × 类别       ×    业务维度 × 角色
         ↓                          ↓
  "L2 可观测性设计"          "项目管理中的可观测性"
  "L2 凭据管理开发"          "SaaS 安全工程中的凭据策略"
```

两者通过**交叉引用**关联：
- 技术文档中引用业务场景
- 业务文档中引用技术实现

### 5.4 知识库存储形式

**当前阶段：Markdown + frontmatter**（与现有知识库一致）

理由：
- 零依赖，与现有工具链（kb_index.py）兼容
- 人机共读，Rex 可直接编辑
- 版本控制友好

**未来演进**：当业务知识量 >100 篇时，评估自建知识库系统（ADR-003 阶段 3）

## 6. L3 建设方法论（独立知识库）

### 6.1 方法论定位

L3 建设方法论是一个**独立的知识库**，记录"如何建设 L3"的标准化流程。它既是建设指南，也是经验沉淀容器。

```
knowledge-base/by-category/business/methodology/
├── README.md                    # 方法论索引
├── dimension-design.md          # 业务维度设计方法
├── role-definition.md           # 角色定义规范
├── knowledge-authoring.md       # 知识文档编写指南
├── quality-standard.md          # 质量标准与验证
└── lessons-learned.md           # 建设经验沉淀（持续更新）
```

### 6.2 业务维度设计方法

**目标**：从业务需求到可落地的 L3 维度定义。

**步骤**：

| 步骤 | 输入 | 产出 | 关键问题 |
|------|------|------|----------|
| 1. 需求识别 | 业务场景描述 | 维度清单 | "这个业务场景需要哪些角色？" |
| 2. 知识调研 | 业界标准/最佳实践 | 知识来源清单 | "这个领域有哪些权威知识体系？" |
| 3. 维度定义 | 调研结果 | 维度边界定义 | "这个维度包含什么、不包含什么？" |
| 4. 角色规划 | 维度边界 | 角色清单 | "这个维度需要哪些角色？" |
| 5. 依赖分析 | 角色清单 | 维度间依赖图 | "这个维度与其他维度如何协作？" |
| 6. 优先级排序 | 所有上述 | 建设顺序 | "先建哪个维度？" |

**原则**：
- 维度边界清晰，不重叠
- 每个维度有 ≥3 个角色
- 维度间通过共享上下文协作，不直接依赖

### 6.3 角色定义规范

**目标**：确保所有角色定义一致、可复用。

**标准流程**：

| 步骤 | 内容 | 产出 |
|------|------|------|
| 1. 角色定位 | 一句话定义 + 适用场景 | IDENTITY.md |
| 2. 能力定义 | 核心能力清单 + 行为边界 | SOUL.md 上半部分 |
| 3. 方法论绑定 | 遵循的知识体系/标准 | SOUL.md 下半部分 |
| 4. 工作流设计 | 标准工作步骤 + 决策树 | AGENTS.md 上半部分 |
| 5. 交付物定义 | 每次交互的产出物清单 | AGENTS.md 下半部分 |
| 6. 工具映射 | 需要哪些 L2 能力 | AGENTS.md 工具章节 |
| 7. 质量验证 | 角色能否正确执行任务 | 端到端测试 |

**质量标准**：
- [ ] IDENTITY.md ≤ 100 字
- [ ] SOUL.md 包含"不做"清单
- [ ] AGENTS.md 包含 ≥3 个交付物
- [ ] 角色能通过端到端测试
- [ ] 角色不与同维度其他角色职责重叠

### 6.4 知识文档编写指南

**目标**：确保业务知识文档质量一致。

**文档标准**：

| 字段 | 要求 |
|------|------|
| title | ≤ 30 字，包含关键词 |
| description | ≤ 200 字，概述核心内容 |
| source | 必须标注权威来源（书籍/标准/官网） |
| version | 知识体系版本（如 PMBOK 7th） |
| last_reviewed | 最后审查日期 |
| tags | ≥ 3 个标签，支持检索 |

**内容原则**：
- 基于权威来源，不编造
- 中文为主，术语保留英文原文
- 结构化（标题 + 列表 + 表格），避免大段叙述
- 包含"适用场景"和"注意事项"
- 标注知识时效性（如"基于 2024 版标准"）

### 6.5 质量标准与验证

**目标**：每个维度建设完成后，有标准化的验证流程。

**验证清单**：

| 检查项 | 标准 | 验证方式 |
|--------|------|----------|
| 知识库完整性 | ≥ 10 篇知识文档 | `kb_index.py --stats` |
| 角色覆盖率 | ≥ 3 个角色，覆盖核心场景 | 角色清单审查 |
| 知识检索准确率 | 业务问题召回相关知识 ≥ 80% | `memory_search` 实测 |
| 角色可用性 | 角色加载后能正确执行任务 | 端到端测试 |
| 交付物质量 | 交付物符合模板标准 | 模板对照检查 |
| 维度独立性 | 新增维度不影响已有维度 | 回归测试 |
| 文档规范合规 | 所有文档符合编写规范 | frontmatter 校验 |

### 6.6 经验沉淀机制

**目标**：建设过程中的教训和经验自动沉淀。

**触发条件**：
- 每个维度建设完成后 → 更新 `lessons-learned.md`
- 发现知识文档质量问题 → 更新 `knowledge-authoring.md`
- 角色定义不清晰 → 更新 `role-definition.md`
- 维度边界调整 → 更新 `dimension-design.md`

**沉淀格式**：
```markdown
## YYYY-MM-DD: <经验标题>

**背景**：发生了什么
**问题**：哪里出了问题
**根因**：为什么会这样
**修复**：怎么解决的
**预防**：如何避免再次发生
**影响范围**：影响了哪些维度/角色
```

## 7. 与其他层的关系

### 7.1 L3 → L2 依赖

| L3 需求 | L2 提供的能力 |
|---------|--------------|
| 业务知识存储 | 知识库能力（kb_index.py + Markdown 索引） |
| 项目状态持久化 | 持久化适配（SQLite + Repository） |
| 配置管理 | 配置管理（快照 + 四步流程） |
| 健康监控 | 可观测性（日志 + 指标） |
| 凭据引用 | 凭据管理（SecretRef） |
| 定时任务 | L1 调度器（cron） |

### 7.2 L3 → L4 继承

```
L4 专有业务（如：某 SaaS 产品开发项目）
  ├── extends L3 项目管理（通用项目管理能力）
  ├── extends L3 产品设计（通用产品设计能力）
  ├── extends L3 系统架构（通用架构设计能力）
  └── adds 专有规则：
      - 本项目的具体技术栈
      - 本项目的业务规则
      - 本项目的数据模型
```

### 7.3 L3 → L1 交互

L3 通过 L2 间接使用 L1 能力，不直接调用运行时 API。

## 10. 风险与缓解

| 风险 | 概率 | 影响 | 缓解 |
|------|------|------|------|
| 知识库内容质量低 | 中 | 高 | 基于权威来源，不编造；方法论中定义质量标准 |
| 角色定义过于宽泛 | 中 | 中 | 明确边界（SOUL.md 中定义"不做"清单） |
| 维度间耦合 | 低 | 高 | 维度间通过交叉引用关联，不直接依赖 |
| 知识过时 | 中 | 低 | 标注来源版本 + 定期 review |
| 建设进度不可控 | 中 | 中 | 按阶段渐进，每个阶段有明确产出和验证 |
