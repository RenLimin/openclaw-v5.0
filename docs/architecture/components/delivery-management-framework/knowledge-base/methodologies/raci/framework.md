# RACI 职责分配框架

## 概述
**RACI**（也叫 RACI 矩阵）是一种职责分配工具，用于明确每个任务/决策/可交付物的角色分工，避免职责重叠或职责真空。

**全称**：
- **R** — Responsible（执行）：具体干活的人
- **A** — Accountable（负责）：最终负责的人，只有一个
- **C** — Consulted（咨询）：需要被咨询意见的人
- **I** — Informed（告知）：需要被告知结果的人

## 核心原则

### 1. 每个任务有且只有一个 A
Accountable 是最终责任人，出了问题 TA 扛。多个 A = 没人负责。

### 2. R 至少一个
可以多人 R，但不要太多——3 个以上 R 说明任务可以拆分。

### 3. C 和 I 按需设置
不是每个任务都需要 C 和 I。太多 C = 决策慢，太多 I = 沟通成本高。

### 4. RACI 是角色的分配，不是人的分配
先分配到角色（PM、Dev、QA），再到人。人换了，角色不换。

## 4 种角色详解

### R — Responsible（执行）
- **定义**：实际完成工作的人
- **特征**：动手干活、产出结果、可能是一个或多个
- **数量**：1 个或多个，建议 ≤ 3 个
- **例子**：开发写代码、设计做图、测试测功能

### A — Accountable（最终负责）
- **定义**：对结果最终负责的人，有决策权
- **特征**：拍板、担责、批准交付物
- **数量**：**必须有且只有 1 个**
- **例子**：项目经理对项目进度最终负责、产品负责人对需求最终负责

### C — Consulted（咨询）
- **定义**：在决策或执行前需要听取意见的人
- **特征**：有专业知识或相关利益、双向沟通
- **数量**：0 个或多个，不要太多
- **例子**：架构师评审技术方案、法务审合同条款

### I — Informed（告知）
- **定义**：需要被告知结果的人
- **特征**：不参与决策、单向通知、事后知晓
- **数量**：0 个或多个
- **例子**：管理层被告知项目进展、相关团队被告知接口变更

## 变种

| 变种 | 含义 | 适用场景 |
|------|------|---------|
| **RACI** | 标准 4 角色 | 大多数项目 |
| **RASCI** | 加一个 Support（支持） | 有明显支持角色的场景 |
| **RACI-VS** | 加 Verify（验证）和 Sign-off（签字） | 质量要求高、需要签字的项目 |
| **RACIO** | 加 Omitted（省略/不参与） | 明确谁**不**参与 |
| **DACI** | Driver / Approver / Contributors / Informed | 决策型任务 |

## 构建 RACI 矩阵的步骤

```
1. 列出所有关键任务/可交付物/决策
   ├─ 从 WBS 中提取
   ├─ 从项目计划中提取
   └─ 不要太细（到任务级别）也不要太粗（到阶段级别）

2. 列出所有角色
   ├─ 项目团队角色
   ├─ 干系人角色
   └─ 外部角色（供应商、客户等）

3. 逐个分配 R/A/C/I
   ├─ 先定 A（最终负责人）
   ├─ 再定 R（执行者）
   ├─ 再定 C（需要咨询谁）
   └─ 最后定 I（需要告知谁）

4. 验证矩阵
   ├─ 每行有且只有一个 A 吗？
   ├─ 每行至少一个 R 吗？
   ├─ 有人全是 A 吗？（太多了）
   ├─ 有人全是 R 吗？（太累了）
   ├─ C 和 I 是不是太多？
   └─ 每个角色都清楚自己的职责吗？

5. 与相关方确认
   ├─ 团队成员确认
   ├─ 干系人确认
   └─ 达成共识后发布
```

## 示例：软件开发项目

| 任务 | PM | PO | Dev | QA | UX | 架构师 |
|------|----|----|-----|----|----|-------|
| 需求分析 | A | R | C | I | R | C |
| 架构设计 | A | I | C | I | C | R |
| UI 设计 | A | R | C | I | R | C |
| 开发实现 | A | I | R | C | I | C |
| 测试执行 | A | I | C | R | I | C |
| 部署上线 | A | I | R | C | I | R |
| 验收交付 | A | R | I | R | I | C |

## 常见误区

### 1. 多个 A = 没人负责
"两个人负责"等于"没人负责"。每个任务必须有唯一的 A。

### 2. R 和 A 不分
R 是干活的，A 是担责的。A 可以也干活，但 TA 最终担责。

### 3. 每个人都是 C
太多 C 会拖慢决策。只让真正需要参与的人参与。

### 4. 矩阵做出来就不管了
RACI 是活的文档，项目过程中角色/任务变化了要更新。

### 5. 颗粒度太细或太粗
- 太细：到"写登录接口"这种级别 → 维护成本太高
- 太粗：到"项目执行"这种级别 → 没有指导意义
- 合适：到 WBS 第 2-3 层

### 6. 用 RACI 搞政治
RACI 是协作工具，不是甩锅工具。出了问题先解决，再复盘。

## 在交付管理中的应用
1. **项目启动**：定义角色、分配职责、避免角色模糊
2. **跨团队协作**：明确接口处的 R/A，避免推诿
3. **新成员加入**：快速了解自己在每个任务中的位置
4. **冲突解决**：职责不清导致的冲突，查 RACI 解决
5. **组织改进**：识别某些人负担过重、某些角色职责缺失
