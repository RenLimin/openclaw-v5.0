# 混合敏捷方法

## 概述
现实中，纯瀑布或纯敏捷都很少见，**大多数项目是混合的**——在不同维度、不同阶段、不同团队用不同的方法。

**混合不是妥协，是精准匹配**：
- 稳定的部分用结构化方法
- 不确定的部分用敏捷方法
- 关键是接口和契约清晰

## 4 种主要混合模式

### 模式 1：Scrum + 看板 = Scrumban
**组合方式**：Scrum 的节奏 + 看板的流动

**特征**：
- 保留 Sprint（固定节奏）
- Sprint 内用看板管理流动
- 有 WIP 限制
- 有 Sprint Goal 但允许调整范围（pull 模式）

**适用场景**：
- 想从 Scrum 中获得更多流动效率
- 维护型/支持型团队（需求随时来）
- 团队 WIP 失控、多任务严重

**DMS 映射**：milestone 设 Sprint 节奏 + deliverable 用看板列管理

### 模式 2：瀑布 + 敏捷 = 混合开发生命周期
**组合方式**：前面瀑布，后面敏捷，或反之

**典型模式 A — 预测+敏捷**：
```
需求分析（瀑布） → 设计（瀑布） → 开发（敏捷迭代） → 验收（瀑布）
```
- 适用：需求基本清晰但实现有探索性

**典型模式 B — 敏捷+预测**：
```
探索（敏捷） → 产品化（瀑布）
```
- 适用：前期探索性强，后期需要严格质量/合规

**适用场景**：
- 大型项目，部分稳定部分变化
- 合规要求高的行业（金融、医疗）
- 硬件+软件结合的项目

**DMS 映射**：workflow_scheme 中定义混合式工作流，前期 milestone 用固定阶段，后期用迭代

### 模式 3：规模化敏捷
**组合方式**：多团队协同的敏捷框架

**常见框架**：

| 框架 | 特点 | 适用 |
|------|------|------|
| **SAFe** | 最完整、最重的规模化框架 | 50+ 人、大型企业 |
| **LeSS** | 轻量、Scrum 扩展 | 2-8 个团队 |
| **Nexus** | Scrum.org 出品，最小化 | 3-9 个团队 |
| **Spotify 模型** | 部落/分会/小队/公会，文化驱动 | 互联网公司、文化开放 |

**核心挑战**：
- 跨团队依赖管理
- 集成频率和质量
- 共同愿景和目标对齐
- 架构治理与自治的平衡

**DMS 映射**：多 project 组合 = Program，project 间通过 EventBus 联动

### 模式 4：敏捷 + DevOps
**组合方式**：Scrum/看板做需求管理，DevOps 做交付流水线

**核心实践**：
- CI/CD（持续集成/持续交付）
- 自动化测试
- 基础设施即代码
- 监控与可观测性
- 小批量、高频发布

**关键指标**：
- 部署频率
- 变更前置时间
- 变更失败率
- 平均恢复时间 (MTTR)

**DMS 映射**：deliverable.accepted → 自动部署 → sla_tracking 监控

## 选择混合模式的决策框架

```
需求稳定吗？
├── 是 → 瀑布或迭代瀑布
└── 否 → 技术确定吗？
         ├── 是 → 敏捷（Scrum/看板）
         └── 否 → 探索性方法（Lean Startup/设计冲刺）

团队规模？
├── 小（<9人） → 单团队框架
├── 中（9-30人） → 轻量规模化（LeSS/Nexus）
└── 大（>30人） → 重量级规模化（SAFe）或组合治理

合规要求？
├── 高 → 前置瀑布阶段 + 文档化 + 审计跟踪
├── 中 → 混合模式 + 关键节点评审
└── 低 → 纯敏捷 + 最小化流程
```

## 常见陷阱
1. **"Scrum 但..."综合征**：名义上敏捷，实际瀑布（Scrumfall）
2. **框架照搬**：不考虑上下文，直接套 SAFe/Spotify
3. **忽视工程实践**：只有流程敏捷，没有技术敏捷
4. **混合 = 各玩各的**：没有清晰的接口和契约
5. **度量错位**：用瀑布的指标管敏捷团队

## 与 DMS 框架的映射

DMS 框架天然支持混合模式：
| 混合维度 | DMS 支持 |
|---------|---------|
| 生命周期混合 | workflow_scheme 自定义工作流 |
| 模块级混合 | 模块热插拔，按需启用 |
| 项目级混合 | 不同项目用不同 scheme |
| 组织级混合 | 多租户/多项目，各项目独立配置 |
