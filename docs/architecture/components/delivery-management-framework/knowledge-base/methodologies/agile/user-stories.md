# 用户故事与需求拆分

## 概述
用户故事是从**用户视角**描述需求的简短语句，用于敏捷开发中沟通和规划需求。它不是需求文档，而是**需求的占位符**，代表一次对话。

## 用户故事格式

### 标准格式
```
作为 [角色]，我想要 [功能]，以便 [价值/原因]
```

**三要素**：
1. **角色（Who）**：谁要用这个功能？
2. **功能（What）**：要做什么？
3. **价值（Why）**：为什么需要？带来什么价值？

### 好例子
> 作为**电商用户**，我想要**查看我的订单历史**，以便**了解我买过什么和花了多少钱**

### 坏例子
> 做一个订单页面 ❌（没有角色、没有价值、是技术描述）

## INVEST 原则

好的用户故事应该满足 **INVEST**：

| 字母 | 含义 | 说明 |
|------|------|------|
| **I** | Independent（独立） | 不依赖其他故事，可以独立交付 |
| **N** | Negotiable（可协商） | 细节可以讨论，不是冻结的需求 |
| **V** | Valuable（有价值） | 对用户/业务有明确价值 |
| **E** | Estimable（可估算） | 团队能估算工作量 |
| **S** | Small（小） | 一个迭代内能完成 |
| **T** | Testable（可测试） | 有明确的验收标准 |

## 验收标准 (Acceptance Criteria)

### 格式：Given-When-Then
```
Given [前提条件]
When [操作]
Then [预期结果]
And [更多结果]
```

**例子**：
```
Given 我已登录
When 我点击"订单历史"
Then 页面显示我的所有订单
And 每个订单显示：日期、金额、状态、商品摘要
And 订单按日期倒序排列
```

### 3C 原则
- **Card（卡片）**：写在卡片上的简短描述
- **Conversation（对话）**：与 PO/干系人的沟通讨论
- **Confirmation（确认）**：明确的验收标准

## 7 种拆分技术

### 1. 按操作拆分
一个故事包含多个操作 → 拆成多个 CRUD 故事。
- 例："管理用户" → 查看用户 + 新增用户 + 编辑用户 + 删除用户

### 2. 按业务规则拆分
不同规则复杂度不同 → 分开做。
- 例：支付 → 微信支付 + 支付宝 + 银行卡
- 先做高频/简单的，再做低频/复杂的

### 3. 按数据范围/边界拆分
先做简单情况，再扩展。
- 例：搜索 → 精确搜索 + 模糊搜索 + 高级搜索

### 4. 按界面/页面拆分
多页面/多步骤 → 分开实现。
- 例：注册流程 → 第一步基本信息 + 第二步邮箱验证 + 第三步完善资料

### 5. 按性能/质量属性拆分
先做功能，再优化。
- 例：报表 → 生成报表 + 导出 Excel + 性能优化（<3s）

### 6. 按角色/权限拆分
不同角色看到的不同 → 分开。
- 例：仪表盘 → 普通用户视图 + 管理员视图 + 超级管理员视图

### 7. 按依赖拆分（反面模式）
**不要**按技术层拆分（前端故事、后端故事），因为：
- 不可独立交付
- 没有用户价值
- 增加协调成本
- 推荐：按功能切分，端到端交付

## 故事点估算

### 什么是故事点
- 不是人天，是**相对复杂度**的度量
- 考虑：工作量、复杂度、风险、不确定性
- 常用斐波那契数列：1, 2, 3, 5, 8, 13, 21, ...

### Planning Poker
1. 每人持有一组卡片（0, 1, 2, 3, 5, 8, 13, 20, 40, 100, ?, ∞）
2. PO 读故事，团队提问澄清
3. 每人同时出卡
4. 差异大的人解释理由
5. 讨论后再投票，直到达成共识

### 速度 (Velocity)
- 一个迭代完成的故事点总和
- 用于预测未来迭代能做多少
- **注意**：速度是团队的，不是个人的；不用于个人绩效

## 史诗 (Epic) 与主题 (Theme)

```
主题 (Theme)
 └── 史诗 (Epic) — 大故事，需要拆分
      └── 用户故事 (Story) — 一个迭代内能完成
           └── 任务 (Task) — 具体开发任务
```

**史诗拆分的信号**：
- 估算 > 8 或 13 点（团队基线的 2 倍以上）
- 跨多个组件/团队
- 包含多个用户角色
- 验收标准 > 5 条

## 常见误区
1. **故事写得太细**：变成任务，失去对话空间
2. **故事写得太粗**：无法估算，开发时才发现坑
3. **把故事当需求文档**：写了就不能改
4. **强制所有需求都用故事格式**：技术债、bug 不需要
5. **追求估算精确**：估算就是估算，不是承诺
6. **用故事点评绩效**：速度是团队指标，不是个人指标
