# 变更请求模板

## 模板用途
对项目范围、进度、成本、质量等基线的变更进行正式申请和审批，确保变更可控、影响可评估、决策可追溯，防止范围蔓延和项目失控。

## 填写说明
| 字段 | 必填 | 说明 |
|------|------|------|
| 变更编号 | ✅ | 唯一标识，便于追踪 |
| 变更标题 | ✅ | 一句话说清变更内容 |
| 变更类型 | ✅ | 范围/进度/成本/质量/资源/其他 |
| 变更原因 | ✅ | 为什么要变，背景和驱动力 |
| 变更内容 | ✅ | 具体要改变什么 |
| 影响分析 | ✅ | 对范围、进度、成本、质量、资源的影响 |
| 风险评估 | ✅ | 做这个变更带来的风险，以及不变更的风险 |
| 备选方案 | ⬜ | 除了提议方案，还有没有其他选择 |
| 申请人 | ✅ | 谁提出的变更 |
| 审批人 | ✅ | 谁来批准（按变更级别对应审批人） |
| 变更状态 | ✅ | 待审批/已批准/已拒绝/已实施/已关闭 |

## 注意事项
1. **变更申请必须书面化**：口头答应的变更不算数，必须填单审批，防止事后扯皮
2. **影响分析要客观**：申请人不能只说好处不说代价，PM 和技术负责人要独立评估
3. **分级审批**：不是所有变更都要总监批
   - 轻微变更（影响 < 1 人天，不涉及基线）：PM 审批即可
   - 一般变更（影响 1-5 人天，轻度影响基线）：PM + 产品负责人审批
   - 重大变更（影响 > 5 人天，或影响基线 > 10%）：交付总监审批
4. **紧急变更可以走绿色通道**：比如线上故障修复，先做后补单，但 24 小时内必须补流程
5. **被拒绝的变更也要记录**：留痕很重要，以后再有人提同样的变更，可以翻历史记录
6. **变更批准后要更新基线**：变更批准后，相应的项目计划、范围说明书等要同步更新
7. **定期回顾变更**：项目结束时统计变更数量和原因，是经验教训的重要输入
