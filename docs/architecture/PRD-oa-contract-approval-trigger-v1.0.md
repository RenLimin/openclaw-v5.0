## 1. 背景与问题

既有 P1~P4（已推送 `316b886`/`6c4cdcf`）已具备**零件**：`oa_todo_dist`（待办发现）、`oa_workflow_ones --capture`（读单据）、`contractctl oa-enhance`（R1 履约义务 + R2 概算）、`report.py enhance_section`（报告串联）。
但缺**三层**，导致 Rex 需逐次手报 requestid、格式漂移：

| # | 缺口 | 证据 |
|---|---|---|
| G1 | **无触发词**：SKILL 路由表只写「OA 销售合同审批（757）出审批建议」的**场景**，无固定触发指令「处理OA销售合同审批」→ 无法一句话进入编排 | `contract-manager-expert/SKILL.md` §典型编排 |
| G2 | **无编排**：capture / oa-enhance / 固定核查是**三个独立 CLI**，无「发现待办→逐张处理→汇总」流水线 | `cli/contractctl.py` 子命令彼此独立 |
| G3 | **无标准输出契约**：886377 的「审批建议」是**手写**（`review-summary-v3.md` §七），非代码产物，格式不可复现、无法直接贴 OA | v3 报告 §七 |

> **流程名口径**：OA 官方名 =「**销售合同审核流程**」（workflowid 757，`oa_todo_dist.py:44` + 知识库 §一）。
> Rex 指令中的「销售合同审批流程」为**同一流程的口语叫法**，取数范围 = **workflowid 757**。
> ⚠️ 勿与 L3 `contract-approval`（SCA-001「销售合同审批工作流」）混淆——那是**本地审批框架**，非 OA 757（知识库 §六）。

### N3 固定核查项（分层，fail-closed）

| 层级 | 核查项 | 数据源 | 缺失时 |
|---|---|---|---|
| L1 表单 | 合同编号缺失 | `body.txt`「合同编号！」 | 直接判**退回项** |
| L1 表单 | 服务期仅「签订之日起 N 年」、未明确起止 | `body.txt` 服务开始/结束日期 + 合同正文 | 有表单日期→提示；无→提示 |
| L2 原文 | 甲方官方邮箱留空 | 合同正文（`contract.txt`/docx） | **原文未提供 → 转人工，不判** |
| L2 原文 | 最终用户信息表缺失 | 合同正文 11.6 附件 | 同上 |
| L2 原文 | 版本描述不一致（流程分项 vs 合同正文） | 分项 `field26699` vs 合同正文 | 同上 |

> **硬约束（实测）**：757 单据合同附件 REST 下载无权限（探针返回「对不起，您暂时没有权限！」）。
> 故 L2 三项**仅在调用方提供合同原文时**才自动判定；否则显式标注「⚠️ 合同原文未提供，以下 N 项转人工」，**绝不伪造**。

### N4 标准审批备注（Rex 认可草案）

```
【审批建议】<退回补充 / 同意 / 退回补充（待原文）>
合同：<合同名称>（<requestid>，<金额> 元，<客户>）
退回项（需关闭后重提）：
1. <原因>
提示项（不阻断）：
1. <原因>
R1 履约义务：<判定>（ONES 实时 <日期>）
R2 概算一致性：<判定>（<差异>，仅提醒）
```

- 结论由「退回项是否存在」推导；无退回项 → 同意。
- 降级（R1/R2 skipped）→ 备注内显式标注，结论不得伪装完整。
