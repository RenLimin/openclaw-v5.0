# 系统架构

> 综合开放平台的分层架构设计。本文档是系统建设的**单一事实来源 (Single Source of Truth)**。

## 1. 设计原则

| 原则 | 说明 |
|---|---|
| **分层自治** | 每层只依赖下层，禁止跨层调用（如基础设施层不能直接调用通用业务层） |
| **契约稳定** | 层间通过明确定义的接口契约通信，契约变更需走 ADR |
| **适配优先** | 自定义能力必须适配官方系统层，不得破坏基座契约 |
| **复用优先** | 专有业务必须从通用业务层继承，仅叠加专有规则 |
| **治理横切** | 安全、合规、可观测、成本、组织协作作为横切关注点贯穿所有层 |

## 2. 分层架构

### 2.1 全景图

```
┌─────────────────────────────────────────────────────────────┐
│              横切关注点 (Cross-Cutting Concerns)            │
│   安全 · 合规 · 可观测 · 成本 · 组织协作 · 知识管理         │
└─────────────────────────────────────────────────────────────┘
                          ▲
┌─────────────────────────────────────────────────────────────┐
│  L4  专有业务层 (Proprietary Business Layer)                 │
│      · 继承通用业务能力 + 专有业务规则                       │
│      · 业务专有数据模型、专有流程、专有策略                   │
├─────────────────────────────────────────────────────────────┤
│  L3  通用业务层 (Generic Business Layer)                     │
│      · 跨场景通用业务能力（用户、商品、订单、支付…）          │
│      · 按业务维度切分，每维度独立演进                         │
├─────────────────────────────────────────────────────────────┤
│  L2  基础设施层 (Infrastructure Layer)                       │
│      · 自定义组件 / 系统资产                                  │
│      · 必须适配 L1 OpenClaw 官方契约                         │
├─────────────────────────────────────────────────────────────┤
│  L1  系统层 (System Layer) — OpenClaw 官方                  │
│      · 基座能力：Agent、Skills、Memory、Cron、Gateway、…     │
│      · 不可改，作为系统依赖                                  │
└─────────────────────────────────────────────────────────────┘
```

### 2.2 各层职责

#### L1 — 系统层 (System Layer)
- **来源**：OpenClaw 官方
- **职责**：提供基座能力（agent runtime、skill 系统、memory 持久化、gateway、cron、文件/进程工具、IM/平台集成等）
- **约束**：**不可修改**，作为系统依赖存在
- **演进方式**：跟随 OpenClaw 升级，关注 breaking changes

#### L2 — 基础设施层 (Infrastructure Layer)
- **来源**：自定义
- **职责**：封装/适配官方能力，提供本系统专用的基础设施服务
- **关键约束**：
  - 必须适配 L1 契约（不能绕过、不能 hack）
  - 提供给 L3 的接口必须稳定（契约变更需 ADR）
- **典型组件**（示例）：
  - 配置管理（profile、config schema、env 注入）
  - 可观测性适配（logging、metrics、tracing）
  - 持久化适配（memory、文件、KV）
  - 工具/技能封装（domain-specific skills）
  - 调度/任务编排（cron、agent turn、isolated run）
  - **知识库能力**（自建系统演进目标）

#### L3 — 通用业务层 (Generic Business Layer)
- **来源**：自定义
- **职责**：跨场景通用的业务能力
- **组织方式**：按业务维度切分（如 user、catalog、order、payment、notification、analytics…）
- **演进方式**：每个维度独立模块、独立版本
- **关键约束**：
  - 不感知专有业务上下文
  - 不直接依赖 L4
  - 通过契约提供服务

#### L4 — 专有业务层 (Proprietary Business Layer)
- **来源**：自定义
- **职责**：在通用业务能力之上叠加专有业务信息
- **关键约束**：
  - **必须继承 L3**，不得重写通用能力
  - 仅新增专有规则、专有数据、专有流程
  - 与 L3 的扩展点必须显式声明

### 2.3 调用关系

```
L4 → L3 → L2 → L1    (允许)
L4 → L2 / L1         (禁止)
L3 → L4              (禁止)
L1 → 任何上层         (反向依赖，禁止)
```

## 3. 横切关注点 (Cross-Cutting Concerns)

横切关注点**不构成独立层**，而是贯穿 L1~L4 的约束与能力。

| 关注点 | 在每层的要求 |
|---|---|
| **安全** | 凭据管理、权限边界、输入校验、审计日志 |
| **合规** | 数据驻留、隐私、监管要求 |
| **可观测** | 日志、指标、追踪、告警 |
| **成本** | 资源使用、API 调用、外部服务计费 |
| **组织协作** | 文档、决策记录、知识沉淀 |
| **知识管理** | 知识库分层、经验沉淀、ADR |

## 4. OpenClaw 契约边界

> 这是本系统最重要的约束——**基础设施层不得破坏的边界**。

### 4.1 可控范围
- Skills / 自定义插件
- Workspace 文件 / 配置
- Cron / 自动化任务
- 自有工具（exec、文件、网络）
- Memory / 日志
- 第三方集成（IM、平台）

### 4.2 不可控范围
- OpenClaw 核心行为 / 安全策略
- Gateway 内部实现
- Agent prompt / 工具策略（除非显式允许）
- 系统提示注入

### 4.3 扩展点（已知）
- Skills：新增、扩展
- Agent 配置：模型、工具、权限
- Cron：自定义任务
- 工具：新增（需符合契约）
- Memory：读写
- 外部平台：经由 OpenClaw 提供的接入

> 任何试图绕过 4.2 或在 4.3 之外扩展的能力，必须先走 ADR。

## 5. 演进路线

### 5.1 阶段一：基座搭建（当前）
- L1 + L2 最小可用（基于 OpenClaw workspace）
- L3 / L4 暂未启动
- 知识库采用 **Markdown + 元数据** 轻量方案
- 目标：跑通分层，验证契约

### 5.2 阶段二：业务能力沉淀
- L3 按业务维度逐步建设
- L4 开始引入
- 知识库继续以文件形式承载，但增加**结构化元数据 + 索引**

### 5.3 阶段三：自建知识库系统
- 在 L2 / L3 中实现**自建知识库系统**
- 支持人机协作阅读、跨系统移植
- 文档/经验/ADR 全部迁入自建系统
- 文件形式的知识库作为**导出格式**保留

### 5.4 阶段四：企业级治理
- 横切关注点全面落地
- 完整的可观测、合规、安全体系
