## 二、五块图例的完整含义与数据清理

### 组1 项目经理信息（col 1–4，R3–R36）

- 字段：项目经理 / 部门 / 中心 / 备注
- **31 个真实经理**，部门归并为 4 个：北区客户服务部(8) / 大客户服务部(11) / 南区客户服务部(9) / 其他(3)
- 中心：31 人全部「交付中心」（"其他"3 行中心是占位/汇总）
- `备注` 不是普通备注，实际承载**人员状态**：
  - 已离职（10 人）、已转岗（1 人，代杭旅）
  - 徐亚东/胡李鑫备注「项目管理部」（部门列="其他"，疑似双线/借调，需确认口径）
- R34/R35 的未立项/已结项：部门列=中心列=「其他」，备注=自身值 → 明确是**口径占位**不是人

**清理建议**：`project_manager` 只落 31 名真人（保留 dept/center/人员状态）；`*` 不落盘；`未立项/已结项` 是否需要作为业务允许值单列，见待决策 §四。

### 组2 交付考核信息（col 6–11，R3–R22，共 20 行）

这不是枚举列表，而是一张 **20 行考核规则矩阵**，每行 = 一条加权规则组合。`考核项` 是合并单元格（R3–R12 = 交付计划准确率；R13–R22 = 交付及时率）。

字段：考核项 / 偏差类别 / 是否跨月 / 偏差是否大于15自然日 / 加权系数 / 备注

规则规律（两考核项同构，各 10 行）：

| 偏差类别 | 是否跨月 | >15自然日 | 加权系数 | 备注 |
|---|---|---|---|---|
| 提前 | 是/否 | 是 | 1 | |
| 提前 | 是/否 | 否 | 0.5 | |
| 延后 | 是/否 | 是 | 1 | |
| 延后 | 是/否 | 否 | 0.5/1 | |
| 当月未填写 | 不统计 | （空） | 0 | 不重复考核，纳入"不填"考核项中 |
| 一致 | 不统计 | （空） | 0 | 合规 |

- 加权系数取值只有 `0 / 0.5 / 1`，是数值
- `偏差是否大于15自然日` 仅提前/延后 16 行有值，"当月未填写/一致" 4 行为空（不参与该维度）—— 属正常，不是缺失
- **清理建议**：20 行完整保留为规则定义，字段结构化；这是矩阵不是去重枚举。

## 三、图例数据在系统里的「应用位置」审计结果

| data_type | 是否被业务代码消费 | 消费位置 / 用途 |
|---|---|---|
| `obligation_status`（8 状态） | ✅ **唯一真正参与校验** | `validator.py` ENUM_COLS：校验「异常项目.状态」列的值必须在这 8 个状态内；校准页非法值拦截也走它 |
| 全部 11 类 | ✅ 参与导出还原 | `get_legend_config()` 逆装配成 48 列「图例」sheet（exporter + report engine），纯往返还原，**不参与任何计算** |
| `project_stat_status` | ⚠️ 仅同名，非图例消费 | dashboard 统计维度读的是业务数据列 `COL_STAT_STATUS`，**不读**这份图例 |
| `project_manager` | ⚠️ 仅同名 | wecom 同步的 `项目经理` 是业务字段，与图例无关 |
| `assessment_rule`（加权系数） | ❌ **无任何评分逻辑消费** | 系统目前**不计算**交付计划准确率/及时率，矩阵只是"规则定义"，被导出还原而已 |
| `item_stat_status`/`fin_*`/`sales_team`/3 个交接原因 | ❌ 无业务消费 | 当前仅作参考枚举 + 导出还原 |

**诚实提示**：图例里最有"计算价值"的考核加权矩阵，系统里目前没有任何落地的评分引擎读取它。它现在是"参考字典"，不是"活规则"。
