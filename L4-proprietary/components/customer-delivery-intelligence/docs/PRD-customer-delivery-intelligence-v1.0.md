# PRD：customer-delivery-intelligence（客户交付智能流水线）v1.0

> 状态：v1.0 待审（三份业界调研已完成并落盘 docs/research/）
> 编制：2026-11-10 ｜ 归属：L4 综合业务资产 ｜ 依据：3 份业界调研 + 既有资产实证审计

## 1. 背景与目标

### 1.1 问题

处理「客户项目/合同相关事项」（如中国建设银行）时，虽已具备原子能力（ONES/OA 取数、合同解析、履约汇总、汇报产出、PPT），但每次都要手工编排多段流程，换客户即重来，输出口径靠临场发挥、标准漂移。11-08 已发生「合同编号漏查」事故，根因之一就是取数完整性无统一规范。

### 1.2 目标

固化一条**参数化流水线**：输入仅「客户名 / 周期 / 受众」，经浏览器自动化从 OA、ONES 获取原始文件（数据），综合处理后产出（但不限于）：
- 项目汇总（Project Register）
- 签约项目汇总（含合同条款）★核心
- 履约义务汇总
- 验收条件核查表
- 验收单 / 交付说明（草稿，签字需人工）
- 回款跟踪
- 汇报材料（Markdown / docx / PPT）

同一操作方式与输出标准，跨客户复用；客户名是唯一主变量。

### 1.3 资产定位（Rex 指定）

- **L4 层** Bangcle 业务资产（非 L3 通用逻辑，非基础设施）
- 综合业务能力：**必须**经浏览器自动化等已建设能力，从 OA、ONES 等 Bangcle 相关系统获取原始文件
- 复用既有资产，不重造轮子

## 3. 标准产物契约（schema 要点，据调研-交付产物标准）

### 3.1 双层结构（跨客户一致的核心层 + 客户适配层）
核心层字段跨客户强制一致、全局唯一编码（`PROJ-YYYY-<客户>-<序号>`）；适配层按客户模板增补，变更不破坏核心口径。

### 3.2 六类产物必含字段（详见调研报告，PRD 摘要）

1. **项目汇总**：项目编号/客户主体/项目名/类型/合同号/金额/项目经理/起止/阶段状态/健康度/验收状态/回款状态
2. **签约项目汇总（含合同条款）★**：合同基本信息（编号/日期/类型/金额/税率/双方主体）、范围条款、里程碑与交付物条款、验收条款、付款条款、质保条款、IP与数据条款、违约条款、条款原文摘录（含条款号）
3. **履约义务汇总**：义务编号（`PO-<合同号>-NN`）/描述/可区分性/价格分摊/确认方式（时段法 vs 时点法）/验收节点关联/已确认与剩余金额
4. **验收条件核查表**：核查项编号/条款引用+原文/核查内容/判定标准（量化）/证据材料路径/核查方法/结论/核查人日期（三列制：证据-标准-结论）
5. **验收单/交付说明**：单据头/双方主体/交付物清单（齐套勾选）/验收结论（合格/需整改/不合格+遗留清单）/验收依据（合同条款+标准）/签字栏/附件清单/收入确认关联字段
6. **回款跟踪**：回款计划（节点/金额/触发条件/日期）/验收触发记录/开票记录/应收已收未收/账龄/逾期与催收/核销

### 3.3 双向引用链
五表共用「合同编号+条款号」外键；验收结论必须回溯到合同条款原文。验收=财务事件：每验收节点预映射付款比例、收入确认时点、开票计划。

## 4. 流程设计（据调研-Agent 工作流最佳实践 10 模式映射）

**定调：确定性 workflow 骨架 + 节点内受限 agent**（Anthropic: workflow vs agent 区分），不做端到端自由 Agent。

```
入口参数护栏(F1)
  → 编排器并行 [OA取文件(F3) | ONES取文件(F2)]   ← 模式2 Orchestrator-Workers
  → 文件齐套校验闸(F4)  ← 模式3 HITL 闸1（人工确认）
  → 解析/抽取（structured outputs + schema 校验重试闭环）   ← 模式4
  → 汇总成文（评估器自校验）   ← 模式8 Evaluator-Optimizer
  → 合同条款/对外稿签发  ← 模式3 HITL 闸2（人工签发）
  → 按受众渲染交付（md/docx/PPT）
每步写检查点(F12) ← 模式7；全链路 tracing(F13) ← 模式9；
状态/产物建模 ← 模式10 A2A Task/Artifact 思想；
浏览器：Playwright 确定性为主、Computer Use 兜底(F2/F3) ← 模式6；
护栏：入口合法性自动护栏 + 交付前 PII/越权护栏 ← 模式5。
```

三道强校验：①原始文件齐套校验（落盘后验类型/非空/来源）②产物 schema 校验（Pydantic 契约+回喂重试上限3次，仍失败升级人工）③交付前合规/越权护栏。

成本纪律：多智能体编排 token 消耗可达 15 倍（Anthropic 实测），仅在「跨 OA/ONES 并行取数 + 合同条款高价值抽取」用并行子 agent，其余确定性单步。

## 6. 技术选型（定稿：自建薄 runner + 复用成熟组件）

**结论（据调研 03 六条论证）**：现阶段**自建 Python 薄 runner**，不引入重型引擎；Temporal 保留为明确升级路径（预留适配面，不提前引入）。

### 6.1 为什么不自建 DAG 引擎 / 不引入外部引擎
- 业务量级：低频（周数次）、6~8 步、单 run 分钟级——Temporal/Trigger.dev 的分布式 durable 价值无法兑现，反而引入常驻服务运维面；
- 既有设施契合：仓库已有 job 表异步 + 前端轮询模式（进度条铁律已落地），薄 runner（≈200 行状态机）直接继承该模式实现断点/重试/进度；
- 人在环：验收审批走现有 Agent 审批流（job 状态 + 企微通知/回执），比引擎的 Signal/approval step 更贴合；
- 许可证：n8n（Sustainable Use）、Inngest（SSPL）、Windmill（AGPL+EE 分裂）均存在风险；Apache-2.0/MIT 组件无负担；
- 真正的风险点（OA/ONES 登录态失效、验证码、UI 变化）引擎解决不了，靠「会话持久化 + 步骤级重试 + LLM 兜底」；
- 行业无开箱即用「合同/验收/回款」流水线（关键词检索与 Clawhub 实搜均证实），属自建薄 runner 典型领域。

### 6.2 组件选型（薄 runner 内复用）
| 层 | 选型 | 依据（调研 03） |
|---|---|---|
| 抓取层 | Playwright（确定性主路径：session 持久化/下载拦截/截图取证）+ Playwright MCP（agent 决策指挥）+ browser-use（UI 漂移兜底） | 不引入 Skyvern（AGPL）/Steel（多余服务） |
| 解析层 | Docling（合同 PDF/DOCX→结构化，扫描件+条款表格）+ MarkItDown（Word 快路径） | 放弃 textract（停滞/云依赖）；Unstructured 本地依赖多 |
| 产出层 | 内置 5 类标准交付物模板；核查表/回款核对采用「逐行复算+原文行号引用」范式（借鉴 Clawhub chenqg618 系）；验收结论 ✅/⚠️/❌ 三级（借鉴 golngod 系） | Clawhub 实搜 |
| 编排层 | 薄 runner：步骤=「纯函数 + 状态字典」接口，预留 Temporal 适配面 | 升级路径保留 |

### 6.3 编排与状态模式（据调研 01）
- 确定性 workflow 骨架 + 节点内受限 agent（Anthropic workflow vs agent 区分）
- 中心化强类型状态对象 + 每节点检查点持久化（SQLite，thread_id=任务ID）
- 两道人工闸：①文件齐套确认 ②对外稿签发（HITL，可跨天，从断点精确恢复）
- Schema-First 产物契约（Pydantic/JSON Schema）+ 节点出口独立校验 + 失败回喂重试（上限 3 次）+ 升级人工
- 入口合法性护栏 + 交付前 PII/越权护栏（自动二元，与人工闸分离）
- 全链路 tracing + 「原始文件(URI)→抽取字段→汇总结论」血缘保留（审计）

### 6.4 浏览器自动化策略（据调研 01 模式 6 + 调研 03）
- 固定可重复流程 → 确定性 Playwright 脚本（登录态、导航、点下载、落盘），可靠可审计
- 布局多变/无 API/未知页面 → LLM/Computer Use 兜底（仅兜底）
- 下载即校验：文件名/类型/大小/非空/来源对应；失败 3 次即停、换路径/升级人工，不无限重试
## 7. 验收标准（AC）

- AC1：输入仅客户名/周期/受众，全流程可一键触发（或分步触发），无需手工编排
- AC2：取数完整性可自证（分页触顶校验+快照时间戳），任何「查无数据」结论前有完整性举证（落实 11-08 整改）
- AC3：六类标准产物 schema 校验 100% 通过（黄金基准：建行实例产物为准）
- AC4：签约汇总每条条款结论可回溯到具体合同文件+条款号（血缘可验证）
- AC5：两道人工闸（文件齐套确认、对外稿签发）生效，闸内暂停、闸后从断点精确恢复
- AC6：换客户名（如「山东省城市商业银行合作联盟有限公司」）重跑，输出结构一致、口径一致
- AC7：断点恢复不重跑已取文件（幂等、可审计）
- AC8：对外副作用（OA 流程发起、邮件、发送）一律停等人工确认
- AC9：E2E 用真实浏览器+真实 HTTP 验证（禁止 TestClient 冒充）

## 8. 边界与不做

- 不做：不新增 Agent/角色（复用 PM/合同专家入口）；不建 DAG 执行引擎（薄 runner 即可）
- 不做：不替代客户签字/审批（自动产出到「待确认」，签字必须人工）
- 不做：不自动发起 OA 流程（停等确认）
- 不做：不把凭据写入任何 markdown

## 9. 里程碑（后续文档按铁律顺序产出）

```
PRD（本文）→ 你审通过
  → DESIGN-OUTLINE → DESIGN-DETAIL → 测试方案(VERIFICATION) → OPERATIONS → IMPLEMENTATION-PLAN
  → 建设 → E2E 自测（真实浏览器）→ E2E 人工
首个实例 = 中国建设银行（既是业务目标，又是黄金基准）
```
