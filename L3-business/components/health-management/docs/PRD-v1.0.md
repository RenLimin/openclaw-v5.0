## 1. 背景与目标

### 1.1 背景

个人健康数据长期分散在不同渠道（体检报告、医院病历、智能手环、手动记录），缺乏统一的结构化存储和长期跟踪能力。L4 专有业务层（如家庭健康管理、企业健康福利）均需要健康数据底座，但各做一套会造成重复建设。

### 1.2 目标

提供 L3 通用健康数据管理能力，覆盖**健康档案、体检记录、生命体征、用药管理、风险评估、健康计划**六大领域，为上层 L4 业务提供统一的数据模型和仓储接口。

### 1.3 非目标

- ❌ 不提供计算/分析能力（由 L4 或独立 health-engine 承担）
- ❌ 不提供 Web UI（由 L4 层实现）
- ❌ 不做权限控制（由 L4 层通过 tenant_id 隔离）
- ❌ 不接外部设备/API 数据同步

## 3. 功能清单

### P0 — 核心能力

| 编号 | 功能 | 描述 |
|---|---|---|
| F-001 | 健康档案管理 | 个人基本信息、生活方式、家族病史、过敏史的 CRUD |
| F-002 | 体检记录管理 | 体检报告结构化录入、查询、历史对比 |
| F-003 | 生命体征追踪 | 血压、心率、血糖、体重等指标的记录与趋势查询 |
| F-004 | 用药管理 | 药品名、剂量、频次、起止时间、用药提醒基础数据 |
| F-005 | 风险评估记录 | 健康风险评估结果存储（评估逻辑由上层提供） |
| F-006 | 健康计划管理 | 健康目标、计划项、执行进度跟踪 |
| F-007 | 多租户隔离 | 所有实体携带 tenant_id，数据天然隔离 |
| F-008 | 软删除 | 所有操作通过 is_deleted 标记，不物理删除 |

### P1 — 增强能力

| 编号 | 功能 | 描述 |
|---|---|---|
| F-010 | 指标趋势查询 | 按时间范围、指标类型查询指标序列 |
| F-011 | 体检对比 | 两次体检数据字段级对比 |
| F-012 | 用药提醒基础 | 用药频次与时间配置化存储 |
| F-013 | 健康计划进度 | 计划完成率自动计算 |

### P2 — 未来规划

| 编号 | 功能 | 描述 |
|---|---|---|
| F-020 | 数据导出 | CSV / JSON 格式导出健康档案全量数据 |
| F-021 | 数据导入 | 批量导入体检/指标数据 |
| F-022 | 家庭成员 | 多 profile 关联，支持家庭健康管理 |

## 4. 验收标准

### 4.1 功能验收

| 编号 | 验收项 | 验证方式 |
|---|---|---|
| AC-001 | 6 大领域模块均可独立完成 CRUD 操作 | 单元测试全部通过 |
| AC-002 | 所有实体包含 tenant_id，跨租户数据不可见 | 集成测试验证隔离性 |
| AC-003 | 所有删除操作为软删除，数据可恢复 | 测试 delete 后 is_deleted 状态 + 可查询已删除记录 |
| AC-004 | Pydantic 模型验证生效，非法数据拒绝入库 | 边界值测试 |
| AC-005 | BaseRepository 提供统一 CRUD 接口，各领域 repo 继承复用 | 代码审查 + 单测覆盖 |

### 4.2 非功能验收

| 编号 | 验收项 | 标准 |
|---|---|---|
| AC-010 | 代码结构 | 领域驱动分层，每个领域独立 models + repository |
| AC-011 | 测试覆盖 | 7 个测试文件，覆盖全部 6 个领域 + base repo |
| AC-012 | 数据库迁移 | 单文件 SQL 迁移脚本，可执行初始化 |
| AC-013 | L4 适配性 | L4 可直接 import 本组件模型与仓储，无反向依赖 |

## 5. 技术约束

- **语言**: Python 3.10+
- **模型验证**: Pydantic
- **数据访问**: Repository 模式，SQLite/MySQL 适配
- **分层规则**: L3 不依赖 L4，仅依赖 L2 基础设施
- **依赖方向**: L4 → L3（单向）
