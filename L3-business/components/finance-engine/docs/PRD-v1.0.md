## 1. 背景与目标

### 1.1 背景

个人/家庭理财场景中，多个 L4 专有业务（如 FIN-L4 家庭理财系统、企业员工福利、保险工具）都需要底层的财务计算能力——贷款核算、保险测算、投资分析、复式记账等。如果每个 L4 业务各自实现，会造成：

- 重复开发，维护成本高
- 计算口径不一致（同一贷款不同模块算出来不一样）
- 精度与边界条件处理不统一

### 1.2 目标

提供 L3 通用理财计算引擎，覆盖**复式记账、贷款核算、保险测算、利率服务、投资组合、理财建议**六大领域，为上层 L4 业务提供统一、精确、可复用的纯函数式计算能力。

### 1.3 核心原则

- **纯函数式**：输入 → 计算 → 输出，不修改全局状态
- **无持久化**：不直接读写数据库，数据由 L4 层注入
- **单向依赖**：L4 → L3，L3 不感知 L4
- **唯一 IO 例外**：`fin004_rate` 含本地文件缓存（TTL 24h）

### 1.4 非目标

- ❌ 不提供 Web UI（由 L4 层实现）
- ❌ 不做权限控制（由 L4 层实现）
- ❌ 不做数据持久化（由 L4 层实现）
- ❌ 不接用户账号体系
- ❌ 不做风控/合规审批

## 4. 验收标准

### 4.1 功能验收

| 编号 | 验收项 | 验证方式 |
|---|---|---|
| AC-001 | 6 大引擎模块功能完整 | 单元测试全部通过 |
| AC-002 | 贷款 4 种还款方式计算正确 | 与银行计算器对比误差 < 0.01 元 |
| AC-003 | 保险 IRR 计算收敛（牛顿迭代） | 迭代 ≤ 200 次收敛，精度 1e-8 |
| AC-004 | 复式记账借贷平衡 | 试算平衡表借贷相等 |
| AC-005 | 利率服务缓存机制生效（TTL 24h） | 首次请求走网络，二次走缓存 |
| AC-006 | 投资收益计算正确（金额加权 + 时间加权） | 与基准公式一致 |
| AC-007 | 财务 KPI 诊断分级正确（good/warning/danger） | 符合 KPI_BENCHMARKS |
| AC-008 | 纯函数式：相同输入 → 相同输出 | 幂等性测试 |
| AC-009 | Decimal 精度，无浮点数误差 | 全部金额计算使用 Decimal |

### 4.2 非功能验收

| 编号 | 验收项 | 标准 |
|---|---|---|
| AC-010 | 单向依赖 | L3 不 import 任何 L4 代码 |
| AC-011 | 可测试性 | 纯函数设计，单测易写，覆盖率 > 85% |
| AC-012 | 性能 | 单笔贷款摊销 < 1ms；10 年期保险 IRR < 10ms |
| AC-013 | 精度 | 金额 2 位小数（四舍五入）；利率保留高精度 |
| AC-014 | 可扩展性 | 新增险种/还款方式只需扩展枚举 + 函数 |
| AC-015 | L4 适配性 | fin-l4 可直接 import 本引擎，零修改 |

## 5. 技术约束

- **语言**: Python 3.10+
- **精度**: `decimal.Decimal`（所有金额计算）
- **数据结构**: `dataclass`（纯数据，无需 Pydantic 验证层）
- **缓存**: 本地 JSON 文件（fin004_rate 专用）
- **架构风格**: 纯函数式 + 模块独立
- **依赖方向**: L4 → L3（单向）
