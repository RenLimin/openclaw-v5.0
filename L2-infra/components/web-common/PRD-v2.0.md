# web-common — 产品需求文档 (PRD)

> 组件：web-common (L2 基础设施层)
> 版本：v2.0
> 日期：2026-10-17
> 状态：proposed
> 关联 ADR：ADR-033

## 1. 概述

web-common 是 L2 基础设施层的 Web UI 公共组件，为 L3/L4 所有 Web 应用提供统一的设计系统、组件库、视觉回归测试和 UI 验收体系。

**v2.0 升级背景**：v1.0 仅提供基础模板宏和静态资源，缺乏设计系统规范和视觉质量保障。BDMS 等项目的 UI 调试暴露了布局不一致、间距不统一、视觉验收缺失等低级问题，需系统性升级。

**目标**：从"CSS 文件集合"升级为完整的 **Web UI 设计开发能力体系**，确保所有 Web 页面视觉一致、布局规整、质量可控。

## 3. 用户故事

### 3.1 开发者视角
作为 L3/L4 组件开发者，我希望有统一的 Design Tokens 和组件库，这样：
- 不用每个项目重新定义颜色/间距/字号
- 直接复用组件，开发效率高
- 页面风格自然一致

### 3.2 质量保障视角
作为交付负责人，我希望有自动化视觉回归测试，这样：
- 改一个页面的 CSS 不会弄坏其他页面
- 布局/对齐/间距等低级问题不会流到用户
- 交付质量有数据化指标

### 3.3 Rex 视角
作为系统负责人，我希望 UI 问题在开发阶段就被发现，不用我反复指出低级问题，这样：
- 交付一次到位，减少往返
- 整体视觉品质有保障
- 我只需要拍板审美方向，不用抠细节

## 4. 验收标准

### 4.1 Design Tokens
- [ ] 六大类 Tokens 完整定义（颜色/间距/字号/圆角/阴影/断点）
- [ ] CSS 变量实现，与现有样式平滑过渡
- [ ] 文档齐全，每个 Token 有用法说明

### 4.2 视觉回归测试
- [ ] Playwright Python 安装并可用
- [ ] 单页面截图对比测试可运行
- [ ] 基准图管理机制清晰
- [ ] Diff 报告可查看
- [ ] 动态内容 mask 机制可用

### 4.3 UI 验收 Checklist
- [ ] 5 大类 25+ 检查项完整
- [ ] 每项有明确的判断标准和检查方法
- [ ] 嵌入交付 7 步法流程

### 4.4 组件库规范化
- [ ] 4 个 macro 文档补齐
- [ ] 每个组件有示例代码和效果图
- [ ] 暗/亮双主题完整覆盖

### 4.5 UI 设计师角色
- [ ] 角色定义文件完整
- [ ] 走查工作流文档化
- [ ] 可通过 role-library 调用

## 5. 非功能需求

| 维度 | 要求 |
|---|---|
| **一致性** | 所有 L3/L4 Web 组件使用统一的 Design Tokens |
| **可维护性** | Tokens 单一来源，修改一处全局生效 |
| **可测试性** | 每个页面可一键跑视觉回归测试 |
| **性能** | 视觉回归测试单页面 < 5 秒（不含首次基准图） |
| **兼容性** | v2.0 向后兼容 v1.0，现有页面不破坏 |

## 6. 范围边界

### 包含
- Design Tokens 体系建设
- 现有组件库规范化和文档补齐
- 视觉回归测试基础设施
- UI 验收 Checklist 和流程
- UI 设计师角色定义
- 现有页面 UI 走查和批量修复

### 不包含
- 完整的 UI/UX 设计能力（AI 模型本身的视觉感知局限）
- 交互设计师角色（复杂交互设计仍需专业设计师）
- 设计稿到代码的自动生成
- 移动端适配的全面升级（后续单独规划）
- React/Vue 等前端框架引入（保持 Jinja2 + 原生 CSS 技术栈）

## 7. 演进路线

| Phase | 内容 | 预计工时 | 交付物 |
|---|---|---|---|
| **Phase 1** | 基础设施：Design Tokens + 视觉测试框架 + Checklist + UI 角色 | 3 天 | Tokens 文档 + 测试框架 + Checklist + 角色定义 |
| **Phase 2** | 组件库升级：规范化 + 文档补齐 + 主题验证 + CI 接入 | 5 天 | 组件文档 + 测试 CI 化 |
| **Phase 3** | 全量走查：7 组件 × 71 页面逐一排查和修复 | 7 天 | 基准图库 + 修复报告 |
