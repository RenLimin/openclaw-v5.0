# AI 知识库 - 检索增强引擎详细设计 v1.0

> L2 Infrastructure Component · ai-knowledge-base
> 版本：v1.0 · 状态：Draft
> 最后更新：2026-10-18

---

## 1. 设计目标

1. **高召回率**：用户换各种方式问都能找到相关知识
2. **高准确率**：Top-K 结果相关性高，减少无效信息
3. **多级回退**：精确匹配 → 模糊匹配 → 语义匹配 → 图谱扩展，层层兜底
4. **可解释性**：每个结果都有明确的召回路径和相似度分数
5. **可配置性**：检索策略、权重、阈值均可配置，适配不同领域知识库
6. **高性能**：万级切片 P95 < 500ms，百万级切片 P95 < 2s

## 2. 检索架构

### 2.1 整体流程

```
用户查询
    ↓
┌─────────────────────────┐
│   查询预处理与改写       │
│   - 分词/清洗/纠错       │
│   - 查询扩展（同义词）   │
│   - 查询分解（多意图）   │
└───────────┬─────────────┘
            ↓
┌──────────────────────────────────────────┐
│               多路召回                   │
│  ┌──────┐ ┌──────┐ ┌──────┐ ┌────────┐ │
│  │实体精│ │ FTS  │ │向量  │ │图谱扩展│ │
│  │确匹配│ │关键词│ │相似度│ │  召回  │ │
│  └──────┘ └──────┘ └──────┘ └────────┘ │
└──────────────────────┬───────────────────┘
                       ↓
┌──────────────────────────────────────────┐
│            融合排序 (Recall Fusion)      │
│  - 去重                                  │
│  - 多路分数归一化 + 加权融合              │
│  - 权限过滤 + 过期过滤                   │
└──────────────────────┬───────────────────┘
                       ↓
┌─────────────────────────┐
│   精排序 (Rerank)       │  ← 可选，Phase 2
│   交叉编码器重排 Top-N  │
└───────────┬─────────────┘
            ↓
┌─────────────────────────┐
│   上下文压缩           │  ← 可选，Phase 2
│   提取最相关片段       │
└───────────┬─────────────┘
            ↓
返回 Top-K 结果（含来源引用 + 相似度 + 召回路径）
```

### 2.2 模块划分

| 模块 | 职责 | 关键类 |
|---|---|---|
| QueryProcessor | 查询预处理、改写、扩展 | `QueryProcessor`, `QueryRewriter` |
| EntitySearch | 实体精确/模糊匹配 | `EntitySearcher` |
| FtsSearch | 全文关键词检索 | `FtsSearcher` |
| VectorSearch | 向量相似度检索 | `VectorSearcher` |
| GraphSearch | 知识图谱扩展检索 | `GraphSearcher` |
| FusionRanker | 多路召回融合排序 | `FusionRanker` |
| Reranker | 交叉编码器精排 | `CrossEncoderReranker` |
| ContextCompressor | 上下文压缩 | `ContextCompressor` |
| RetrievalEngine | 检索引擎统一入口 | `RetrievalEngine` |

## 3. 查询预处理与改写

### 3.1 查询预处理

| 步骤 | 操作 | 目的 |
|---|---|---|
| 清洗 | 去除特殊字符、多余空格、控制字符 | 规范化输入 |
| 纠错 | 常见错别字纠正（可选） | 提高召回率 |
| 分词 | 中英文分词 | 为后续处理做准备 |
| 意图识别 | 判断是查实体/查文档/查概念/对比等 | 选择最优检索策略 |
| 实体识别 | 识别查询中的已知实体名 | 优先走精确匹配 |

### 3.2 查询改写

| 改写策略 | 描述 | 示例 |
|---|---|---|
| 同义词扩展 | 用同义词典扩展查询词 | "APP加固" → "APP加固 / 应用加固 / 移动端加固" |
| 缩写展开 | 缩写展开为全称 | "APT" → "APT / 高级持续性威胁" |
| 中英文转换 | 中文 ↔ 英文术语互转 | "人工智能" → "人工智能 / AI" |
| 错别字纠正 | 基于词典的纠错 | "梆梆安全" → （已正确，不变） |
| 查询分解 | 复杂问题拆成多个子查询 | "A和B有什么区别" → 分别检索A和B |

### 3.3 查询质量评估

评估查询的"可检索性"：
- **明确实体**：查询包含明确实体名 → 高置信度走实体精确匹配
- **描述性问题**：自然语言描述 → 走向量 + FTS 混合检索
- **模糊查询**：过于宽泛/简短 → 降低召回阈值，增加多样性

## 4. 多路召回

### 4.1 召回通道

#### 通道 1：实体精确匹配（Entity Search）

**适用场景**：用户明确知道实体名称（产品名、文档名等）

**匹配策略**（按优先级）：
1. 完全匹配（`name = ?` 或 `code = ?`）
2. 别名匹配（`aliases` 中包含查询词）
3. 前缀匹配（`name LIKE ?%`）
4. 模糊匹配（`name LIKE %?%`）
5. FTS 名称全文检索

**返回**：匹配的实体列表 + 匹配类型得分

**评分**：
| 匹配类型 | 基础分 |
|---|---|
| 完全匹配 | 1.0 |
| 别名完全匹配 | 0.9 |
| 前缀匹配 | 0.75 |
| 模糊匹配 | 0.6 |
| FTS 匹配 | 0.5 |

#### 通道 2：FTS 关键词检索

**适用场景**：关键词明确的查询

**技术**：SQLite FTS5（默认）/ PostgreSQL GIN（生产版）

**查询构造**：
- 中文：分词后用 AND 连接主要关键词，OR 连接扩展词
- 英文：直接用短语查询 + 词干提取
- 支持 NEAR 操作符（词距控制）

**评分**：BM25 分数归一化到 [0, 1]

#### 通道 3：向量相似度检索

**适用场景**：语义描述性查询，用户不知道确切关键词

**技术**：
- 轻量版：全量 NumPy 余弦相似度计算（< 10万切片可行）
- 标准版：HNSW / IVF 索引（FAISS / Annoy / Qdrant）
- 企业版：Milvus 分布式向量数据库

**相似度计算**：cosine similarity（余弦相似度）

**评分**：相似度分数，范围 [0, 1]

#### 通道 4：知识图谱扩展检索

**适用场景**：需要关联知识的查询

**策略**：
1. 先通过实体匹配找到起始实体
2. 沿知识图谱关系扩展 1-2 跳
3. 将扩展出的关联实体的文档也加入召回
4. 按关系权重和距离衰减打分

**评分**：`基础分 * 关系权重 * 衰减因子^跳数`

### 4.2 召回策略配置

每个知识库实例可以独立配置召回策略：

```yaml
retrieval:
  channels:
    entity:
      enabled: true
      weight: 1.2
      top_k: 10
    fts:
      enabled: true
      weight: 1.0
      top_k: 20
    vector:
      enabled: true
      weight: 0.9
      top_k: 20
    graph:
      enabled: false  # 可选开启
      weight: 0.8
      max_depth: 2
      top_k: 10
  
  fusion:
    method: weighted_sum  # weighted_sum / rrf / reciprocal_rank
    top_k: 5
  
  rerank:
    enabled: false
    model: cross-encoder
    top_n: 20
```

## 5. 融合排序

### 5.1 融合算法

#### 方法 1：加权求和（Weighted Sum）- 默认

```
最终得分 = Σ ( 通道权重 * 归一化分数 )
```

- 简单高效，可解释性强
- 适合通道间分数分布已知的场景
- 权重可配置，按领域调整

#### 方法 2：倒数秩融合（RRF - Reciprocal Rank Fusion）

```
RRF 得分 = Σ ( 1 / (k + 排名) )
```

- 不需要归一化，对不同分数分布鲁棒
- 适合多路召回质量参差不齐的场景
- k 通常取 60

#### 方法 3：相对排名融合

```
得分 = Σ ( 1 - 排名/总结果数 ) * 通道权重
```

- 简单直观，兼顾排名和权重

### 5.2 过滤层

融合后，经过以下过滤：

| 过滤器 | 作用 | 可配置 |
|---|---|---|
| 相似度阈值过滤 | 低于最低相似度的结果丢弃 | 是（默认 0.3） |
| 过期过滤 | status=expired 的实体丢弃（默认） | 是（include_expired 开关） |
| 权限过滤 | 当前用户无权访问的文档/切片丢弃 | 是（ABAC权限系统） |
| 去重过滤 | 同一文档的多个相似chunk只保留最相关的 | 是（per_doc_max 配置） |
| 最小来源数 | 有效结果不足时触发降级策略 | 是（默认 1） |

### 5.3 降级策略

当高质量召回结果不足时：

| 情况 | 降级动作 |
|---|---|
| 精确匹配 0 结果 | 降低阈值，扩大模糊匹配范围 |
| 所有通道结果都很少 | 开启更多通道（如图谱扩展） |
| 相似度普遍偏低 | 降低相似度阈值，但标注低置信度 |
| 完全没有相关结果 | 返回空结果 + 建议改写查询 |

## 6. 重排序（Rerank）- Phase 2

### 6.1 作用

多路召回融合后的 Top-N 结果（如 20-50 条），用更精确的交叉编码器计算查询与每个chunk的相关性，重新排序，提升 Top-K 的准确率。

### 6.2 技术选型

| 方案 | 适用场景 | 特点 |
|---|---|---|
| 本地 CrossEncoder | 小数据量/离线 | 部署简单，速度中等 |
| 重排序 API（如 Cohere Rerank） | 云端部署 | 效果好，有API成本 |
| LLM 打分 | 高质量要求 | 最准但最慢，适合少样本 |

### 6.3 集成方式

- 可插拔：通过配置开启/关闭
- 缓存：相同查询+相同chunk的重排序结果缓存
- 异步：重排序耗时较长时，可先返回粗排结果，后台异步重排更新

---

## 7. 上下文压缩 - Phase 2

### 7.1 作用

将召回的chunk进一步压缩，只保留与问题最相关的句子/片段，减少 token 消耗，提高答案精准度。

### 7.2 压缩策略

| 策略 | 描述 |
|---|---|
| 句子提取 | 将chunk拆成句子，计算每个句子与查询的相似度，保留 Top-M 句子 |
| 关键词高亮 | 提取包含查询关键词的句子和上下文 |
| 摘要式压缩 | 用LLM对chunk生成摘要（可能丢失细节，慎用） |

## 8. 结果格式

### 8.1 检索结果结构

```python
@dataclass
class RetrievalResult:
    query: str                     # 原始查询
    rewritten_query: str           # 改写后的查询
    total_found: int               # 总匹配数
    results: List[ChunkResult]     # Top-K 结果
    confidence: str                # 整体置信度：high / medium / low
    search_path: str               # 主要召回路径说明

@dataclass
class ChunkResult:
    entity: Dict                   # 关联实体信息
    doc: Dict                      # 关联文档信息
    chunk: Dict                    # 切片信息（文本、标题、位置等）
    score: float                   # 最终综合得分 [0, 1]
    scores: Dict[str, float]       # 各通道的原始得分（用于调试）
    recall_channels: List[str]     # 从哪些通道召回的
    rank: int                      # 最终排名
    permission_level: str          # 权限级别
```

### 8.2 置信度评估

根据以下因素综合评估检索结果的置信度：

| 因素 | 高置信度 | 中置信度 | 低置信度 |
|---|---|---|---|
| 有效结果数 | ≥ 5 | 2-4 | 0-1 |
| 最高分 | ≥ 0.8 | 0.5-0.8 | < 0.5 |
| 来源多样性 | ≥ 3 个文档 | 2 个文档 | 1 个文档 |
| 实体匹配 | 有精确匹配 | 有模糊匹配 | 无实体匹配 |

## 9. 性能优化

### 9.1 索引优化

- **FTS 索引**：定期 `optimize`，减少碎片化
- **向量索引**：
  - < 1万条：暴力计算（简单准确）
  - 1万-100万条：HNSW 索引（FAISS / Annoy）
  - > 100万条：分布式向量库（Milvus / Qdrant）
- **实体索引**：名称、别名、编码都建索引

### 9.2 查询优化

- 查询缓存：相同查询直接返回缓存结果（可配置TTL）
- 热门知识预热：高频查询的结果预加载
- 慢查询日志：记录超过阈值的查询，用于优化

### 9.3 并发优化

- 多路召回并行执行（多线程/协程）
- 连接池管理
- 限流保护（防止打爆底层存储）

## 10. 可调试性

### 10.1 检索解释（Explain）

提供 `explain` 模式，返回详细的检索过程信息：
- 每个通道的召回结果和分数
- 融合排序的计算过程
- 过滤掉的结果及原因
- 总耗时和各阶段耗时

### 10.2 评估工具

- **检索质量评估**：输入测试集（查询+相关文档），输出 Recall@K / Precision@K / NDCG 等指标
- **A/B 测试**：支持两种检索策略对比测试
- **Badcase 分析**：收集效果不好的查询，分析原因，持续优化
